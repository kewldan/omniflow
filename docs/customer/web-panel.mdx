The customer web panel is the browser half of the product the Telegram bot has
carried since v0.2. It is not a second product: it reads the same customer
records, the same entitlements, and the same Remnawave state, and a customer who
signs in with Telegram on the web lands on exactly the account the bot has been
using.

It is served by the same Next.js application as the operator panel, under
`/account`, and backed by a third API prefix, `/v1/account`.

Every one of these is the same record the bot reads and writes. A cart started
in a chat is the cart the browser shows; a support reply read on the web stops
being unread in Telegram. There is one product with two surfaces.

## Enabling it

The panel is on by default and needs `APP_DATA_ENCRYPTION_KEY`, which seals OIDC
client secrets and the short-lived sign-in flow cookie.

| Variable | Default | Purpose |
| --- | --- | --- |
| `APP_CUSTOMER_PANEL_ENABLED` | `true` | Mounts `/v1/account`. A Telegram-only installation can turn it off. |
| `APP_CUSTOMER_COOKIE_SECURE` | `true` | Marks the session cookie `Secure`. Turn it off only for a plain-HTTP local stack. |
| `APP_CUSTOMER_MAGIC_LINK_ENABLED` | `false` | Offers the bot-delivered sign-in link. Requires `APP_PUBLIC_URL`. |
| `APP_SUPPORT_ATTACHMENT_DIR` | `/var/lib/omniflow/support-attachments` | Where a file uploaded through the web panel is kept. Mount a volume at it. |

The checkout reads `APP_TERMS_URL`, `APP_RECOVERY_WINDOW_HOURS`, and
`APP_TRIAL_MINIMUM_ACCOUNT_AGE_HOURS` — the same variables the bot reads, so one
`.env` configures both processes identically. A trial the chat refuses and the
browser grants would be an abuse control with a hole in it.

<Note>
  A ticket opened in Telegram stores only a Telegram file reference, because the
  bytes stay with Telegram. A browser upload has no such custodian, so the
  installation holds it — which is why the panel needs a writable directory and
  the bot does not.
</Note>

<Warning>
  Leaving `APP_CUSTOMER_COOKIE_SECURE` off in production means the session cookie
  can be captured from any plain-HTTP request to the same host.
</Warning>

## Sign-in

### Telegram

The primary route. Telegram's login widget signs its fields with HMAC-SHA256
under the bot token, so a payload that verifies is proof Telegram produced it for
this bot. Omniflow additionally bounds `auth_date` to one minute: the hash never
expires on its own, and without the bound a payload captured from a URL or a
screenshot would authenticate indefinitely.

The widget is loaded by the bot's username, which Omniflow resolves from the bot
API on first use. Telegram only renders the widget on a domain bound to the bot,
so set that domain with `/setdomain` in BotFather before enabling it.

Opened as a Telegram Mini App the panel signs in with no button at all: the
surrounding client hands the page a signed `initData`, which is verified the same
way under a different key derivation.

### The sign-in link

An operator-enabled fallback for installations where the widget is not usable.
The customer sends `/login` to the bot and receives a one-time link, valid for
ten minutes and single-use.

It is requested from the bot rather than from a web form on purpose. A form would
have to take some identifier and answer whether Omniflow knows it, and every
version of that answer tells a stranger whether somebody is a customer here.
Starting inside a chat the customer has already authenticated to removes the
question, and guarantees the link can only reach somebody who already controls
the account.

<Note>
  The link is a bearer credential for ten minutes. The bot says so in the message
  and sends it with forwarding disabled.
</Note>

### OIDC

Any number of providers may be enabled at once, each an ordinary discovery
document with an operator-chosen label, icon, and ordering. The flow is
Authorization Code with PKCE, an anti-forgery `state`, and a `nonce` verified
against the returned ID token.

Presets for Google, Yandex, and Discord prefill the form and produce ordinary
rows; nothing downstream branches on which provider a row came from.

<Warning>
  Yandex does not consistently return `email_verified`. Its preset therefore
  leaves the verified-email requirement off — turning it on for that provider
  refuses every sign-in through it.
</Warning>

Two rules govern how an external identity maps to a customer:

- **A subject nobody has linked never adopts an existing account by email.**
  Matching on an address would let anyone who can make a provider assert somebody
  else's address take over their account. An unlinked subject either provisions a
  fresh customer, when the provider allows it, or is refused.
- **Linking happens from inside a session.** An existing customer adds a provider
  from their own security screen. If the subject already belongs to another
  customer the attempt is refused as a conflict, never merged: joining two
  customers would move one person's orders, wallet, and subscription into another
  person's account with no way back.

Because the subject is the key and the address is only a claim, a customer
changing their email upstream is a non-event and needs no recovery path.

## Sessions

Sessions are cookie-backed, `__Host-` prefixed, `HttpOnly`, and `SameSite=Lax`.
Only the SHA-256 of the token is stored, so a database read never yields a usable
cookie.

| Property | Customer panel | Operator panel |
| --- | --- | --- |
| Inactivity timeout | 14 days | 30 minutes |
| Absolute lifetime | 60 days | 12 hours |
| Token rotation | every 24 hours | every 15 minutes |
| Re-authentication window | 15 minutes | — |

The customer figures are deliberately more generous. An operator signing in again
costs seconds of a working day; a customer checking how many days are left does
not warrant the same friction, and a panel that logs them out over lunch simply
pushes them back to the bot. The absolute horizon and rotation do the security
work instead, together with re-authentication on the few actions that warrant it.

**Re-authentication** applies to the actions a stolen but still-live cookie could
otherwise use to lock the real owner out: rotating the subscription link,
disconnecting every device at once, and removing a sign-in method. Each is
destructive, none is reversible from the panel, and all are rare and deliberate.
A session older than fifteen minutes is refused with
`reauthentication_required`, and the panel says so before the button is pressed
rather than after.

Every unsafe request carries a double-submit CSRF token derived from a
per-session secret, so a token minted for one session cannot be replayed in
another — and the customer and operator panels derive theirs under different
labels, so neither can mint a credential for the other.

## The subscription screens

The dashboard answers the question customers open it with: is my subscription
working, and how long is left. The subscription switcher appears only when the
installation allows concurrent subscriptions; a single-subscription installation
keeps the one-screen experience with no selection step.

Traffic is shown as a bar and, above it, as a sentence — the textual equivalent
is visible to everyone rather than hidden for assistive technology, and the bar
carries that same sentence as its accessible name. The percentage is computed on
the server so the two can never disagree.

When Remnawave cannot be reached the page still renders what Omniflow itself
knows — the plan, the period, the expiry — and says which figures are not
current, rather than presenting a traffic number that has stopped moving as
though it were live.

### Connecting a device

The connect screen exists to move one string onto another device. It offers a
deep link per documented client, a QR code rendered in the browser, and the raw
link with a copy button. The client list comes from the same table the bot
renders, so a customer who reads one recommendation in the chat and a different
one in the browser is impossible by construction.

### Rotating the access link

Rotation invalidates the old link on every device, and every device must import
the new one before it connects again. Traffic and expiry are unaffected. It is
the remedy when a link has been shared or leaked, and it sits behind a typed
confirmation as well as a recent sign-in.

## Devices and privacy

The panel never returns a hardware identifier or an IP address for a connected
device. A device is named by an opaque handle — a truncated digest the server
resolves back by hashing its own current list — so removing one never requires
the caller to hold the identifier being acted on. Last-seen is a date rather than
a precise instant: enough to recognise your own laptop, not enough to build a
movement log from.

Subscription links are credentials, so every `/v1/account` response is sent with
`Cache-Control: no-store` and `Referrer-Policy: no-referrer`. The QR code is
generated in the browser rather than fetched as an image, which would otherwise
put the link into a request line, a proxy log, and the browser cache.

## Account history

The security screen lists live sessions, the linked sign-in methods, and an
account history the customer can read: sign-ins, sign-outs, link rotations,
device removals, and changes to sign-in methods.

That history is a separate record from the operator audit trail. The audit trail
is an operator artefact searched under operator permissions, and deciding per row
which of its fields a customer may see would put a disclosure decision in the
read path. The customer-facing log is written to be shown: its vocabulary is
closed, and it has no column for an amount, a link, or another party's
identifier.

Removing a sign-in method is refused when it is the last one. A customer who
removes their only way in has locked themselves out of an account holding a paid
subscription, and nothing in the panel can let them back in.

## Buying and paying

The store screen compares plans on the terms that decide a purchase: period,
traffic allowance, device limit, price, and currency. Eligibility is decided by
the server and arrives with the plan, together with the lifecycle operations the
configured policy allows against the customer's current subscriptions — so the
panel offers *renew*, *upgrade*, or *downgrade* because the API said so, not
because React worked the rules out a second time.

A checkout is a resumable purchase intent, and a customer has at most one. It is
shared with the bot: opening a checkout in a browser supersedes one left open in
a chat rather than running beside it, because two half-finished purchases for one
person is a state neither surface could explain.

<Steps>
  <Step title="Choose a plan and a target">
    When concurrent subscriptions are enabled, every renewal, upgrade, and
    downgrade names the subscription it changes. A single-subscription
    installation renders no picker at all.
  </Step>
  <Step title="Configure it">
    Squads and add-ons, where the plan offers them, with the proration rule for
    each add-on stated rather than implied.
  </Step>
  <Step title="Apply a promo code">
    A refused code is answered with a reason — unknown, ineligible, exhausted,
    or malformed — and the quote is repriced without it, so the screen explains
    the outcome instead of failing.
  </Step>
  <Step title="Read the breakdown">
    Subtotal, add-ons, discount, wallet applied, and the external amount that
    still has to be settled. Every figure is computed by the server, so the
    number a customer approves and the number they are charged cannot be arrived
    at two different ways.
  </Step>
  <Step title="Pay">
    Only providers that are enabled *and* settle the chosen currency are
    offered. A hosted provider opens its own checkout; Telegram Stars sends an
    invoice to the chat; a wallet-covered order needs no handoff at all.
  </Step>
</Steps>

### When a payment does not land cleanly

Pending, successful, failed, cancelled, duplicate, and delayed-webhook each get a
screen that says what happened and what to do next. A **refresh** control
re-reads the provider rather than merely re-fetching Omniflow's own record, so a
customer who returns before the webhook arrives still sees the settled state.

Provisioning progress is read from the fulfillment operation the order created.
It therefore survives a page reload, a second tab, and a switch to Telegram — a
page that remembered "we are setting this up" in its own memory would forget it
exactly when the customer most wants to know.

<Note>
  Confirming a checkout reuses the checkout's own idempotency key, so a double
  tap or a retried request resolves to the order already created. The same is
  true of starting a payment, where the key is scoped to the order and the chosen
  adapter — switching provider is a new payment, pressing the same button twice
  is not.
</Note>

## Wallet

Balances are per currency and isolated: a balance in one currency never funds an
order in another. The ledger is append-only, so a correction appears as a
compensating entry rather than as an edited row.

Top-up runs through the same order, webhook, and reconciliation pipeline a plan
purchase uses, with the operator's preset amounts, minimum, maximum, and rolling
window applied. The caller's idempotency key becomes the order's key, so a
retried request credits the same top-up rather than a second one.

## Digital goods

The shop sells Telegram Premium and Stars under exactly the rules the bot
follows.

**A price is a quote with an expiry.** It is issued when a product is opened, not
when the catalogue is listed — a page of promises that begin expiring while it is
read would be worse than none. The panel shows the countdown, and the purchase
echoes the displayed quote back. The server re-quotes before charging and refuses
with a distinct reason when the window has passed or the number moved, so the
price on screen is always the price charged.

**The recipient is confirmed on its own.** The handle is normalised by the server
and shown in the exact form the gateway will be given, and the purchase is
refused unless the confirmed string is the one submitted. Delivery is
irreversible once a gateway has sent the goods, and a mistyped username cannot be
recovered.

**An ambiguous delivery parks.** The gateway that fronts Fragment honours no
idempotency key, so a lost answer is genuinely ambiguous: retrying might deliver
and charge twice, and refunding might refund goods that arrived. Such a delivery
moves to the operator review queue and the panel says so, offering support rather
than a retry button. A delivery that fails permanently is refunded to the wallet
through the existing pipeline.

## Support and news

Tickets are the operator desk's tickets and the bot's tickets — one conversation
per record, read from whichever surface the customer opened.

Unread state lives on the message rather than on the surface, so a reply read in
Telegram is not still bold on the web, and a customer who answers in a browser
appears in the operator queue exactly as one who answered in a chat.

Internal operator notes are never returned. They live in their own table and no
customer-facing query touches it, which is a stronger guarantee than filtering
them out would be.

Attachments are bounded by size and by an allowlist of media types — an unknown
type is refused rather than guessed at — and the limits are shown before an
upload rather than only after one is rejected. A file attached in Telegram stays
with Telegram and is named rather than offered for download, because offering a
download that cannot work is worse than saying where the file lives.

### Preferences and consent

Notification choices, quiet hours, and marketing consent are set here and apply
to both surfaces. Consent is append-only: a change records a new decision with
the surface and request that made it, so the question "when did this person opt
in, and where" always has an answer.

Unsubscribing stops marketing messages. It does not stop transactional ones about
a payment, an expiry, or a support reply — those are the messages a customer
needs in order to keep using what they bought.

Browser notifications are offered only behind an explicit opt-in, never requested
on page load, and they are foreground-only: the panel raises one for a new
operator reply or announcement it observes while the tab is open. There is no web
push, no service worker, and no stored subscription.

## Referrals and loyalty

The referral screen shows the code, its shareable link, the program terms and
qualification rule, the invited and qualified counts, the remaining slots against
the operator's cap, and the reward history with each reward's state.

A reversed reward is excluded from the earned total and from the cap count. An
operator reverses one when a referral turns out to be abuse, and the slot it
consumed comes back with it.

When no public URL is configured the panel shows the code and says no link can be
built, rather than rendering a link to nowhere.

Loyalty shows the current tier, the progress toward the next, and the rules that
govern it. Nothing on these screens grants a reward or promotes a tier: the
reward and evaluation workers already wrote those rows, and doing it on a page
load would make a customer's balance depend on which screen they opened.

## Personal data

### Export

A customer can download their own records: profile, identities, contacts,
subscriptions, entitlements, orders, payments, wallet ledger, support
conversations, referral and loyalty standing, consent history, and lifecycle
events.

It is produced synchronously rather than queued. A queued export would need a
delivery channel, a retention window, and a link that authenticates on its own —
three further disclosure decisions to answer a question that fits in one
response.

The document declares what it left out and why: no other customer's identifier,
no payment credential, no provider secret, no subscription link, and no device or
network identifier. It also names any section that hit its row cap, because an
export that silently omitted something would be worse than one that says so.

### Deletion

Requesting deletion records a request. It does not delete.

The retention workflow an operator already governs is what carries it out, so an
irreversible action never happens on the strength of one browser session. The
request needs a recent sign-in and a stated reason, it can be withdrawn until it
is executed, and cancelling it needs no re-authentication — cancelling only ever
prevents the irreversible thing.

### Identity conflicts

A contact address already registered elsewhere is refused with nothing more than
"not available here", and the remedy is contacting support. Saying that another
account holds it would turn the panel into an oracle for whether a given address
is a customer.
