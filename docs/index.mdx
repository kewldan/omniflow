Omniflow is an open-source commerce, support, and marketing platform for a VPN service that already
runs on [Remnawave](/integrations/remnawave). Remnawave stays authoritative for VPN users, traffic,
devices, access links, nodes, squads, and Xray state. Omniflow owns everything a business needs
around that: customer identity, a versioned catalogue, orders, payments, a double-entry wallet,
entitlements, durable provisioning, support, campaigns, referrals, loyalty, operator access control,
and an append-only audit trail. It never connects to Remnawave's database and never manages an Xray
process.

It is one Go module with three entrypoints — `api`, `bot`, and `worker` — sharing one PostgreSQL
database and one Valkey instance, plus one Next.js application that serves both the customer account
and the operator workspace. The split is about failure isolation, not scale: a batch of four hundred
subscription changes must not be tied to the lifetime of the HTTP request that started it, and
automatic renewals — the only place money moves with nobody watching — run where no request can
cancel them.

## Who each surface is for

| Surface | Who uses it | Where it lives | How a caller is authenticated |
| --- | --- | --- | --- |
| Telegram bot | A customer | A private chat with your bot | The Telegram account behind the update |
| Customer web panel | A customer | `/account`, backed by `/v1/account` | Session cookie plus CSRF token |
| Operator panel | An operator | `/admin`, backed by `/v1/panel` | Session cookie, CSRF, TOTP, and 27 RBAC permissions |
| Bearer-token API | Your own code, and the bot's `/ops` tooling | `/v1/admin` | `Authorization: Bearer <APP_OPERATOR_TOKEN>` |

The three `/v1` prefixes are kept apart deliberately. `/v1/panel` is a browser surface and therefore
carries cookie, CSRF, and permission checks; `/v1/admin` is a machine surface with one long-lived
token and no cookies; `/v1/account` belongs to a customer and can never reach an operator route. Two
more routes are public by necessity: `GET /v1/catalog/plans`, and
`POST /v1/payments/webhooks/{provider}`, whose authenticity comes from the provider's signature
rather than from a credential on the route.

A customer does not choose between the chat and the browser. It is one product with two surfaces: a
cart started in a chat is the cart the browser shows, and a support reply read on the web stops
being unread in Telegram.

## What Omniflow deliberately does not do

- **It does not manage Xray, and it does not read Remnawave's database.** Every VPN-side change is
  an authenticated call to the Remnawave API, made by the fulfillment pipeline so that it carries an
  idempotency key, a retry policy, and a history. See [Data ownership](/architecture/data-ownership).
- **It does not show an operator a subscription link, a hardware identifier, or a raw provider
  payload.** A device is named by an opaque handle the server resolves back; a fulfillment history
  returns a status, a classification, and a correlation ID and nothing else.
- **It does not delete financial, audit, consent, identity, or entitlement history.** Retention
  sweeps remove disposable operational data only, and a wallet correction is a compensating entry
  rather than an edit. See [Financial invariants](/commerce/financial-invariants).
- **It does not reconfigure itself from the panel.** Runtime configuration is environment variables,
  read once at startup by each process; the panel's installation-settings sections store what an
  operator types, and no process reads those documents back while running. See
  [Installation settings](/operations/installation-settings) and
  [Configuration](/getting-started/configuration).
- **It does not perform a model call or an MCP tool call.** The AI and MCP surfaces in this build
  register providers, enable features one at a time, set budgets, and allowlist tools; no process
  constructs a gateway or an MCP client, so nothing consumes that configuration at runtime. See
  [AI governance](/operations/ai-governance).
- **It does not coordinate replicas.** Every scheduled loop — maintenance detection, the payment
  reconciler, sweeps, renewals, campaigns, retention, backups — is an in-process ticker with no
  leader election, so the supported topology is one instance of each role. See
  [Deployment](/operations/deployment).
