---
title: Переезд с Bedolaga
description: Перенос клиентов, балансов, подписок и рефералов бота Bedolaga в Omniflow с отрепетированным переключением, при котором не меняется ни одна ссылка подписки
---

У установки, работающей на Telegram-боте Bedolaga, уже есть клиенты, деньги на их балансах и
оплаченные подписки, которые обслуживает Remnawave. Переезд на Omniflow — это перенести всё это, никого
не списав дважды, не потеряв ни копейки и не поменяв ни одной ссылки доступа, — и сохранить
возможность откатиться, если переключение пойдёт не так.

Данные переносит `cmd/migrate-bedolaga`. Он читает базу Bedolaga внутри одного снимка только для
чтения, читает список пользователей панели Remnawave и пишет в Omniflow через собственные таблицы и
сервисы Omniflow. Скрипты в `deploy/migration/` оборачивают его в репетицию на копии и в переключение с
подтверждениями.

<Note>
  Импортёр **никогда не пишет ни в Bedolaga, ни в Remnawave**. Подключение к Bedolaga открывается с
  `default_transaction_read_only=on`, и каждое чтение идёт в транзакции `READ ONLY`. Единственный
  вызов панели, который он может сделать, — список пользователей: у переданного ему интерфейса нет
  других методов, а у импортированного права доступа нет операции выдачи, поэтому не существует задачи,
  которая могла бы что-то отправить в панель. Пользователями и их ссылками подписки по-прежнему владеет
  Remnawave: ссылка клиента до переключения — это его ссылка и после.
</Note>

## Самый быстрый безопасный путь

<Steps>
  <Step title="Подготовьте Omniflow">
    Разверните Omniflow с применёнными миграциями, создайте версию плана для каждого тарифа Bedolaga,
    который ещё продаётся, и настройте используемых платёжных провайдеров — `00-convert-env.sh`
    перенесёт их ключи из `.env` Bedolaga. Бота и воркер Omniflow против боевой панели пока не
    запускайте.
  </Step>
  <Step title="Отрепетируйте на копии">
    `01-snapshot-bedolaga.sh`, `02-restore-staging.sh`, затем `03-plan.sh`, `04-apply.sh` и
    `05-verify.sh` против временной базы Omniflow. Повторяйте, пока в плане не останется конфликтов, по
    которым вы не приняли решение, и проверка не пройдёт. Запомните, сколько длился `apply`.
  </Step>
  <Step title="Переключитесь">
    `06-cutover.sh` останавливает Bedolaga, снимает финальный снимок, выполняет финальный импорт в бой,
    проверяет его, переносит Telegram-бота и вебхуки платежей и последним запускает воркер Omniflow.
  </Step>
  <Step title="Оставьте путь назад">
    Контейнеры Bedolaga оставьте остановленными, но не удаляйте. `07-rollback.sh` вернёт Bedolaga к
    клиентам, если понадобится.
  </Step>
</Steps>

## Что переносится и куда

| Bedolaga | Omniflow | Как |
| --- | --- | --- |
| Строка `users` | `users` | Статус, язык (`ru` или `en`; всё остальное становится `ru`) и исходный `created_at` |
| `users.telegram_id`, `username`, `first_name`, `last_name` | `identities` | Активная подтверждённая идентичность `telegram`; имена лежат в её `metadata` как `username`, `firstName`, `lastName` |
| `users.email` при `email_verified` | `contact_channels` | Вид `email`, зашифрован ключом `APP_DATA_ENCRYPTION_KEY`, подтверждён, транзакционные письма включены, маркетинг выключен. Неподтверждённый адрес не переносится |
| `users.status = 'blocked'` | `users.status = 'suspended'` | Только если в сопоставлении `blockedUsers: suspend`; причина записывается событием жизненного цикла `suspended` |
| `users.balance_kopeks` | `ledger_transactions` + `ledger_entries` | Одна аудируемая корректировка кошелька на клиента, см. [ниже](#балансы) |
| `users.remnawave_id` или пользователь панели первой активной подписки | `remnawave_users` | Сопоставление на уровне клиента, которое читает бот |
| Активная строка `subscriptions` | `subscriptions` + `orders` + `order_lines` + `entitlements` | См. [подписки](#подписки) |
| Истёкшая строка `subscriptions`, чей пользователь панели ещё существует | `subscriptions` | Привязана к этому пользователю панели, без права доступа |
| Активный пробный период | как выше, плюс `trial_claims` | Пробный период Bedolaga засчитывается клиенту как его единственный |
| `users.referred_by_id` | `referral_attributions` | Тот же пригласивший; квалифицирована, если приглашённый платил, см. [рефералы](#рефералы) |
| `tariffs` | — | Сопоставляются с версиями планов через ваш [файл сопоставления](#файл-сопоставления) |

Собственный учёт импортёра — две таблицы. `bedolaga_import_items` хранит по строке на каждого
пользователя, подписку и реферальную пару Bedolaga, по которым принято решение, — это долговременное
сопоставление ID Bedolaga с клиентом, подпиской и правом доступа Omniflow, — а `bedolaga_import_runs`
хранит каждый запуск `apply` с полным отчётом.

### Балансы

Bedolaga хранит балансы в копейках, а это минимальные единицы рубля, поэтому сумма переносится как
есть. Каждый положительный баланс становится одной корректировкой кошелька по тому же пути, что и
корректировка оператора: тип `credit`, ссылка `bedolaga-user:<id>:1`, причина из вашего сопоставления
(её видит клиент) и событие аудита `wallet.adjusted` с именем исполнителя. Нулевые балансы ничего не
пишут. Отрицательные балансы — конфликт и не переносятся.

Если баланс в Bedolaga изменился после предыдущего запуска — финальная дельта во время переключения, —
следующий запуск запишет разницу как `correction` с номерами `bedolaga-user:<id>:2`, `:3` и так далее.
Уже перенесённое читается из самого журнала проводок, поэтому запуск, упавший сразу после фиксации
движения, в следующий раз видит это движение и не начисляет дважды.

### Подписки

Подписка, которая в Bedolaga `active`, `trial` или `limited` и заканчивается в будущем, становится:

- подпиской в следующем свободном слоте клиента, подхватывающей пользователя Remnawave, который её уже
  обслуживает, — подписка сохраняет свою ссылку доступа, а продление потом обновит этого пользователя;
- заказом нулевой стоимости в состоянии `fulfilled` с операцией `purchase` и ключом идемпотентности
  `bedolaga:subscription:<id>`, с одной строкой на сопоставленную версию плана. В выручку он ничего не
  добавляет и нужен, чтобы привязать право доступа к плану;
- правом доступа со статусом из панели (`ACTIVE` → `active`, `LIMITED` → `limited`, `DISABLED` →
  `disabled`), которое начинается в `start_date` Bedolaga и заканчивается в `end_date` Bedolaga, с
  лимитом трафика, лимитом устройств и сквадами, которые панель держит для этого пользователя сейчас.

Зеркалирование лимитов панели сделано намеренно: когда заработает воркер Omniflow, его сверка каждые
пятнадцать минут отправляет право доступа в панель, и зеркало ничего не меняет. Дата окончания берётся
из Bedolaga, потому что платил клиент там; если она расходится со сроком в панели (после льготного
периода плана), план сообщает `expiry_differs_from_panel`, и первая сверка переведёт панель на дату
Bedolaga.

Подписка сопоставляется с пользователем панели по `subscriptions.remnawave_id`. У пользователя ровно с
одной подпиской без этого ID используется `users.remnawave_id` — так Bedolaga хранила его до
мультитарифов.

### Рефералы

Каждая пара, обе стороны которой импортированы, становится атрибуцией с датой регистрации в Bedolaga в
`created_at`. Если приглашённый платил в Bedolaga (`has_had_paid_subscription`), атрибуция приходит с
заполненным `qualified_at` и без квалифицирующего заказа. Пригласивший получил за неё награду в
Bedolaga, поэтому такая атрибуция в Omniflow больше не выплачивается; приглашённый, который не платил,
квалифицируется своим первым заказом в Omniflow как обычно, с учётом срока действия атрибуции в
программе.

## Что не переносится

| Остаётся в Bedolaga | Почему и что делать |
| --- | --- |
| История платежей: `transactions` и таблицы платежей по провайдерам | Журнал Omniflow записывает деньги, которые двигал Omniflow, и места только для добавления под платежи чужой системы нет. Архив — снимок из `01-snapshot-bedolaga.sh`; сохраните его |
| Заказы магазина звёзд (`stars_orders`) | Заказ товара в Omniflow требует настоящего заказа и котировки. План считает их по статусам и сумме; они остаются в архиве |
| Тикеты поддержки и сообщения | Закройте или ответьте на них в Bedolaga до переключения; план их считает |
| Промокоды и промогруппы | Их правила скидок не ложатся на акции Omniflow один к одному. План считает активные коды по типам и группы по участникам; нужное заново создайте в панели |
| История реферальных начислений и заявки партнёров на вывод | Заработанные деньги уже входят в переносимый баланс. Обработайте ожидающие выводы в Bedolaga заранее |
| Сохранённые способы оплаты и соглашения автоплатежа | Токены провайдера принадлежат настройке мерчанта Bedolaga; клиенты снова включают автопродление в Omniflow |
| Привязки OAuth, пароли кабинета, вход по почте | В Omniflow клиенты входят через Telegram или провайдера, которого вы там настроите. Клиент без Telegram ID и без подтверждённой почты импортируется с предупреждением `no_sign_in_identity` |
| Реферальные коды и ссылки Bedolaga | Каждый клиент получает новый реферальный код Omniflow. Старые ссылки `start=ref…` перестают атрибутировать |
| Удалённые пользователи | Пропускаются с `deleted_in_source` |
| Наложения льготного периода | Право доступа заканчивается в оплаченный `end_date`, а не в дату наложения льготного периода |
| История пробных периодов у клиентов без активной подписки | Пробным периодом переносится только активный. Бывший пользователь пробного периода без активной подписки может один раз взять пробный период Omniflow |

## Перед началом

- **Bedolaga v5** с числовыми ID Remnawave (`users.remnawave_id`, `subscriptions.remnawave_id`).
  Читатель проверяет нужные ему колонки и останавливается, назвав отсутствующую.
- **Развёрнутый Omniflow**: миграции применены, API отвечает на `APP_PUBLIC_URL`, платёжные провайдеры
  настроены, для каждого тарифа с активными подписками есть версия плана. План вида `trial`, если у вас
  были пробные периоды.
- **Собранный импортёр** из того же коммита, что и ваш Omniflow:

  ```bash
  go build -o migrate-bedolaga ./cmd/migrate-bedolaga
  # или образом
  docker build -f build/go.Dockerfile --build-arg TARGET=migrate-bedolaga -t omniflow-migrate-bedolaga .
  ```

- **Роль только для чтения** в базе Bedolaga для финального импорта. Читатель и так ничего не пишет;
  роль, которой разрешён только `SELECT`, делает это верным дважды:

  ```sql
  CREATE ROLE omniflow_reader LOGIN PASSWORD '<выберите пароль>';
  GRANT CONNECT ON DATABASE remnawave_bot TO omniflow_reader;
  GRANT USAGE ON SCHEMA public TO omniflow_reader;
  GRANT SELECT ON ALL TABLES IN SCHEMA public TO omniflow_reader;
  ```

- **Файл окружения** вне репозитория по образцу `deploy/migration/migration.env.example`, с правами
  `chmod 600`, загружаемый командой `set -a; . /путь/к/файлу; set +a`. Скрипты проверяют переменные и
  никогда их не печатают.

### Что читает импортёр

| Переменная | Что это |
| --- | --- |
| `APP_DATABASE_URL` | База Omniflow, в которую он пишет |
| `APP_DATA_ENCRYPTION_KEY` | Ключ, которым API шифрует контакты; им же шифруются подтверждённые адреса почты |
| `APP_REMNAWAVE_URL`, `APP_REMNAWAVE_TOKEN` | Панель; вызывается только `GET /api/users/` |
| `APP_BEDOLAGA_DATABASE_URL` | База Bedolaga; только чтение |

### Файл сопоставления

Ваши решения в YAML или JSON (`deploy/migration/mapping.example.yaml`). Неизвестные ключи отвергаются,
поэтому опечатка не может молча оставить тариф без сопоставления.

```yaml
currency: RUB
blockedUsers: suspend          # или active. Обязателен, если в Bedolaga есть заблокированные
walletReason: "Balance carried over from the previous bot"
plans:
  - tariffId: 1
    planVersionId: 0b7c…       # месячный вариант тарифа 1 по умолчанию
  - tariffId: 1
    periodDays: 360
    planVersionId: 5d1e…       # годовые подписки тарифа 1
  - trial: true
    planVersionId: 9a40…       # все пробные периоды
  - noTariff: true
    planVersionId: 77f2…       # подписки, проданные без тарифа
```

Побеждает более конкретное правило: тариф с `periodDays` — над тарифом без него, правило тарифа — над
правилом пробного периода без тарифа. `periodDays` подходит подписке, длина которой от начала до конца
округляется до этого числа дней. `plan` выводит все версии планов Omniflow, которые можно указать, и
все ещё не сопоставленные тарифы.

У `blockedUsers` намеренно нет значения по умолчанию. Bedolaga пишет `blocked` и когда оператор банит
человека, и когда рассылка обнаруживает, что клиент заблокировал бота; по данным их не различить,
поэтому, пока вы не выбрали, каждый заблокированный пользователь — конфликт `blocked_policy_missing`.

## Переменные окружения: Bedolaga → Omniflow

Процессы Omniflow читают свои переменные `APP_*`; см. [Конфигурация](/ru/getting-started/configuration).
`deploy/migration/00-convert-env.sh` делает преобразование ниже за вас: читает `.env` Bedolaga,
записывает основные настройки и переменные каждого платёжного провайдера, у которого
`<PROVIDER>_ENABLED` равно `true`, в новый файл с правами `600`, печатает только имена переменных и
отказывается перезаписывать существующий файл. Ключи выключенных провайдеров намеренно не переносятся.

```bash
sh deploy/migration/00-convert-env.sh /root/remnawave-bedolaga-telegram-bot/.env /root/omniflow-converted.env
```

Проверьте результат и перенесите его в `.env` Omniflow. Привычные настройки Bedolaga попадают сюда:

| Bedolaga | Omniflow | Примечание |
| --- | --- | --- |
| `BOT_TOKEN` | `APP_TELEGRAM_TOKEN` | Переезжает тот же бот; у клиентов остаётся их чат |
| `WEBHOOK_URL` + `WEBHOOK_PATH` | `APP_TELEGRAM_WEBHOOK_URL` | Бот Omniflow обслуживает `POST /telegram/webhook` на `APP_BOT_HTTP_ADDR` и сам регистрирует вебхук |
| `WEBHOOK_SECRET_TOKEN` | `APP_TELEGRAM_WEBHOOK_SECRET` | 32–256 символов из `A–Z a–z 0–9 _ -`; если ваш короче, сгенерируйте новый |
| `BOT_RUN_MODE` | — | Вебхук, если задан `APP_TELEGRAM_WEBHOOK_URL`, иначе long polling |
| `ADMIN_IDS` | `APP_OPERATOR_TELEGRAM_IDS` | Кому разрешён `/ops`; операторы веб-панели — отдельные учётные записи |
| `ADMIN_NOTIFICATIONS_CHAT_ID` | `APP_OPERATOR_CHAT_ID` | Группа с темами; бот сам создаёт свои темы, поэтому ID тем Bedolaga не переносятся |
| `SUPPORT_USERNAME` | `APP_SUPPORT_URL` | URL, например `https://t.me/<username>` |
| `REMNAWAVE_API_URL` | `APP_REMNAWAVE_URL` | |
| `REMNAWAVE_API_KEY` | `APP_REMNAWAVE_TOKEN` | Отправляется как bearer-токен. Режимам Bedolaga с токеном Caddy и basic-auth соответствия нет |
| `YOOKASSA_SHOP_ID` | `APP_YOOKASSA_SHOP_ID` | |
| `YOOKASSA_SECRET_KEY` | `APP_YOOKASSA_SECRET` | Ссылки возврата строятся из `APP_PUBLIC_URL`; у `YOOKASSA_RETURN_URL` соответствия нет |
| `CRYPTOBOT_API_TOKEN` | `APP_CRYPTOBOT_TOKEN` | |
| `CRYPTOBOT_TESTNET` | `APP_CRYPTOBOT_TESTNET` | В Omniflow по умолчанию `true` — для настоящих платежей задайте `false` |
| `TELEGRAM_STARS_ENABLED`, `TELEGRAM_STARS_RATE_RUB` | — | Звёзды работают через токен бота; план можно оплатить звёздами, если у его версии есть цена в `XTR`. См. [Платежи](/ru/integrations/payments) |
| `HELEKET_*`, `PLATEGA_*`, `FREEKASSA_*`, `CLOUDPAYMENTS_*`, `LAVA_*`, … (25 провайдеров) | `APP_<ИМЯ>` | То же имя с префиксом `APP_`: 140 из 156 переменных провайдеров совпадают с Bedolaga дословно. Остальные (выбор способа оплаты, клиентский сертификат Overpay, IP сервера FreeKassa) перечислены в разделе [Другие платёжные провайдеры](/ru/integrations/payment-providers) |
| `FRAGMENT_*`, `STARS_SHOP_*` (форк Omniflow) | `APP_FRAGMENT_*`, `APP_GOODS_VPN_OFFER_ENABLED` | Переносит `00-convert-env.sh`, если `STARS_SHOP_ENABLED=true`. Цена за звезду, лимиты и пресеты задаются в `/admin/shop` → Звёзды. См. [Подарки и цифровые товары](/ru/commerce/gifts-and-goods) |
| `POSTGRES_*`, `DATABASE_URL` | `APP_BEDOLAGA_DATABASE_URL` | Только для импортёра. Своя база Omniflow — в `APP_DATABASE_URL` |
| `REDIS_URL` | `APP_VALKEY_URL` | Собственный Valkey Omniflow; из Redis Bedolaga ничего не переносится |
| `CABINET_URL` | `APP_PUBLIC_URL` | Клиентская панель — веб-приложение Omniflow |
| `TRIAL_*` | — | План вида `trial` в каталоге |
| `REMNAWAVE_WEBHOOK_*`, `WEB_API_*`, `MINIAPP_*`, `SERVER_STATUS_*` | — | Соответствующей настройки нет |

## Репетиция

Запускайте на сервере, где работает Bedolaga, или там, откуда доступен контейнер базы бота.

<Steps>
  <Step title="Снимок">
    ```bash
    sh deploy/migration/01-snapshot-bedolaga.sh
    ```
    `pg_dump` выполняется внутри `BEDOLAGA_DB_CONTAINER` (по умолчанию `remnawave_bot_db`) и пишет в
    `MIGRATION_DIR` файл `bedolaga-<время>.dump` и рядом `.sha256`. Файлы никогда не перезаписываются.
  </Step>
  <Step title="Восстановление во временную базу">
    ```bash
    sh deploy/migration/02-restore-staging.sh "$MIGRATION_DIR"/bedolaga-<время>.dump
    set -a; . "$MIGRATION_DIR/staging.env"; set +a
    ```
    Проверяет контрольную сумму, запускает контейнер PostgreSQL на `127.0.0.1:${STAGING_PORT:-55432}`,
    восстанавливает снимок и пишет `APP_BEDOLAGA_DATABASE_URL` в `staging.env` с паролем,
    сгенерированным для этой копии. `APP_DATABASE_URL` направьте на временную базу Omniflow с
    применёнными миграциями и созданным каталогом.
  </Step>
  <Step title="План">
    ```bash
    sh deploy/migration/03-plan.sh
    ```
    Ничего не пишет. Прочитайте счётчики, конфликты, несопоставленные тарифы, предупреждения и то, что
    остаётся в архиве. Исправьте сопоставление и повторите.
  </Step>
  <Step title="Применение — дважды">
    ```bash
    sh deploy/migration/04-apply.sh     # попросит ввести: apply
    sh deploy/migration/04-apply.sh     # второй запуск не должен ничего записать
    ```
    `APPLY_LIMIT=100` делает поэтапный первый проход, который останавливается после ста записей.
  </Step>
  <Step title="Проверка">
    ```bash
    sh deploy/migration/05-verify.sh
    ```
    Затем войдите во временную панель Omniflow и посмотрите на нескольких знакомых вам клиентов.
  </Step>
</Steps>

<Warning>
  Во время репетиции **не запускайте воркер Omniflow против боевой панели**. Воркер каждые пятнадцать
  минут сверяет каждое активное право доступа с Remnawave; направленный на бой, репетиционный воркер
  начал бы писать в настоящих пользователей. Сам импортёр панель только читает, поэтому plan, apply и
  verify против боевого Remnawave безопасны.
</Warning>

### Конфликты и предупреждения

Конфликтная запись не импортируется и пересматривается при следующем запуске, так что вся процедура —
исправить данные и снова запустить `apply`. JSON-отчёты называют записи только по ID строки Bedolaga.

| Код | Значение |
| --- | --- |
| `duplicate_telegram_id` | У двух пользователей Bedolaga один Telegram ID; не импортируется ни один |
| `invalid_telegram_id` | Нулевой или отрицательный Telegram ID |
| `telegram_already_linked` | Этот Telegram ID уже у клиента Omniflow — кто-то раньше времени воспользовался новым ботом. При необходимости объедините учётные записи в панели потом |
| `blocked_policy_missing` | Заблокированный пользователь, а `blockedUsers` в сопоставлении нет |
| `negative_balance` | Клиент импортируется, баланс — нет |
| `subscription_without_remnawave_user` | Активная подписка без ID пользователя панели |
| `remnawave_user_not_found` | В панели нет пользователя с таким ID |
| `duplicate_remnawave_user` | Две подписки Bedolaga указывают на одного пользователя панели |
| `remnawave_user_already_linked` | Этот пользователь панели уже принадлежит клиенту Omniflow |
| `unmapped_tariff`, `unknown_plan_version` | Исправьте файл сопоставления |
| `user_not_imported`, `referrer_not_imported`, `referee_not_imported` | Следствие конфликта у пользователя |
| `entitlement_owned_by_omniflow` | Обновление отклонено: Omniflow уже действовал с этим правом доступа |

Предупреждения ничего не блокируют: `expiry_differs_from_panel`, `telegram_differs_from_panel`,
`panel_status_differs`, `plan_kind_mismatch`, `plan_version_retired`, `language_defaulted`,
`no_sign_in_identity`, `several_subscriptions` (включите `APP_MULTI_SUBSCRIPTION_ENABLED` и задайте
`APP_MAX_SUBSCRIPTIONS_PER_CUSTOMER`, если у клиентов их несколько), `balance_decreased` и
`changed_since_apply`.

## Сколько длится переключение

Клиенты замечают окно между остановкой Bedolaga и моментом, когда начинает отвечать бот Omniflow. В
нём: `pg_dump` базы бота, один `apply`, один `verify` и ручные шаги. Каждая запись — своя короткая
транзакция, а список пользователей панели читается страницами по 500, поэтому `apply` обычно занимает от
секунд до нескольких минут; измерьте его на своих данных во время репетиции — начало и конец каждого
запуска лежат в `bedolaga_import_runs`, а `migrate-bedolaga runs` их выводит. Кабинеты провайдеров и
проверка руками занимают больше, чем импорт; для отрепетированной установки комфортное окно — тридцать
минут.

## Переключение

```bash
sh deploy/migration/06-cutover.sh
```

Скрипт идёт по списку ниже, выполняя то, что может, и останавливаясь там, где нужен человек. Каждый
шаг, который что-то меняет, печатает команду и ждёт введённой фразы.

1. **Предусловия.** Репетиция с этим сопоставлением прошла, Omniflow развёрнут, бот и воркер Omniflow
   не запущены, клиенты предупреждены.
2. **Обслуживание.** `docker stop` для бота Bedolaga (и `BEDOLAGA_EXTRA_CONTAINERS`, например
   кабинета). Его база продолжает работать. Время записывается в `MIGRATION_DIR/cutover-at`.
3. **Финальный снимок** через `01-snapshot-bedolaga.sh` — архив всего, что не переносится.
4. **Финальный импорт.** `04-apply.sh` против боя с `APP_BEDOLAGA_DATABASE_URL` на боевой базе бота,
   затем `05-verify.sh`. Расхождение останавливает переключение.
5. **Telegram.** Показывает текущий вебхук; в режиме polling удаляет его; запускает бота Omniflow с тем
   же токеном, и тот сам регистрирует вебхук; снова показывает регистрацию. Отправьте `/start` с
   аккаунта, который был в Bedolaga.
6. **Платёжные провайдеры.** Печатает `https://<APP_PUBLIC_URL>/v1/payments/webhooks/<slug>` для каждого
   слага из `PAYMENT_PROVIDERS` — их нужно указать в кабинете провайдера. Звёздам Telegram URL не нужен.
7. **Ссылки подписки.** Менять нечего: ими владеет Remnawave. Если задан `SAMPLE_SUBSCRIPTION_URL`,
   скрипт проверяет одну ссылку до и после.
8. **Воркер.** Последним запускается воркер Omniflow; с этого момента Omniflow сверяет импортированные
   права доступа. Через пятнадцать минут в **/admin → System → Drift** не должно быть ничего
   неожиданного.

Продление, сделанное в Bedolaga между предыдущим и финальным запуском, финальный запуск подхватит:
импортированное право доступа, с которым Omniflow ещё не действовал, переедет на новую дату окончания,
а изменившийся баланс получит свою корректировку.

## Проверка

`05-verify.sh` сверяет источник с собственными таблицами Omniflow, а не с учётом импортёра:

| Проверка | Проходит, когда |
| --- | --- |
| nothing left to apply | В свежем плане не осталось записей |
| users | У каждого импортируемого пользователя Bedolaga есть клиент с его Telegram ID |
| balance sum | Перенесённые движения каждого клиента в сумме равны его балансу в Bedolaga |
| active subscriptions | У каждой активной подписки есть право доступа на том же пользователе панели, заканчивающееся в дату окончания из Bedolaga |
| referral pairs | Каждая импортируемая пара указывает на правильного пригласившего |

Код выхода `4` — расхождение; отчёт называет первые ID Bedolaga, на которых проверка не прошла.

## Откат

```bash
sh deploy/migration/07-rollback.sh
```

Поскольку импортёр никогда не писал в Bedolaga, её база ровно такая, какой была в момент остановки.
Откат останавливает воркер и бота Omniflow, считает, что произошло в Omniflow после `cutover-at`
(оплаченные заказы, новые клиенты, движения по кошелькам — задайте `OMNIFLOW_DB_CONTAINER`, иначе
скрипт напечатает запрос), снова запускает Bedolaga (она сама регистрирует свой вебхук) и просит
вернуть URL у платёжных провайдеров. Платежи, которые клиенты сделали в Omniflow после переключения,
назад не переходят: зачислите их в Bedolaga вручную по этому списку.

Импортированные данные Omniflow остаются. Повторный запуск `04-apply.sh` позже обновит изменившееся, а
не импортирует второй раз.

## Запуск импортёра вручную

```text
migrate-bedolaga plan   -mapping FILE [-json FILE]
migrate-bedolaga apply  -mapping FILE -confirm [-json FILE] [-limit N] [-actor NAME]
migrate-bedolaga verify -mapping FILE [-json FILE]
migrate-bedolaga runs
```

Коды выхода: `0` готово, `1` ошибка, `2` неверный вызов, `3` apply оставил ошибки или остановился на
`-limit`, `4` verify нашёл расхождение. `apply` без `-confirm` не запускается. `-actor` записывается в
событие аудита каждой корректировки кошелька и в запуск.
