**Статус:** принято.

## Контекст

В Bedolaga был WebSocket-канал для live-обновлений и живой чат поддержки. Панели
Omniflow опрашивали сервер: оператор видел новое сообщение в тикете при следующем
обновлении списка, а клиент видел ответ оператора с задержкой до пятнадцати
секунд. Обеим панелям нужно быстро узнавать, что показанное изменилось, — ответ в
переписке, оплата заказа, выдача подписки, — а переписка поддержки должна
ощущаться живой с обеих сторон.

Каждое сообщение в переписке уже *отправляется* обычным аутентифицированным
запросом: `POST`, который проверяет сессию, CSRF, права, лимиты, блокировку
клиента в поддержке и записывает сообщение, след аудита и уведомления в одной
транзакции. Не хватает только обратного направления — сказать открытому экрану,
что есть что-то новое.

## Решение

**Live-обновления — это потоки server-sent events, по одному на панель:**
`GET /v1/panel/live` для операторов и `GET /v1/account/live` для клиентов.
Каждый поток с коротким интервалом — три секунды — перечитывает несколько
номеров версий и отправляет событие с названиями областей, версия которых
сдвинулась (`support`, `orders`, `subscriptions`, `wallet` у клиента; `support`,
`finance`, `errors`, `customers` у оператора, каждая — только при праве на её
чтение). Затем браузер перечитывает показанное через те же маршруты, что и
раньше.

**Поток не несёт записей.** В нём нет ни текста сообщения, ни суммы, ни
идентификатора; версии клиента считаются только по строкам этого клиента.
Поэтому авторизация остаётся там, где она уже есть, — на маршрутах, которые
перечитывает экран, — и поток не может стать вторым, более слабым путём к
данным.

**Отправка остаётся обычным запросом.** Живая переписка поддержки — это
существующий маршрут отправки плюс поток: сообщение любой стороны сдвигает
версию `support` у другой стороны, и открытая переписка перечитывается за
секунды.

**Потоки короткоживущие.** Таймаут запроса в роутере закрывает поток через
минуту (клиентский поток к тому же ограничивает себя пятью минутами), и
`EventSource` переподключается через middleware сессии, поэтому отозванная
сессия быстро перестаёт получать обновления. Клиентский поток отправляет версии
как идентификатор события; переподключающийся браузер возвращает их в
`Last-Event-ID`, поэтому изменение, сделанное во время переподключения, всё равно
будет объявлено.

## Почему не WebSocket

- **Трафик односторонний.** Всё, что говорит клиент, уже имеет маршрут с
  нужными проверками. Сокету пришлось бы либо дублировать эти проверки для
  сообщений, пришедших по нему, либо ничего не передавать вверх и быть
  SSE-потоком с более сложным рукопожатием.
- **Он ложится на существующий путь запроса.** SSE — это обычный `GET` с
  cookie: те же middleware сессии, CSRF, RBAC и request ID, та же настройка
  обратного прокси и то же разделение трёх префиксов `/v1/panel`, `/v1/admin` и
  `/v1/account`. Апгрейд до WebSocket требует собственной аутентификации на
  рукопожатии, собственных проверок origin и настроек прокси для апгрейдов и
  таймаутов простоя.
- **Переподключение встроено.** `EventSource` переподключается сам и повторно
  отправляет последний идентификатор события; с WebSocket клиенту пришлось бы
  самому реализовать отсрочку, повторную подписку и восстановление пропусков.
- **Никаких новых движущихся частей.** Версии читаются из PostgreSQL —
  единственного долговременного хранилища
  ([решение 0002](/ru/architecture/decision-0002-postgresql-only-durability)).
  Рассылка через WebSocket по нескольким репликам api потребовала бы pub/sub,
  то есть брокера сообщений, которого проект решил не добавлять без отдельного
  решения.

## Последствия

- Обновление приходит в пределах интервала опроса, а не мгновенно: примерно до
  трёх секунд. Для переписки поддержки и статуса заказа этого достаточно; ничто в
  панелях не требует доставки быстрее секунды.
- Каждая открытая панель стоит одного небольшого индексного запроса за
  интервал. Клиентский поток читает только строки вошедшего клиента через
  добавленные для него индексы (`orders`, `subscriptions` и `entitlements` по
  клиенту и последнему изменению).
- Нет индикатора набора текста и присутствия: им нужны сообщения от клиента,
  которых эта схема не несёт.
- Браузеры ограничивают число одновременных HTTP/1.1-соединений на origin;
  клиент с множеством вкладок по HTTP/1.1 может их исчерпать. Отдача панелей по
  HTTP/2, как в эталонном развёртывании, снимает ограничение.

## Когда пересмотреть

Когда функции понадобятся сообщения от клиента с малой задержкой по тому же
каналу — присутствие, набор текста, совместное редактирование — или когда
стоимость опроса открытых панелей станет заметной на фоне остальной нагрузки на
базу; тогда поток на `LISTEN`/`NOTIFY` или WebSocket с брокером получат
собственное решение.
