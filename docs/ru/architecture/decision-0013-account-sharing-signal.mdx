**Статус:** принято.

## Контекст

Операторы Bedolaga ищут подписки, которыми пользуются несколько человек.
Доказательства — устройства, их платформы, подключения, IP-адреса — хранятся в
Remnawave, который по [решению 0004](/ru/architecture/decision-0004-remnawave-boundary)
отвечает за устройства, трафик и доступ. Remnawave уже ограничивает число
устройств пользователя. Сбор журналов подключений или истории IP в Omniflow
дублировал бы состояние Remnawave и хранил бы персональные данные, которые
Omniflow больше ни для чего не нужны.

## Решение

**Omniflow вычисляет сигнал только для чтения из списка устройств Remnawave,
когда оператор открывает устройства подписки**, и ничего не сохраняет. Сигнал —
«возможно» или «вероятно» с причинами: пять и больше устройств, активных за
сутки, четыре и больше платформ, три и больше моделей одной платформы.

**Omniflow никогда не действует по сигналу.** Он не удаляет устройства, не
снижает лимиты, не блокирует и не пишет клиенту. Ограничение остаётся за
лимитом устройств Remnawave, который оператор задаёт в тарифе; удаление
устройства остаётся прежним ручным действием с аудитом.

**История IP и подключений не собирается.** В хранилище Omniflow ничего не
добавляется, телеметрия не меняется.

## Последствия

- Сигнал настолько хорош, насколько хороши отчёты Remnawave об устройствах;
  клиент, не передающий hardware ID, для него невидим.
- Списка «всех расшаренных подписок» нет: для него понадобился бы вызов
  Remnawave на каждую подписку по расписанию, от чего эта запись отказывается.

## Когда пересмотреть

Remnawave начнёт отдавать через API агрегированный сигнал шаринга или число
одновременных подключений — Omniflow сможет читать его так же, ничего не храня.
