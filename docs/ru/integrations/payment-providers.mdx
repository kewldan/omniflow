Эти адаптеры перенесены из Bedolaga, чтобы установка при переезде сохранила эквайера, с которым у неё
уже есть договор. Каждый реализует тот же контракт, что и четыре встроенных из раздела
[Платёжные провайдеры](/ru/integrations/payments): способ оплаты показывается покупателю, только если он
настроен **и** принимает валюту заказа; зачисление происходит только по проверенному уведомлению или
авторизованному запросу статуса; деньги всегда хранятся целыми минимальными единицами.

## Как включить провайдера

Каждый провайдер ниже читает свои переменные `APP_<SLUG>_*` при запуске процесса — и в API, и в
воркере. Если не задана ни одна обязательная переменная провайдера, он не регистрируется; если заданы
только некоторые — это ошибка запуска, поэтому наполовину настроенный эквайер обнаруживается до первой
оплаты, а не во время неё. После изменения перезапустите процессы.

Провайдеры, которые передают адрес колбэка в каждом платеже, строят его из `APP_PUBLIC_URL`:

```text
https://<APP_PUBLIC_URL>/v1/payments/webhooks/<slug>
```

Если провайдер принимает адрес колбэка в своём кабинете, укажите там этот же URL.

## Кнопки и способы оплаты

Клиент видит список **кнопок**. По умолчанию каждый настроенный провайдер — одна кнопка.
Провайдер, у эквайера которого несколько способов оплаты, может показать каждый отдельной кнопкой:
перечислите их в переменной `APP_<SLUG>_PAYMENT_METHODS` — через запятую `ключ` для известного
способа или `ключ:код` для любого кода провайдера, в нужном порядке:

| Провайдер | Переменная | Известные ключи (код) |
| --- | --- | --- |
| FreeKassa | `APP_FREEKASSA_PAYMENT_METHODS` | `sbp` (44), `card` (36); переменная включает API заказов, которому нужен `APP_FREEKASSA_SERVER_IP` |
| KassaAI | `APP_KASSA_AI_PAYMENT_METHODS` | `sbp` (44), `card` (36), `sberpay` (43) |
| CisPay | `APP_CISPAY_PAYMENT_METHODS` | `card` (CARD), `sbp` (SBP), `crypto` (CRYPTO) |
| Platega | `APP_PLATEGA_PAYMENT_METHODS` | `sbp` (2), `card` (11), `intl` (12), `crypto` (13) |
| Antilopay | `APP_ANTILOPAY_PAYMENT_METHODS` | `sbp` (SBP), `card` (CARD_RU), `sberpay` (SBER_PAY) — передаются как `prefer_methods` |

Ключ способа — до десяти строчных латинских букв, цифр или подчёркиваний. Нажатая кнопка
сохраняется в платёжном намерении (`payment_intents.method`), поэтому продолжение оплаты нажимает
ту же кнопку.

Дальше списком управляет раздел **Settings → Commerce** панели:

- Переключатель **Enabled** и **Display order** в строке провайдера решают, предлагается ли
  провайдер и где. Провайдер без сохранённой строки предлагается, как и раньше; сохранённый
  выключенным исключается из всех списков клиента, а платёж, начатый для него в обход, отклоняется.
- **Кнопки оплаты** (`GET`/`PUT /v1/panel/settings/payment-methods`, `settings.read` /
  `settings.write`) настраивают каждую кнопку: название и описание на русском и английском, порядок
  внутри провайдера, минимальную и максимальную сумму, до восьми быстрых сумм пополнения (пока
  кнопка выбрана, они заменяют общие пресеты кошелька), сразу ли открывать страницу провайдера и
  кому её показывать — клиентам с определённым способом входа (Telegram, e-mail, VK ID, OIDC),
  только до или только после первого оплаченного пополнения, или только некоторым уровням
  лояльности.

Правила одинаково применяются в боте и веб-кабинете и ещё раз на сервере при старте платежа, так
что скрытую кнопку нельзя нажать через устаревший экран. Сохранённые изменения доходят до всех
процессов в течение тридцати секунд.

## Назначение платежа

Назначение платежа, которое провайдер показывает на своей странице, в чеке или в выписке банка, —
это название тарифа для заказа, `Wallet top-up` для пополнения и `Subscription renewal` для
автопродления. Оператор может сформулировать его сам:

| Переменная | Для чего |
| --- | --- |
| `APP_PAYMENT_SERVICE_NAME` | `{service}` в шаблонах ниже |
| `APP_PAYMENT_ORDER_TEMPLATE` | Покупка и смена тарифа, докупки, подарки и заказы магазина |
| `APP_PAYMENT_TOPUP_TEMPLATE` | Пополнение кошелька |
| `APP_PAYMENT_RENEWAL_TEMPLATE` | Автопродление |

В шаблоне можно использовать `{service}`, `{description}` (назначение по умолчанию, см. выше) и
`{order}` (первые восемь символов ID заказа), например `{service}: {description} #{order}`.
Результат обрезается до 128 символов; без шаблона остаётся назначение по умолчанию.

## Общее для всех адаптеров

- **Данные плательщика.** Omniflow передаёт собственный ID покупателя и, если покупатель вошёл через
  Telegram, его Telegram ID. E-mail покупателя передаётся только адаптеру, которому он нужен, —
  Antilopay, который без контакта отклоняет платёж, и YooKassa при включённых чеках, — и только
  если у покупателя есть **подтверждённый** e-mail. Он открывается из зашифрованного хранилища
  контактов ключом `APP_DATA_ENCRYPTION_KEY`; без ключа или без подтверждённого адреса ничего не
  передаётся, и Antilopay отклоняет платёж ещё до обращения к эквайеру. Телефон не передаётся никогда.
- **Неподписанные уведомления.** Если провайдер не подписывает вебхук, уведомление считается подсказкой:
  перед зачислением платёж перечитывается через авторизованный API провайдера.
- **Повторы.** На уведомление, которое не прошло проверку или ссылается на платёж, не открытый этой
  установкой, отвечаем `400`. На уведомление, не обработанное по временной причине, — `503`, чтобы
  провайдеры, повторяющие доставку только при ошибках сервера, прислали его снова.
- **Возвраты.** Безопасный вызов возврата из этих эквайеров есть только у CloudPayments. Остальным
  делайте возврат в кабинете провайдера и фиксируйте его в Omniflow.

## Heleket

Heleket — криптовалютный платёжный шлюз. Omniflow выставляет в Heleket счёт в фиатной валюте заказа;
покупатель оплачивает его криптовалютой на странице Heleket, а Heleket сообщает результат на вебхук
Omniflow.

**Валюты:** заказы в `RUB` или `USD`. Монету, которой платит покупатель, задаёт
`APP_HELEKET_DEFAULT_CURRENCY`.

### Настройка

| Переменная | Обязательна | По умолчанию | Значение |
| --- | --- | --- | --- |
| `APP_HELEKET_MERCHANT_ID` | Да | — | UUID мерчанта из кабинета Heleket, передаётся в заголовке `merchant`. |
| `APP_HELEKET_API_KEY` | Да | — | Платёжный API-ключ. Им подписывается каждый запрос и проверяется каждый вебхук. Держите в секрете. |
| `APP_HELEKET_BASE_URL` | Нет | `https://api.heleket.com/v1` | Базовый адрес API. |
| `APP_HELEKET_DEFAULT_CURRENCY` | Нет | `USDT` | Монета, в которую конвертируется счёт (`to_currency`). |
| `APP_HELEKET_DEFAULT_NETWORK` | Нет | — | Сеть блокчейна для этой монеты (`network`), например `tron`. Если не задана, сеть выбирает покупатель. |
| `APP_HELEKET_INVOICE_LIFETIME` | Нет | `3600` | Время жизни счёта в секундах, в пределах от 300 до 43200. |
| `APP_HELEKET_MARKUP_PERCENT` | Нет | `0` | Наценка для покупателя в процентах. Округляется до целого и передаётся как отрицательный `discount_percent`. |

Также обязателен `APP_PUBLIC_URL`: каждый счёт несёт адрес вебхука в `url_callback`, поэтому без него
Omniflow не запускает адаптер. Если задан только один из двух ключей, запуск завершается ошибкой; если
не задан ни один, Heleket выключен.

### Вебхук

Адрес обратного вызова уже передаётся в каждом счёте, поэтому в кабинете ничего вводить не нужно. Он
такой:

```text
https://<APP_PUBLIC_URL>/v1/payments/webhooks/heleket
```

Уведомление принимается, только если его поле `sign` совпадает с `md5(base64(тело) + API-ключ)`,
посчитанным по телу без `sign`. Уведомление без подписи, с неверной подписью или с изменённой суммой
отклоняется. Заказ оплачивают только статусы `paid` и `paid_over`; любой другой статус записывается и
ничего не меняет.

### Возможности

| Возможность | Поддерживается |
| --- | --- |
| Вебхуки | Да, с подписью |
| Опрос статуса | Да, через `payment/info` |
| Проверка подключения только на чтение | Да, `payment/list` |
| Возвраты | Нет |
| Рекуррентные списания | Нет |
| Отмена открытого счёта | Нет |

### Проверка

1. Задайте переменные выше и `APP_PUBLIC_URL` и перезапустите API. Ошибка запуска называет
   отсутствующую или заданную наполовину переменную.
2. При желании вызовите `POST /v1/panel/settings/providers/heleket/test`. Он выполняет проверку только
   на чтение; где сейчас виден её результат, описано в разделе «Как убедиться, что провайдер
   действительно работает» на странице [Платежи](/ru/integrations/payments).
3. Купите самую дешёвую версию тарифа сами через Heleket. Следите за уведомлением в `/admin` → System →
   Webhooks и за историей платежа в `/admin/finance/{orderId}`. Если вебхук не пришёл, сверка прочитает
   статус счёта через `payment/info`.

## Mulen Pay

Mulen Pay — российский платёжный шлюз для оплаты картой и через СБП в рублях. Omniflow создаёт платёж
со строкой фискального чека и отправляет покупателя на страницу оплаты Mulen Pay.

**Валюты:** только `RUB`.

### Настройка

| Переменная | Обязательна | По умолчанию | Значение |
| --- | --- | --- | --- |
| `APP_MULENPAY_API_KEY` | Да | — | API-ключ, передаётся как `Authorization: Bearer`. Держите в секрете. |
| `APP_MULENPAY_SECRET_KEY` | Да | — | Секретный ключ: входит в SHA-1 `sign` каждого платежа и проверяет контрольную сумму, если она есть в колбэке. Держите в секрете. |
| `APP_MULENPAY_SHOP_ID` | Да | — | Числовой ID магазина из кабинета Mulen Pay. |
| `APP_MULENPAY_BASE_URL` | Нет | `https://mulenpay.ru/api` | Базовый адрес API. |
| `APP_MULENPAY_LANGUAGE` | Нет | `ru` | Язык страницы оплаты. |
| `APP_MULENPAY_VAT_CODE` | Нет | `0` | `vat_code` строки чека. |
| `APP_MULENPAY_PAYMENT_SUBJECT` | Нет | `4` | `payment_subject` строки чека. |
| `APP_MULENPAY_PAYMENT_MODE` | Нет | `4` | `payment_mode` строки чека. |
| `APP_MULENPAY_WEBSITE_URL` | Нет | `APP_PUBLIC_URL` | Передаётся как `website_url`. |

Если задана только часть из трёх учётных данных, запуск завершается ошибкой; если не задано ничего,
Mulen Pay выключен. ID магазина, не являющийся положительным целым числом, — ошибка запуска.

Mulen Pay требует в каждом платеже контакт плательщика (`client`). Omniflow передаёт e-mail или ID
покупателя, если они есть в запросе на оплату, а иначе — ID заказа.

### Вебхук

Укажите этот адрес как URL обратного вызова в кабинете Mulen Pay:

```text
https://<APP_PUBLIC_URL>/v1/payments/webhooks/mulenpay
```

Колбэки Mulen Pay не аутентифицированы, поэтому колбэк сам по себе никогда не оплачивает заказ. Если в
нём есть контрольная сумма `sign`, она должна быть верной, иначе колбэк отклоняется. Затем Omniflow
читает платёж через аутентифицированный `GET /v2/payments/{id}` и действует только по этому ответу:
код статуса `3` (успех) оплачивает заказ, любой другой статус ничего не меняет. Колбэк о платеже,
которого эта установка не создавала, отклоняется без обращения к Mulen Pay.

### Возможности

| Возможность | Поддерживается |
| --- | --- |
| Вебхуки | Да, с подтверждением опросом |
| Опрос статуса | Да, `GET /v2/payments/{id}` |
| Проверка подключения только на чтение | Да, `GET /v2/payments?limit=1` |
| Возвраты | Нет |
| Рекуррентные списания | Нет |
| Отмена открытого платежа | Нет |

### Проверка

1. Задайте переменные выше и перезапустите API. Ошибка запуска называет отсутствующую или неверную
   переменную.
2. При желании вызовите `POST /v1/panel/settings/providers/mulenpay/test`. Он выполняет проверку только
   на чтение; где сейчас виден её результат, описано в разделе «Как убедиться, что провайдер
   действительно работает» на странице [Платежи](/ru/integrations/payments).
3. Купите самую дешёвую версию тарифа сами через Mulen Pay. Следите за колбэком в `/admin` → System →
   Webhooks и за историей платежа в `/admin/finance/{orderId}`.

## PayPalych (Pal24)

PayPalych (`pal24.pro`) — российский платёжный шлюз. Omniflow выставляет в PayPalych счёт на оплату
через СБП или картой и отправляет покупателя на страницу оплаты счёта.

**Валюты:** только `RUB`.

### Настройка

| Переменная | Обязательна | По умолчанию | Значение |
| --- | --- | --- | --- |
| `APP_PAL24_API_TOKEN` | Да | — | API-токен, передаётся как `Authorization: Bearer`. Держите в секрете. |
| `APP_PAL24_SHOP_ID` | Да | — | ID магазина из кабинета PayPalych. |
| `APP_PAL24_SIGNATURE_TOKEN` | Нет | `APP_PAL24_API_TOKEN` | Токен, которым подписываются постбэки. Задайте его, если токен подписи магазина отличается от API-токена. Держите в секрете. |
| `APP_PAL24_PAYMENT_METHOD` | Нет | `sbp` | `sbp` или `card`; передаётся как `payment_method` `SBP` или `BANK_CARD`. |
| `APP_PAL24_BASE_URL` | Нет | `https://pal24.pro/api/v1/` | Базовый адрес API. |
| `APP_PAL24_REQUEST_TIMEOUT` | Нет | `30` | Тайм-аут запроса в секундах. |

Если задан только один из API-токена и ID магазина, запуск завершается ошибкой; если не задан ни один
из трёх токенов, PayPalych выключен. Любое другое значение способа оплаты — ошибка запуска.

### Вебхук

Укажите этот адрес как Result URL (постбэк) магазина в кабинете PayPalych:

```text
https://<APP_PUBLIC_URL>/v1/payments/webhooks/pal24
```

Постбэк — в виде формы или JSON — принимается, только если `SignatureValue` равно
`upper(md5(OutSum:InvId:токен))`. Изменённая сумма или неверная подпись отклоняются. `SUCCESS`,
`OVERPAID` и `PAID` оплачивают заказ; любой другой статус ничего не меняет.

<Warning>
  Подпись PayPalych покрывает только `OutSum` и `InvId`, но не `Status`. Держите токен подписи в
  секрете, а вебхук — на HTTPS.
</Warning>

### Возможности

| Возможность | Поддерживается |
| --- | --- |
| Вебхуки | Да, с подписью |
| Опрос статуса | Да, `bill/status` |
| Проверка подключения только на чтение | Да, `merchant/balance` |
| Отмена открытого счёта | Да, `bill/toggle_activity` деактивирует счёт |
| Возвраты | Нет |
| Рекуррентные списания | Нет |

### Проверка

1. Задайте переменные выше и перезапустите API. Ошибка запуска называет отсутствующую или неверную
   переменную.
2. При желании вызовите `POST /v1/panel/settings/providers/pal24/test`. Он выполняет проверку только на
   чтение; где сейчас виден её результат, описано в разделе «Как убедиться, что провайдер действительно
   работает» на странице [Платежи](/ru/integrations/payments).
3. Купите самую дешёвую версию тарифа сами через PayPalych. Следите за постбэком в `/admin` → System →
   Webhooks и за историей платежа в `/admin/finance/{orderId}`. Если постбэк не пришёл, сверка
   прочитает статус счёта через `bill/status`.

**Валюты:** одна валюта из `APP_PLATEGA_CURRENCY`, по умолчанию `RUB`.

### Настройка

| --- | --- | --- | --- |

## Tribute

Tribute — сервис донатов в Telegram. API для открытия оплаты у него нет: покупатель платит по вашей
постоянной донат-ссылке Tribute и сам выбирает там сумму, а Tribute уведомляет Omniflow о каждом
донате.

**Валюты:** только `RUB`. Суммы донатов приходят в копейках.

<Warning>
  Донат Tribute называет Telegram-аккаунт плательщика и донат-ссылку, но не заказ Omniflow. Omniflow
  проводит его по самому свежему открытому платежу Tribute этого плательщика **ровно** на
  задоначенную сумму, если заказ ещё ждёт оплаты. Плательщик должен быть авторизован под тем же
  Telegram-аккаунтом. Донат, которому ничего не соответствует (другая сумма, другой аккаунт, заказ
  уже истёк), проверяется и записывается в `/admin` → System → Webhooks с ошибкой
  `payment_not_found` и не зачисляется.
</Warning>

### Настройка

| Переменная | Обязательна | По умолчанию | Значение |
| --- | --- | --- | --- |
| `APP_TRIBUTE_API_KEY` | Да | — | API-ключ Tribute. Им проверяется `trbt-signature` каждого вебхука. Держите в секрете. |
| `APP_TRIBUTE_DONATE_LINK` | Да | — | Ваша донат-ссылка Tribute. Покупатель переходит по ней без изменений. |

Если задана только одна из двух переменных, запуск завершается ошибкой; если не задана ни одна,

Укажите этот адрес как URL вебхука в настройках Tribute:

```text

```

Вебхук принимается, только если `trbt-signature` равен `hex(HMAC-SHA256(API-ключ, тело))`. Изменённое
тело или неверная подпись отклоняются. `new_donation` и `recurrent_donation` — это платежи;
`cancelled_subscription` и другие события ничего не меняют. Повторные доставки одного доната имеют
один ID события, собранный из ID донат-ссылки, Telegram-пользователя, суммы и `created_at` события.

## FreeKassa

FreeKassa — российский платёжный агрегатор. Адаптер `freekassa` открывает оплату одним из двух
способов и зачисляет платёж по подписанному уведомлению FreeKassa:

- **Платёжная форма (по умолчанию).** Omniflow подписывает ссылку на `https://pay.fk.money/`, и
  клиент выбирает способ оплаты там. Для открытия оплаты API не вызывается.
- **Заказ через API.** Если способ оплаты закреплён в `APP_FREEKASSA_PAYMENT_SYSTEM_ID` или задано
  `APP_FREEKASSA_USE_API=true`, Omniflow создаёт заказ через `https://api.fk.life/v1/orders/create` и
  отправляет клиента по ссылке `location`, которую возвращает FreeKassa. Так оплата сразу ведёт в СБП
  (QR-код) или на оплату российской картой, минуя форму выбора.

**Валюта.** Одна валюта на магазин — `RUB`, если `APP_FREEKASSA_CURRENCY` не задаёт другую. Тарифу с
ценой в другой валюте FreeKassa не предлагается.

<Steps>
  <Step title="Получите реквизиты магазина">
    В личном кабинете FreeKassa понадобятся идентификатор магазина, API-ключ, секретное слово 1
    (подписывает ссылку на форму оплаты) и секретное слово 2 (подписывает уведомления).
  </Step>
  <Step title="Настройте Omniflow">
    ```env
    APP_FREEKASSA_SHOP_ID=12345
    APP_FREEKASSA_API_KEY=…
    APP_FREEKASSA_SECRET_WORD_1=…
    APP_FREEKASSA_SECRET_WORD_2=…
    # Необязательно: сразу один способ оплаты через API
    # APP_FREEKASSA_PAYMENT_SYSTEM_ID=sbp
    # APP_FREEKASSA_SERVER_IP=203.0.113.10
    ```
    Адаптер регистрируется, если задано хотя бы одно из четырёх значений, а если заданы не все,
    запуск завершается ошибкой с перечнем недостающих.
  </Step>
  <Step title="Укажите URL уведомлений">
    В личном кабинете укажите URL оповещения (result URL)
    `https://<your-public-host>/v1/payments/webhooks/freekassa` — это `APP_PUBLIC_URL`, за которым
    следует `/v1/payments/webhooks/freekassa`. Там же настраиваются страницы успеха и ошибки: заказы
    FreeKassa не получают от Omniflow возвратный URL.
  </Step>
  <Step title="Оплатите тестовый заказ">
    Купите самый дешёвый тариф сами и проверьте его по разделу **Как убедиться, что провайдер
    действительно работает** на странице платёжных провайдеров.
  </Step>
</Steps>

| Переменная | Обязательна | По умолчанию | Назначение |
| --- | --- | --- | --- |
| `APP_FREEKASSA_SHOP_ID` | Да | — | Числовой идентификатор магазина. Подписывает и идентифицирует каждый запрос и уведомление |
| `APP_FREEKASSA_API_KEY` | Да | — | API-ключ. Ключ HMAC-SHA256 для заказов через API, опроса статуса и проверки баланса |
| `APP_FREEKASSA_SECRET_WORD_1` | Да | — | Подписывает ссылку на форму оплаты |
| `APP_FREEKASSA_SECRET_WORD_2` | Да | — | Проверяет уведомления |
| `APP_FREEKASSA_CURRENCY` | Нет | `RUB` | Единственная валюта, в которой работает магазин |
| `APP_FREEKASSA_PAYMENT_SYSTEM_ID` | Нет | пусто | Закрепляет способ оплаты и переключает на заказы через API: `sbp` (44, СБП по QR-коду), `card` (36, российские карты) или любой числовой идентификатор платёжной системы FreeKassa, например `42` (обычный СБП). Пустое значение — форма выбора способа |
| `APP_FREEKASSA_USE_API` | Нет | `false` | Создаёт заказы через API даже без закреплённого способа; тогда передаётся платёжная система `1` |
| `APP_FREEKASSA_SERVER_IP` | При заказах через API | — | Публичный IPv4-адрес сервера Omniflow, передаётся в поле заказа `ip`. Обязателен, когда используются заказы через API |

**Создание.** Ссылка на форму содержит `m`, `oa`, `currency`, `o` (идентификатор заказа Omniflow),
`lang=ru` и `s = md5(shop:amount:секретное слово 1:currency:order)`. Заказ через API — это JSON
`POST` с полями `shopId`, `nonce`, `paymentId` (идентификатор заказа), `i` (платёжная система),
`email`, `ip`, `amount` и `currency`, подписанный HMAC-SHA256 от значений, отсортированных по ключу и
соединённых через `|`. Поле `email` для API обязательно; Omniflow не передаёт FreeKassa адрес клиента
и отправляет вместо него `user_<идентификатор заказа>@telegram.org`. Суммы записываются без
незначащих нулей (`100`, `100.5`).

**Проверка вебхука.** FreeKassa отправляет форму с полями `MERCHANT_ID`, `AMOUNT`,
`MERCHANT_ORDER_ID`, `intid` и `SIGN = md5(MERCHANT_ID:AMOUNT:секретное слово 2:MERCHANT_ORDER_ID)`.
Omniflow требует совпадения идентификатора магазина, сравнивает подпись за постоянное время и
зачисляет подписанную сумму `AMOUNT` в настроенной валюте. На проверенное уведомление отвечается
голое тело `YES` — именно оно прекращает повторы со стороны FreeKassa; на отклонённое — ответ об
ошибке, и доставка повторяется. Идентификатор события — `paid:<intid>`, поэтому повторная доставка
распознаётся как дубликат.

<Note>
  FreeKassa отправляет уведомления с фиксированного набора адресов. Omniflow не
  проверяет адрес отправителя — маршрут видит только заголовки, а заголовок forwarded-for можно
  подделать — и полагается на подпись. Чтобы дополнительно ограничить доступ по адресу, разрешите на
  обратном прокси к этому пути только `168.119.157.136`, `168.119.60.227`, `178.154.197.79` и
  `51.250.54.238`.
</Note>

**Опрос статуса.** Поддерживается. `POST /orders` с идентификатором заказа; заказ со статусом `1`
оплачен и зачисляется на сумму, которую сообщает API. Любой другой статус или заказ, которого
FreeKassa ещё не знает, остаётся в ожидании.

**Возвраты и рекуррентные платежи.** Не поддерживаются. Возврат отклоняется на уровне адаптера —
используйте зачисление на кошелёк.

succeeded, `process` → processing, `decline` и `fail` → failed, а `new` или неизвестный статус →
pending. Идентификатор события — `<тип>:<id payin>:<статус>`. На проверенное уведомление отвечается

**Возвраты и рекуррентные платежи.** Не поддерживаются. Проверки подключения нет: у SeverPay нет
вызова только на чтение, которому не нужен существующий payin.

использоваться уже полученный ключ. Если ключа нет вовсе, проверить ничего нельзя, и уведомление
отклоняется, чтобы WATA повторила доставку. `transactionStatus` `Paid` зачисляет подписанную сумму

`<transactionStatus>:<transactionId>`. На проверенное уведомление отвечается `{"status":"ok"}`.

оплаченная транзакция — на её сумму.

**Возвраты и рекуррентные платежи.** Не поддерживаются.

другую. Тариф с ценой в иной валюте CloudPayments не предлагает.

### Настройка

| Переменная | Обязательна | По умолчанию | Значение |
| --- | --- | --- | --- |
| `APP_CLOUDPAYMENTS_PUBLIC_ID` | Да | — | Public ID сайта из кабинета CloudPayments. |
| `APP_CLOUDPAYMENTS_API_SECRET` | Да | — | API secret сайта. Аутентифицирует вызовы API и подписывает уведомления. |
| `APP_CLOUDPAYMENTS_CURRENCY` | Нет | `RUB` | Единственная валюта, в которой отправляются заказы. |
| `APP_CLOUDPAYMENTS_API_URL` | Нет | `https://api.cloudpayments.ru` | Адрес API. |
| `APP_CLOUDPAYMENTS_TEST_MODE` | Нет | `false` | При `false` уведомление с признаком `TestMode` записывается, но никогда не оплачивает заказ. |

Если задан только один из двух ключей, запуск завершается ошибкой; если не задан ни один, адаптер не
регистрируется.

### Уведомления

В кабинете CloudPayments направьте уведомления **Check**, **Pay** и **Fail** на один адрес:

```text
https://<APP_PUBLIC_URL>/v1/payments/webhooks/cloudpayments
```

Каждое уведомление должно нести корректный заголовок `X-Content-HMAC` или `Content-HMAC` — base64 от
HMAC-SHA256 тела на ключе API secret. Принимается подпись и URL-кодированного, и раскодированного
тела: CloudPayments считает эти два заголовка по разным формам. Читаются оба формата уведомлений —
form-urlencoded и JSON.

Все три вида приходят на один адрес, поэтому различаются по содержимому:

- **Pay** — статус `Completed` с полем `Reason` или `AuthCode`. Только это уведомление оплачивает
  заказ.
- **Fail** — статус `Declined` или `Cancelled`. Записывается; ничего не оплачивается.
- **Check** — всё остальное, приходит до списания с карты. Записывается и разрешается; ничего не
  оплачивается.

Статус `Authorized` — двухстадийная блокировка, которую Omniflow никогда не подтверждает, поэтому
заказ не оплачивается. Используйте на сайте одностадийную схему.

На каждое записанное уведомление отправляется ответ `{"code":0}` — единственный, который
CloudPayments считает подтверждением приёма. Идентификатор события — `<вид>:<TransactionId>`, поэтому
повторная доставка распознаётся как дубликат.

### Возможности

- **Опрос.** `POST /payments/find` по номеру счёта, которым служит идентификатор заказа Omniflow. Пока
  транзакции нет, намерение остаётся `pending`.
- **Возвраты.** Полные и частичные, через `POST /payments/refund` по транзакции, найденной для счёта.
  Ключ идемпотентности возврата Omniflow передаётся в `X-Request-ID`, поэтому на повторный запрос
  приходит исходный результат, а не второй возврат.
- **Рекуррентные платежи.** Не поддерживаются. CloudPayments привязывает токен карты к `AccountId`, для
  которого он выпущен, а списание сохранённым способом в Omniflow этого значения не содержит.
- **Проверка подключения.** `POST /payments/find` по заведомо несуществующему счёту: на верные ключи
  ответ приходит без ошибки, на неверные — HTTP 401.

### Проверка

На тестовом сайте задайте `APP_CLOUDPAYMENTS_TEST_MODE=true`, настройте адрес уведомлений и оплатите
заказ тестовой картой CloudPayments. Заказ оплачивается, когда приходит уведомление Pay. Перед приёмом
настоящих платежей верните `APP_CLOUDPAYMENTS_TEST_MODE` в `false`.

## Lava

Счета в рублях через Lava Business API (`https://api.lava.ru`). Каждый запрос — JSON `POST`,
подписанный HMAC-SHA256 точных отправляемых байтов на секретном ключе магазина; подпись передаётся в
заголовке `Signature`. Omniflow создаёт счёт через `POST /business/invoice/create`, и покупатель
платит на странице Lava, на которую ведёт ссылка счёта.

**Валюты.** Только `RUB`: счёт Lava содержит сумму в рублях и не содержит валюты.

### Настройка

| Переменная | Обязательна | По умолчанию | Значение |
| --- | --- | --- | --- |
| `APP_LAVA_SHOP_ID` | Да | — | UUID магазина (проекта). |
| `APP_LAVA_SECRET_KEY` | Да | — | Секретный ключ магазина. Подписывает исходящие запросы. |
| `APP_LAVA_WEBHOOK_SECRET` | Да | — | Дополнительный ключ магазина. Проверяет уведомления. |
| `APP_LAVA_BASE_URL` | Нет | `https://api.lava.ru` | Адрес API. |
| `APP_LAVA_PAYMENT_LIFETIME_MINUTES` | Нет | `60` | Срок жизни счёта, ограничивается допустимыми у Lava 1–7200 минутами. |

Также обязателен `APP_PUBLIC_URL`: каждый счёт несёт адрес уведомлений, и без него Lava не
настраивается. Если задана только часть из трёх ключей, запуск завершается ошибкой.

### Уведомления

Omniflow передаёт адрес уведомлений в каждом счёте, поэтому в кабинете Lava ничего вводить не нужно.
Адрес:

```text
https://<APP_PUBLIC_URL>/v1/payments/webhooks/lava
```

Уведомление должно нести заголовок `Authorization` с шестнадцатеричным HMAC-SHA256 тела на
дополнительном ключе. Современные магазины Lava подписывают тело как есть, а магазины, настроенные под
старый PHP SDK, — его пересериализацию с отсортированными ключами; принимается уведомление,
совпавшее с любой из двух форм.

Заказ оплачивает только статус `success`. Перед этим сумма `amount` в рублях из уведомления
сверяется с заказом. Идентификатор события — `<статус>:<invoice_id>`.

### Возможности

- **Опрос.** `POST /business/invoice/status` по идентификатору счёта Lava.
- **Возвраты.** Не поддерживаются: в Business API нет вызова возврата.
- **Рекуррентные платежи.** Не поддерживаются. Подписки Lava — это продукты, цена и периодичность
  которых задаются в кабинете Lava, а списывает их сама Lava по своему расписанию, а не по запросу
  продавца.
- **Проверка подключения.** `POST /business/invoice/get-available-tariffs` — перечисляет способы
  оплаты магазина и ничего не создаёт.

### Проверка

Задайте три ключа и `APP_PUBLIC_URL`, запустите проверку подключения из панели, затем оплатите
небольшой заказ. Адрес возврата Lava не должен содержать строку запроса; Omniflow убирает её из адреса
возврата перед отправкой.

## Overpay

Заказы с оплатой на странице провайдера через API Overpay (`https://api.overpay.io`) с HTTP Basic
аутентификацией и, если продавцу выдан, клиентским TLS-сертификатом. Omniflow создаёт заказ через
`POST /orders/`, и покупатель платит на странице Overpay, на которую ведёт ссылка заказа.

**Валюты.** Одна — та, в которой работает проект: `RUB`, если `APP_OVERPAY_CURRENCY` не задаёт другую.

### Настройка

| Переменная | Обязательна | По умолчанию | Значение |
| --- | --- | --- | --- |
| `APP_OVERPAY_USERNAME` | Да | — | Имя пользователя API. |
| `APP_OVERPAY_PASSWORD` | Да | — | Пароль API. |
| `APP_OVERPAY_PROJECT_ID` | Да | — | Проект (терминал), в котором создаются заказы. |
| `APP_OVERPAY_CLIENT_CERT` | Вместе с ключом | — | Клиентский сертификат (и цепочка) в PEM для взаимного TLS. |
| `APP_OVERPAY_CLIENT_KEY` | Вместе с сертификатом | — | Незашифрованный закрытый ключ этого сертификата в PEM. |
| `APP_OVERPAY_CURRENCY` | Нет | `RUB` | Единственная валюта, в которой отправляются заказы. |
| `APP_OVERPAY_PAYMENT_METHODS` | Нет | `card,fps` | Способы оплаты на странице через запятую. |
| `APP_OVERPAY_LIFETIME_MINUTES` | Нет | `1440` | Срок жизни заказа. |
| `APP_OVERPAY_API_URL` | Нет | `https://api.overpay.io` | Адрес API. |

Если задана только часть из имени пользователя, пароля и проекта, запуск завершается ошибкой.
Сертификат и ключ задаются оба или не задаются вовсе. Overpay выдаёт сертификат файлом P12;
преобразуйте его в PEM, например `openssl pkcs12 -in overpay.p12 -clcerts -nokeys` для сертификата и
`openssl pkcs12 -in overpay.p12 -nocerts -nodes` для ключа. Значение PEM, записанное в одну строку с
буквальными последовательностями `\n`, тоже принимается.

### Уведомления

Укажите адрес уведомлений в кабинете Overpay:

```text
https://<APP_PUBLIC_URL>/v1/payments/webhooks/overpay
```

Overpay подтверждает подлинность уведомлений взаимным TLS, который завершается перед приложением, и
Omniflow этого не видит. Поэтому уведомление — лишь подсказка: Omniflow берёт из него `id`,
`merchantTransactionId` и `status`, затем перечитывает заказ через `GET /orders/{id}` и применяет
только этот ответ. Заказ оплачивает только статус `charged`, и только если сумма `amount` заказа
читается и совпадает. Идентификатор события — `<статус>:<id>`.

### Возможности

- **Опрос.** `GET /orders/{id}`.
- **Возвраты.** Не поддерживаются. Вызов возврата Overpay не принимает ключ идемпотентности, а Omniflow
  повторно спрашивает о возврате, ответ на который потерян, — это могло бы вернуть деньги дважды.
- **Рекуррентные платежи.** Не поддерживаются.
- **Проверка подключения.** Нет: у Overpay нет запроса на чтение, который подтверждал бы ключи без
  существующего заказа, поэтому панель показывает ключи как непроверенные.

### Проверка

Задайте ключи и сертификат, укажите адрес уведомлений и оплатите небольшой заказ. Сценарий прямого
QR СБП и отдельный международный терминал (EUR) из Bedolaga не перенесены.

## ParityPay

Счета в рублях с оплатой через СБП или картой через API ParityPay v2 (`https://api.paritypay.net`).
Запросы аутентифицируются заголовками `X-ShopId` и `X-SecretKey` (секретный ключ №1). Omniflow
создаёт счёт через `POST /v2/invoice/create`, и покупатель платит на странице ParityPay, на которую
ведёт ссылка счёта.

**Валюты.** Только `RUB`.

### Настройка

| Переменная | Обязательна | По умолчанию | Значение |
| --- | --- | --- | --- |
| `APP_PARITYPAY_SHOP_ID` | Да | — | UUID кассы, передаётся в `X-ShopId`. |
| `APP_PARITYPAY_SECRET_KEY` | Да | — | Секретный ключ №1, передаётся в `X-SecretKey`. |
| `APP_PARITYPAY_CALLBACK_SECRET` | Да | — | Секретный ключ №2. Проверяет уведомления. |
| `APP_PARITYPAY_SERVICE` | Нет | пусто | `sbp` или `card`, чтобы задать один способ; пустое значение оставляет выбор покупателю. Задайте его, если в кассе включён ровно один способ. |
| `APP_PARITYPAY_INVOICE_LIFETIME_MINUTES` | Нет | `60` | Срок жизни счёта. |
| `APP_PARITYPAY_BASE_URL` | Нет | `https://api.paritypay.net` | Адрес API. |

Если задана только часть из трёх ключей, запуск завершается ошибкой.

### Уведомления

Укажите адрес уведомлений в настройках кассы ParityPay. Если задан `APP_PUBLIC_URL`, Omniflow также
передаёт его в каждом счёте как `callback_url`:

```text
https://<APP_PUBLIC_URL>/v1/payments/webhooks/paritypay
```

Уведомление должно нести `X-SIGNATURE` — шестнадцатеричный HMAC-SHA256 на секретном ключе №2 от
значений верхнего уровня тела, склеенных в порядке ключей; числа берутся ровно в том виде, в каком
присланы, а `null` — как пустая строка. Подпись проверяется до чтения чего-либо ещё.

Заказ оплачивает только статус `PAID`; уведомление `PAID` без читаемой суммы `amount` отклоняется.
Идентификатор события — `<статус>:<id>`. Уведомления о подписках, приходящие на тот же адрес,
записываются и подтверждаются, ничего не меняя.

ParityPay отклоняет повторный `order_id` с HTTP 422. Если это случается при повторной попытке оплаты,
Omniflow находит счёт по заказу и использует его.

### Возможности

- **Опрос.** `GET /v2/invoice/status?id=…`. ParityPay допускает 60 запросов в минуту с одного IP,
  поэтому основной поток идёт через уведомления, а не опрос.
- **Возвраты.** Не поддерживаются: в API нет вызова возврата.
- **Рекуррентные платежи.** Не поддерживаются. Подписки ParityPay требуют отдельного согласования с
  провайдером и не списываются по запросу продавца.
- **Проверка подключения.** Нет.

### Проверка

Задайте три ключа, укажите адрес уведомлений и оплатите небольшой заказ. Уведомление с неверной
подписью отклоняется, и ParityPay доставляет его повторно.

## PayHot

Платежи в рублях через API HOT Pay v2 (`https://app.pay.hot/api/v2`). Запросы передают рабочий ключ
как bearer-токен, а каждый создающий вызов — заголовок `Idempotency-Key`. Omniflow создаёт платёж
через `POST /payments` и отправляет покупателя по одноразовой ссылке оплаты, которую возвращает
HOT Pay. Если повторный запрос вернулся без этой ссылки, Omniflow выпускает для того же платежа новую
сессию оплаты.

**Валюты.** Только `RUB`.

### Настройка

| Переменная | Обязательна | По умолчанию | Значение |
| --- | --- | --- | --- |
| `APP_PAYHOT_API_KEY` | Да | — | Рабочий ключ API; должен начинаться с `phk_v2_`. Тестовые ключи отклоняются. |
| `APP_PAYHOT_WEBHOOK_SECRET` | Да | — | Текущий секрет подписи уведомлений. |
| `APP_PAYHOT_PREVIOUS_WEBHOOK_SECRET` | Нет | — | Предыдущий секрет, который принимается, пока завершается его замена. |
| `APP_PAYHOT_PAYMENT_METHOD` | Нет | `card` | Один из `card`, `sbp`, `crypto`, `applepay`, `googlepay`. Выберите способ, подключённый к кассе. |
| `APP_PAYHOT_SUCCESS_URL` | Нет | — | HTTPS-адрес возврата после оплаты; используется, если адрес возврата заказа не HTTPS. |
| `APP_PAYHOT_FAIL_URL` | Нет | — | HTTPS-адрес возврата после неудачной оплаты. |
| `APP_PAYHOT_REQUEST_TIMEOUT` | Нет | `30` | Тайм-аут запроса в секундах, 1–60. |
| `APP_PAYHOT_API_URL` | Нет | `https://app.pay.hot/api/v2` | `https://app.pay.hot/api/v2` или `https://gapi.pay.hot/api/v2`; другие адреса не принимаются. |

Если задан только ключ или только секрет, запуск завершается ошибкой. SberPay не предлагается: ему
нужен телефон плательщика, а оплата в Omniflow его не запрашивает. Переход на адрес успешной оплаты
сам по себе оплату не подтверждает.

### Уведомления

В HOT Pay укажите адрес уведомлений и подпишитесь на события `payment.*`. Если используются
рекуррентные списания, подпишитесь также на `recurring_charge.cancelled` и
`recurring_charge.skipped`.

```text
https://<APP_PUBLIC_URL>/v1/payments/webhooks/payhot
```

Уведомление должно нести `PayHot-Signature: t=<unix-время>,v2=<hex>` — HMAC-SHA256 строки
`<t>.<тело>` на текущем или предыдущем секрете, причём `t` отличается от часов Omniflow не более чем
на пять минут. Omniflow также требует, чтобы `PayHot-Event-Id` совпадал с `event_id` тела,
`PayHot-Api-Version` и `api_version` были равны `v2`, заголовки `PayHot-Delivery-Id` и
`PayHot-Delivery-Attempt` имели правильный вид, ни заголовок, ни поле JSON не повторялись, тело было
не больше 64 КиБ, а окружение было только `production`.

Даже проверенное уведомление — лишь подсказка: платёж (или рекуррентное списание) перечитывается
через API, и применяется только этот ответ. Заказ оплачивает только `succeeded`; авторизация,
частичное списание или возврат — нет. Идентификатор события — `event_id` уведомления. На записанные
уведомления отправляется ответ `{"success":true}`.

### Возможности

- **Опрос.** `GET /payments/{id}` либо `GET /recurring-charges/{id}` для рекуррентного списания.
- **Возвраты.** Не поддерживаются. HOT Pay помечает маршрут возврата как устаревший, и Omniflow его не
  вызывает; возвраты оформляются в кабинете HOT Pay.
- **Рекуррентные платежи.** Заявлены. Сохранённый способ — идентификатор мандата HOT Pay. Списание
  читает мандат, отказывает, если он не `active`, отправляет `POST /recurring-charges` с ключом
  идемпотентности вызывающей стороны и выведенной из него ссылкой на списание, затем перечитывает
  списание. Повтор попадает в то же списание. Для рекуррентных списаний продавцу нужно разрешение
  HOT Pay.
- **Проверка подключения.** Нет.

<Warning>
  Ни один путь кода в Omniflow не оформляет мандат: оплата никогда не запрашивает согласие на
  повторные платежи, поэтому идентификатор мандата не сохраняется. Рекуррентные списания заявлены и
  подключены, но пока не могут быть включены. Какие части работают, описано в разделе
  [Рекуррентные платежи](/ru/commerce/recurring-payments).
</Warning>

### Проверка

Omniflow принимает только рабочие ключи, а уведомления из любого другого окружения отклоняются.
Проверяйте небольшим настоящим платежом на рабочей кассе.

начинается с 50,00 RUB; меньшая сумма для карты отклоняется до обращения к CisPay.

<Steps>
  <Step title="Настройте Omniflow">
    Задайте `APP_CISPAY_SHOP_ID` и `APP_CISPAY_API_KEY`, затем перезапустите API и worker.
  </Step>
  <Step title="Укажите адрес webhook">
    В кабинете CisPay направьте уведомления на
    `https://<APP_PUBLIC_URL>/v1/payments/webhooks/cispay`.
  </Step>
  <Step title="Проверьте подключение">
    Проверка подключения читает `GET /store/capabilities`. Она не проходит, если ключ принадлежит
    другому магазину или магазин неактивен. Ничего не создаётся.
  </Step>
</Steps>

**Проверка webhook.** `X-Signature` — hex HMAC-SHA256 точного тела запроса с API-ключом; подпись
должна совпасть. Уведомление должно относиться к настроенному магазину. Затем Omniflow перечитывает
платёж через `GET /payments/status` и применяет только этот ответ: уведомление может не содержать
признака песочницы, а криптоплатёж может сообщать сумму в центах USD. Криптоплатёж закрывается по
рублёвой `source_amount`. ID события webhook — `{status}:{paymentID}`, поэтому повторная доставка
распознаётся как дубль.

**Тестовые платежи.** Платёж с `is_sandbox` или с `block_reason` никогда не считается оплаченным и
отражается как неуспешный.

**Подписки.** Уведомления о подписках CisPay (`X-CISPay-Event`, `subscription_id`) отклоняются:
Omniflow не открывает подписки CisPay.

**Возвраты и автосписания.** Не поддерживаются. В Merchant API нет вызова возврата, а подписки
CisPay — это расписание, которое ведёт сам CisPay, а не списание сохранённого способа оплаты.

**Опрос статуса.** Поддерживается через `GET /payments/status`.

**Проверка.** Тестовый магазин CisPay позволяет убедиться, что webhook доходит и проходит проверку
подписи. Тестовый платёж никогда не закрывает заказ, поэтому полная проверка зачисления требует
реального платежа.

## Antilopay

Antilopay — размещённая платёжная страница поверх платёжного API Antilopay
(`https://lk.antilopay.com/api/v1`). Тело каждого запроса подписывается SHA256withRSA закрытым
ключом мерчанта, а каждое уведомление подписывает Antilopay; оно проверяется открытым ключом
проекта. Суммы передаются в рублях с точностью до копейки.

**Валюты:** только `RUB`.

| Переменная | Обязательна | По умолчанию | Назначение |
| --- | --- | --- | --- |
| `APP_ANTILOPAY_SECRET_ID` | Да | — | Secret ID, передаётся в `X-Apay-Secret-Id`. |
| `APP_ANTILOPAY_PROJECT_ID` | Да | — | Идентификатор проекта, передаётся в `project_identificator`. |
| `APP_ANTILOPAY_PRIVATE_KEY` | Да | — | Закрытый RSA-ключ мерчанта: base64 от PEM или DER, либо PEM-блок как есть. Подписывает запросы. |
| `APP_ANTILOPAY_PUBLIC_KEY` | Да | — | Открытый RSA-ключ Antilopay для проекта, в тех же форматах. Проверяет уведомления. |
| `APP_ANTILOPAY_PRODUCT_NAME` | Нет | `VPN подписка` | `product_name` каждого платежа. |
| `APP_ANTILOPAY_PRODUCT_TYPE` | Нет | `services` | `product_type` каждого платежа. |
| `APP_ANTILOPAY_PREFER_METHOD` | Нет | пусто | `SBP`, `CARD_RU` или `SBER_PAY`, передаётся в `prefer_methods`. Пустое значение оставляет выбор покупателю. |

Все четыре обязательные переменные задаются вместе, и оба ключа должны читаться; иначе запуск
завершается ошибкой.

<Steps>
  <Step title="Настройте Omniflow">
    Задайте четыре обязательные переменные и перезапустите API и worker.
  </Step>
  <Step title="Укажите адрес webhook">
    В кабинете Antilopay направьте уведомления на
    `https://<APP_PUBLIC_URL>/v1/payments/webhooks/antilopay`.
  </Step>
  <Step title="Проверьте подключение">
    Проверка подключения вызывает `payment/check` для заведомо несуществующего заказа.
    Документированный ответ «платёж не найден» (код 8) подтверждает, что Secret ID и подпись
    приняты. Ничего не создаётся.
  </Step>
</Steps>

**Контакт покупателя.** Antilopay требует email или телефон покупателя. Адаптер берёт их из ключей
метаданных намерения `customer_email` и `customer_phone` и отклоняет платёж до обращения к
Antilopay, если нет ни того, ни другого. Выдуманный адрес не подставляется.

**Ссылка на заказ.** Antilopay ищет платежи по номеру заказа мерчанта, поэтому ID заказа Omniflow
служит ссылкой провайдера, которая сохраняется и опрашивается. Собственный `payment_id` Antilopay
хранится в метаданных намерения.

**Проверка webhook.** `X-Apay-Callback` — base64 RSA-подпись точного тела; она должна проверяться
ключом `APP_ANTILOPAY_PUBLIC_KEY`. Применяются только уведомления `type: payment`. Успешный платёж
закрывается по `original_amount` — сумме, на которую создан заказ; `amount` указан за вычетом
комиссии Antilopay и не используется. Успех без корректной рублёвой `original_amount` отклоняется.
Неизвестные статусы и другие типы уведомлений подтверждаются и игнорируются. ID события —
`{status}:{payment_id}`.

| Статус Antilopay | Статус Omniflow |
| --- | --- |
| `PENDING` | `pending` |
| `SUCCESS` | `succeeded` |
| `FAIL`, `CHARGEBACK` | `failed` |
| `CANCEL` | `cancelled` |
| `EXPIRED` | `expired` |

**Потерянные ответы.** Перед созданием платежа Omniflow спрашивает `payment/check`, нет ли уже
платежа по заказу. Antilopay отклоняет второй платёж с тем же номером заказа, поэтому создание, ответ
на которое потерялся, восстанавливается, а не повторяется.

**Возвраты и автосписания.** Не поддерживаются.

**Опрос статуса.** Поддерживается через `payment/check`.

**Проверка.** Создайте небольшой платёж в своём проекте и убедитесь, что уведомление проходит
проверку подписи и заказ закрывается. Тесты адаптера используют только сгенерированные RSA-ключи и
локальный HTTP-сервер.

## Anore

Anore — размещённая платёжная страница поверх API Anore (`https://api.anore.cc/v1`). Omniflow
создаёт счёт, отправляет покупателя на `paymentUrl` Anore и закрывает заказ, когда Anore сообщает
об оплате счёта. Суммы передаются в рублях.

**Валюты:** только `RUB`.

| Переменная | Обязательна | По умолчанию | Назначение |
| --- | --- | --- | --- |
| `APP_ANORE_API_KEY` | Да | — | API-ключ, передаётся как Bearer-токен. Ключ с префиксом `an_test_` — тестовый. |
| `APP_ANORE_SECRET_KEY` | Да | — | Секрет подписи исходящих запросов и входящих webhook. |
| `APP_ANORE_SHOP_ID` | Для аккаунтного ключа | — | Положительный ID кассы. Обязателен для ключа с префиксом `an_`: аккаунтный ключ обслуживает несколько касс. |
| `APP_ANORE_PAYMENT_METHODS` | Нет | `sbp,card,yoomoney,crypto` | Способы оплаты на форме, через запятую. |
| `APP_ANORE_API_URL` | Нет | `https://api.anore.cc/v1` | Адрес API. |

Ключ без секрета, аккаунтный ключ без ID кассы или неизвестный способ оплаты приводят к ошибке

<Steps>
  <Step title="Настройте Omniflow">

    `APP_ANORE_SHOP_ID`. Перезапустите API и worker.

  <Step title="Укажите адрес webhook">
    Если задан `APP_PUBLIC_URL`, каждый счёт передаёт
    `https://<APP_PUBLIC_URL>/v1/payments/webhooks/anore` в `callbackUrl`. Без него укажите этот же
    адрес в настройках кассы Anore.
  </Step>
</Steps>

**Запросы.** Тело каждого запроса подписывается: `Anore-Signature` — hex HMAC-SHA256 точного тела с
секретом. Email покупателя передаётся, если в метаданных намерения есть `customer_email`. Счёт, в

совпадать с подписанным `event`, а `Anore-Delivery-Id` должен присутствовать. Применяются только

подтверждаются и игнорируются. Зачисляется сумма счёта `amount`. Большая `rubAmount` — комиссия,
оплаченная покупателем, и не зачисляется; меньшая отклоняется. ID события — `{event}:{invoiceID}`,
поэтому повторная доставка с новым ID доставки всё равно распознаётся как дубль.

**Тестовые ключи.** Платёж, созданный ключом `an_test_`, никогда не считается оплаченным и
отражается как неуспешный.

**Возвраты и автосписания.** Не поддерживаются.

**Опрос статуса.** Поддерживается через `GET /payments/{id}`.

**Проверка.** С ключом `an_test_` убедитесь, что уведомление доходит до Omniflow и проходит проверку
подписи. Тестовый платёж никогда не закрывает заказ, поэтому полная проверка зачисления требует
боевого ключа.

проходит проверку подписи и заказ закрывается. Тесты адаптера фиксируют обе подписи на векторах,
посчитанных исходной реализацией на Python.

любой неизвестный статус подтверждаются и игнорируются. Успех без читаемой суммы отклоняется. ID
события — `{status}:{transaction_id}`.

**Возвраты, автосписания и опрос статуса.** Не поддерживаются. Исходная интеграция не разбирает
ответ запроса статуса, поэтому зачисление приходит только через уведомление, а проверки
подключения нет.

**Проверка.** Оплатите небольшой заказ и убедитесь, что уведомление проходит проверку подписи и
заказ закрывается.

## TabPay

TabPay (`https://tabpay.org/api`) принимает оплату по СБП и картами с 3-D Secure через размещённую
страницу `payUrl`. Omniflow создаёт платёж, отправляет покупателя на `payUrl` и закрывает заказ по
подписанному webhook TabPay. Суммы передаются целыми копейками.

**Валюты:** только `RUB`, от 1 RUB до 100 000 000 RUB за платёж.

| Переменная | Обязательна | По умолчанию | Назначение |
| --- | --- | --- | --- |
| `APP_TABPAY_API_KEY` | Да | — | Ключ магазина (`tp_…`), передаётся в `X-Api-Key`. |
| `APP_TABPAY_WEBHOOK_SECRET` | Да | — | Секрет подписи webhook магазина. |
| `APP_TABPAY_METHOD` | Нет | пусто | `SBP` или `CARD`. Пустое значение оставляет выбор покупателю на странице оплаты. |
| `APP_TABPAY_WEBHOOK_MAX_AGE_SECONDS` | Нет | `300` | Допустимое расхождение `X-Timestamp` с часами сервера в обе стороны. |
| `APP_TABPAY_BASE_URL` | Нет | `https://tabpay.org/api` | Адрес API. |

<Steps>
  <Step title="Настройте Omniflow">
    Задайте `APP_TABPAY_API_KEY` и `APP_TABPAY_WEBHOOK_SECRET`, затем перезапустите API и worker.
    Синхронизируйте часы сервера (NTP): webhook вне окна свежести отклоняется.
  </Step>
  <Step title="Укажите адрес webhook">
    В настройках магазина TabPay направьте webhook на
    `https://<APP_PUBLIC_URL>/v1/payments/webhooks/tabpay`.
  </Step>
  <Step title="Проверьте подключение">
    Проверка подключения ищет заведомо несуществующий заказ через
    `GET /v1/payments?orderId=…`. Ответ 404 означает, что ключ принят. Ничего не создаётся.
  </Step>
</Steps>

**Создание платежей.** `POST /v1/payments` передаёт `orderId`, `amountKopecks`, описание, адрес
возврата в `successUrl` и `failUrl`, а также `email`, если в метаданных намерения есть
`customer_email`. Перед созданием Omniflow ищет заказ по `orderId`, поэтому создание, ответ на
которое потерялся, не повторяется. На `409` реакция та же: существующий платёж по заказу
переиспользуется, иначе ошибка остаётся (например, способ оплаты недоступен магазину).

**Проверка webhook.** `X-Signature-V2` — hex HMAC-SHA256 от `{X-Timestamp}.{сырое тело}` с секретом
подписи, а `X-Timestamp` должен попадать в окно свежести. `SUCCESS` без `amountKopecks`
отклоняется. Неизвестные статусы подтверждаются и игнорируются. ID события — `{status}:{id}`.

| Статус TabPay | Статус Omniflow |
| --- | --- |
| `CREATED` | `pending` |
| `PENDING` | `processing` |
| `SUCCESS` | `succeeded` |
| `FAILED` | `failed` |
| `EXPIRED` | `expired` |
| `REFUNDED`, `CANCELED` | `cancelled` |

`FAILED` и `EXPIRED` у TabPay не окончательны: QR СБП можно оплатить после таймаута, и такая оплата
приходит отдельным `SUCCESS`, который Omniflow закрывает как позднюю оплату.

**Тестовые платежи.** Платёж с признаком `test` или `isTest` никогда не считается оплаченным и
отражается как неуспешный. Признаком теста считается только явное «да».

**Возвраты и автосписания.** Не поддерживаются.

**Опрос статуса.** Поддерживается через `GET /v1/payments/{id}`.

**Проверка.** Тестовый магазин TabPay позволяет убедиться, что webhook доходит и проходит проверку
подписи. Тестовый платёж никогда не закрывает заказ, поэтому полная проверка зачисления требует
боевого магазина.
