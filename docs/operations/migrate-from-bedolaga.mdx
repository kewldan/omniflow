---
title: Migrating from Bedolaga
description: Move a Bedolaga bot's customers, balances, subscriptions, and referrals into Omniflow with a rehearsed cutover that keeps every subscription link working
---

An installation running the Bedolaga Telegram bot already has customers, money on their balances,
and paid subscriptions served by Remnawave. Moving to Omniflow means carrying those over without
charging anybody twice, losing a kopek, or changing a single access link — and being able to step
back if the cutover goes wrong.

`cmd/migrate-bedolaga` does the data part. It reads the Bedolaga database inside one read-only
snapshot, reads the Remnawave panel's user list, and writes Omniflow through Omniflow's own tables
and services. The scripts in `deploy/migration/` wrap it into a rehearsal on a copy and a guarded
cutover.

<Note>
  The importer **never writes to Bedolaga or to Remnawave**. The Bedolaga connection is opened with
  `default_transaction_read_only=on` and every read runs in a `READ ONLY` transaction. The only panel
  call it can make is the user list: the interface it is given has no other method, and an imported
  entitlement gets no fulfillment operation, so no job exists that could push anything. Remnawave
  keeps owning the users and their subscription links; a customer's link before the cutover is their
  link after it.
</Note>

## The fastest safe path

<Steps>
  <Step title="Prepare Omniflow">
    Deploy Omniflow with its migrations applied, create a plan version for every Bedolaga tariff you
    still sell, and configure the payment providers you use — `00-convert-env.sh` carries their
    credentials over from Bedolaga's `.env`. Do not start Omniflow's bot or worker against the
    production panel yet.
  </Step>
  <Step title="Rehearse on a copy">
    `01-snapshot-bedolaga.sh`, `02-restore-staging.sh`, then `03-plan.sh`, `04-apply.sh`, and
    `05-verify.sh` against a scratch Omniflow database. Repeat until the plan shows no conflict you
    have not decided about and verification passes. Note how long `apply` took.
  </Step>
  <Step title="Cut over">
    `06-cutover.sh` stops Bedolaga, takes a final snapshot, runs the final import against production,
    verifies it, moves the Telegram bot and the payment webhooks, and starts Omniflow's worker last.
  </Step>
  <Step title="Keep the way back open">
    Leave the Bedolaga containers stopped, not removed. `07-rollback.sh` puts Bedolaga back in front of
    customers if you need it.
  </Step>
</Steps>

## What moves, and where

| Bedolaga | Omniflow | How |
| --- | --- | --- |
| `users` row | `users` | Status, locale (`ru` or `en`; anything else becomes `ru`), and the original `created_at` |
| `users.telegram_id`, `username`, `first_name`, `last_name` | `identities` | An active, verified `telegram` identity; the names go in its `metadata` as `username`, `firstName`, `lastName` |
| `users.email` when `email_verified` | `contact_channels` | Kind `email`, sealed with `APP_DATA_ENCRYPTION_KEY`, verified, transactional on, marketing off. An unverified address is not carried |
| `users.status = 'blocked'` | `users.status = 'suspended'`, or `active` with the bot marked blocked | `blockedUsers: suspend` suspends with a lifecycle event saying why; `blockedUsers: bot_blocked` keeps the customer active and writes `bot_delivery_state` as `blocked`, see [the mapping file](#the-mapping-file) |
| `users.balance_kopeks` | `ledger_transactions` + `ledger_entries` | One audited wallet adjustment per customer, see [below](#balances) |
| `users.remnawave_id`, or the first active subscription's panel user | `remnawave_users` | The customer-level mapping the bot reads |
| Active `subscriptions` row | `subscriptions` + `orders` + `order_lines` + `entitlements` | See [subscriptions](#subscriptions) |
| Expired `subscriptions` row whose panel user still exists | `subscriptions` | Linked to that panel user, no entitlement |
| Any subscription, ended or not, or `has_had_paid_subscription` | `trial_claims` | The customer's one trial is spent, see [history](#history-trials-periods-and-payments) |
| Every `subscriptions` row except `pending` | `legacy_subscription_periods` | Start, end, and the trial flag, so segments find customers whose subscription ran out before the migration |
| Completed `transactions` of type `subscription_payment` and `gift_payment`, and gifts bought through a provider (`guest_purchases`) | `legacy_payments` | Amount, date, and method, so segments, loyalty, and reports count what customers spent on VPN before the migration |
| Last use of a `discount` promo code, last claimed discount offer (`discount_offers`) | `legacy_customer_discounts` | The date a promotion's [`discountCooldownDays`](/commerce/catalog-promotions#eligibility) reads |
| `users.referral_code` | `referral_code_aliases` | Upper-cased beside the new Omniflow code, so invite links already handed out keep attributing; see [referrals](#referrals) |
| `users.referred_by_id` | `referral_attributions` | Same referrer; qualified when the referee had paid, see [referrals](#referrals) |
| `REFERRAL_*` keys of `system_settings`, `referral_reward_levels` | `referral_programs` | What an invite pays, switched on as it was, see [referral terms](#referral-terms) |
| `advertising_campaigns` | `ad_campaigns` | By `/start` code, lower-cased; an Omniflow campaign with the code already is matched and left as it is, see [campaigns](#advertising-campaigns) |
| `advertising_campaign_registrations` | `customer_campaign_attributions` | The first campaign a customer arrived through, on its original date, with the bonus recorded as given |
| `stars_orders` with status `completed` | `legacy_goods_orders` | Stars, amount, and delivery date, so segments find stars buyers and the sales report shows the old shop apart, see [Stars orders](#stars-shop-orders) |
| `privacy_policies`, `public_offers`, `service_rules`, `faq_pages` | `info_pages`, `info_page_localizations` | The policy, the offer, the rules, and the FAQ as the pages `privacy`, `offer`, `terms`, and `faq`, see [documents](#documents-tickets-and-consents) |
| `tickets`, `ticket_messages` | `support_tickets`, `support_messages` | Every ticket with its whole conversation and dates, see [documents](#documents-tickets-and-consents) |
| `legal_consents` | `consent_records` | Who accepted the policy and the offer, and when |
| `promo_groups`, `user_promo_groups` | `loyalty_programs`, `loyalty_tiers`, `loyalty_memberships` | A spend programme with a tier per group and every member kept in theirs, see [loyalty](#loyalty-and-the-history-archive) |
| Every other table | `legacy_records` | Row by row, without secret columns, as history on the customer card, see [the archive](#loyalty-and-the-history-archive) |
| `tariffs` | — | Mapped to plan versions by your [mapping file](#the-mapping-file) |

The importer's own bookkeeping is two tables. `bedolaga_import_items` holds one row per Bedolaga
user, subscription, and referral pair it has decided about — the durable mapping from a Bedolaga
ID to the Omniflow customer, subscription, and entitlement — and `bedolaga_import_runs` holds each
apply run with its full report.

### Balances

Bedolaga stores balances in kopeks, which are RUB minor units, so the amount is carried as it is.
Each positive balance becomes one wallet adjustment through the same path an operator adjustment
takes: type `credit`, reference `bedolaga-user:<id>:1`, the reason from your mapping (shown to the
customer), and a `wallet.adjusted` audit event naming the actor. Zero balances write nothing.
Negative balances are a conflict and are not carried.

If the Bedolaga balance changed after an earlier run — the final delta during the cutover — the next
run writes the difference as a `correction` numbered `bedolaga-user:<id>:2`, `:3`, and so on. What
was already moved is read from the ledger itself, so a run that dies right after a movement commits
sees that movement next time and never credits twice.

### Subscriptions

A subscription that is `active`, `trial`, or `limited` in Bedolaga with an end in the future becomes:

- a subscription on the customer's next free slot, adopting the Remnawave user that already serves
  it — the subscription keeps its access link, and a renewal later patches that user;
- a zero-value order, state `fulfilled`, operation `purchase`, idempotency key
  `bedolaga:subscription:<id>`, with one order line on the mapped plan version. It adds nothing to
  revenue and is how the entitlement is tied to a plan;
- an entitlement with status taken from the panel (`ACTIVE` → `active`, `LIMITED` → `limited`,
  `DISABLED` → `disabled`), starting at Bedolaga's `start_date` and ending at Bedolaga's `end_date`,
  with the traffic limit, device limit, and squads the panel holds for that user today.

Mirroring the panel's limits is deliberate: once Omniflow's worker runs, its reconciliation pushes the
entitlement to the panel every fifteen minutes, and a mirror changes nothing. The end date is
Bedolaga's, because Bedolaga is where the customer paid; where it differs from the panel's expiry
(after the plan's grace period) the plan reports `expiry_differs_from_panel`, and the first
reconciliation will move the panel to Bedolaga's date.

A subscription is matched to its panel user by `subscriptions.remnawave_id`. A user with exactly one
subscription and no ID on it falls back to `users.remnawave_id`, which is how Bedolaga stored it
before multi-tariff.

### History: trials, periods, and payments

Three kinds of record carry what happened before the migration, so a migrated base is not a base of
customers who seem never to have subscribed or paid.

**Trial claims.** Bedolaga offered the trial only to somebody with no subscription at all. Every
imported customer who had any subscription in Bedolaga — a live or expired trial, a paid subscription,
whether or not its panel user still exists — or who is marked `has_had_paid_subscription` gets a row
in `trial_claims`, so the Omniflow trial is refused to them as Bedolaga refused it. The claim is dated
when their first Bedolaga subscription started, and its `origin` says which kind it is:
`bedolaga_trial` for a customer who had a trial, `bedolaga_history` for one who subscribed without
one. A `bedolaga_history` claim blocks a trial without having been one, so trial conversion figures
leave it out. A live trial still claims through the order its entitlement hangs off; every other
carried claim has no order. The claim names the plan of the mapping's `trial: true` rule, or the
catalogue's only plan of kind `trial`; with neither, the claims are the conflict `trial_plan_missing`.
Carried claims are written in a transaction marked as an import, so the operator group is not told
about thousands of trials taken today.

**Subscription periods.** Every Bedolaga subscription except an unpaid `pending` one becomes a row of
`legacy_subscription_periods` with its start, end, and trial flag, including the ones whose panel user
is gone. A subscription still running also became an entitlement; the period sits beside it. A
repeated run before the cutover moves a period's dates when Bedolaga renewed or cut the subscription.

**Payments.** The history is what customers spent on VPN, not what they paid into the balance: in
the Omniflow fork of Bedolaga the balance also buys Telegram Stars, so a top-up (`deposit`) says
nothing about where the money went. What is carried is every completed VPN purchase: a
`subscription_payment` — a subscription, renewal, or add-on, from the balance or through a provider
on a landing page — a `gift_payment`, a gift paid from the balance, and a gift bought in the web
cabinet through a provider (a `guest_purchases` row with `is_gift`, a buyer, and `paid_at`, stored
under the source `bedolaga_gift`, because no transaction records it). Stars purchases
(`stars_payment`) are not. Each becomes a row of `legacy_payments` with its amount in kopeks (Bedolaga
writes some purchases as negative debits; the absolute amount is carried), its date (`completed_at`,
or `created_at` where Bedolaga did not record one; a gift's `paid_at`), and `payment_method`. A
zero-amount purchase is an operator's tariff switch and is not carried. The mapping's
`excludedPaymentMethods` leaves out purchases by the methods it lists (nothing by default), and the
plan counts what each excluded method removed. A payment is carried once: a repeated run writes
only the purchases made since.

**Last discount.** For each customer the importer takes the latest moment Bedolaga gave them a
one-off discount — a use of a promo code of type `discount`, or a discount offer they claimed with a
non-zero percent — and stores it in `legacy_customer_discounts`. A promotion with
`discountCooldownDays` reads it beside Omniflow's own redemptions, so "a discount at most once in
sixty days" holds across the cutover. A promo group's standing discount is not a one-off and is not
read. A repeated run only ever moves the date later.

**Unclaimed gifts.** A gift somebody paid for whose recipient has not received it yet (a
`guest_purchases` row with `is_gift`, `paid_at` set, and a status other than `delivered`) is **not**
carried: the recipient's claim link points at Bedolaga. The plan counts them, sums them, breaks them
down by status, and names each one by its Bedolaga ID in the problems with the code
`gift_unclaimed`. Hand each over or refund it in Bedolaga before the cutover; the money for it is
already in the buyer's carried payments.

None of these is Omniflow's record of a sale. No ledger entry, order, or entitlement is written
for them, and Omniflow's own sales figures do not include them. What reads them:

| Reader | What it counts |
| --- | --- |
| Segment filter `goods` | Carried Stars orders beside Omniflow's delivered goods orders |
| Segment filter `subscription` | `expired` and `none` count carried periods as subscriptions had |
| Segment filter `expiredDaysAgo` | The end of the last carried period or entitlement |
| Segment filters `minimumSpendMinor`, `inactiveForDays`, `activeWithinDays` | Carried payments as spend and as activity |
| Segment filter `trial` | A carried trial period as a trial had |
| [Loyalty](/commerce/referrals-loyalty) | Carried payments in the programme's currency and window as spend and as orders; the first carried period as the start of tenure |
| [Sales report](/operations/sales-reporting) | Carried payments as earlier payments for returning payers, and what customers spent on VPN in the previous bot in the period, apart from the sales |

### Referrals

Every customer gets an Omniflow referral code, and their Bedolaga code is kept beside it in
`referral_code_aliases`, upper-cased. Links already handed out keep crediting the same inviter: the
bot reads a bare `/start refAbCd1234` as a referral when somebody holds that code, and otherwise as a
campaign code the way it did before; a `<site>/?ref=refAbCd1234` cabinet link is carried to sign-in;
a code typed or attached by an operator works in either form. Two Bedolaga codes that differ only in
case cannot be told apart once upper-cased, so neither is carried (`duplicate_referral_code`); a code
another customer already holds stays with them (`referral_code_taken`).

Every pair whose both sides are imported becomes an attribution with Bedolaga's sign-up date as its
`created_at`. When the referee had paid in Bedolaga (`has_had_paid_subscription`) the attribution
arrives with `qualified_at` set and no qualifying order. Its inviter was rewarded in Bedolaga, so an
attribution like that never pays again in Omniflow; a referee who never paid qualifies on their first
Omniflow order as usual, subject to the programme's validity window.

### Referral terms

What an invite paid becomes Omniflow's [referral programme](/commerce/referrals-loyalty), switched on or
off as it was in Bedolaga, so invites do not go unrewarded from the morning after the cutover. The terms
are resolved the way the bot resolved them: its compiled-in defaults, under the `REFERRAL_*` keys saved
from its admin panel in `system_settings`, under the `REFERRAL_*` lines of its `.env` — a key set in
`.env` is one the panel could no longer change. Only the database is read, and only keys with that
prefix (the same table holds the bot's tokens), so copy the `REFERRAL_*` lines of `.env` into the
mapping's `referralSettings`; without them the database and the defaults decide.

| Bedolaga | Omniflow |
| --- | --- |
| `legacy` scheme: `REFERRAL_INVITER_BONUS_KOPEKS`, `REFERRAL_FIRST_TOPUP_BONUS_KOPEKS` | `inviterRewardMinor`, `inviteeRewardMinor` |
| `REFERRAL_COMMISSION_PERCENT`, `REFERRAL_FIRST_PAYMENT_COMMISSION_PERCENT` | `commissionBps`, `firstPaymentCommissionBps` |
| `REFERRAL_RECURRING_COMMISSION_TIERS` (`0:10,10:15`) | the `0:` rung as `commissionBps`, the rest as `commissionTiers` |
| `REFERRAL_MAX_COMMISSION_PAYMENTS` | `commissionPaymentCap` (0 is none) |
| `levels` scheme, level 1 paying once (`first_topup`, `registration`) | fixed sums as the one-off rewards, days as `inviterRewardDays` / `inviteeRewardDays`, a percent as the first payment's commission |
| `levels` scheme, level 1 on `every_topup` | its percent as `commissionBps`, `max_payments` as the cap |
| `REFERRAL_ALLOW_REWARD_KIND_CHOICE` | `allowRewardChoice` |
| `REFERRAL_PROGRAM_ENABLED` | `enabled` |

Commission counts subscription orders and top-ups alike, because money reached Bedolaga as top-ups
and reaches Omniflow mostly as orders; only what a provider settled ever earns. `plan` prints the
terms beside a warning for each thing Omniflow cannot say the same way:
`referral_qualifies_on_first_paid_order` (Bedolaga paid on the first top-up, Omniflow on the first
subscription order paid with outside money), `referral_minimum_topup_not_carried`,
`referral_deeper_levels_not_carried`, `referral_required_referrals_not_carried`,
`referral_tariff_reward_as_days` (days on the customer's own plan), `referral_recurring_fixed_reward_dropped`,
`referral_days_clamped`, and `referral_program_disabled`.

The programme is saved once, in one transaction with the audit row `referral.program.saved`. A
programme Omniflow already has stands: one that pays exactly these terms is `unchanged`, any other is
skipped as `referral_program_exists`. Terms that reward nobody are skipped as
`referral_program_pays_nothing`.

### Advertising campaigns

Each Bedolaga campaign is carried under its `/start` parameter, lower-cased, as an Omniflow
campaign code, so a link already in an ad keeps attributing the newcomers it brings. The bonus is
mapped: `balance` becomes wallet credit of the same amount in the mapping's currency, `subscription`
becomes that many days on the trial plan, `tariff` becomes its days on the trial plan with the warning
`tariff_bonus_as_days` (Omniflow's plans are not Bedolaga's tariffs), and `none` stays none. Days
outside 1–365 drop the bonus with the warning `campaign_bonus_dropped`, and the campaign is carried for
tracking. The campaign is active or not as it was. A code Omniflow cannot hold (it allows `a–z`,
`0–9`, and `_`, two to forty characters) is skipped with `invalid_campaign_code`; two Bedolaga codes
that differ only in case are both a conflict (`duplicate_campaign_code`). A campaign whose code an
Omniflow campaign already has is matched: the operator's bonus and name stand.

Each registration whose customer is imported becomes the customer's campaign attribution, on the
registration's date, with the bonus recorded as given then — the customer had it in Bedolaga, and it
is not given again. A customer is attributed to one campaign, the first that brought them; a later
registration is skipped with `earlier_campaign_registration`, and a customer Omniflow already
attributed elsewhere keeps that attribution (`already_in_campaign`). The `adCampaign` segment filter
and the campaign statistics on `/admin/marketing` then count the carried customers. A repeated run
carries nothing twice.

### Stars shop orders

A Telegram Stars order the fork's shop delivered (`stars_orders.status = 'completed'`) is carried
into `legacy_goods_orders`: the customer, the stars, the amount in kopeks, and the delivery date
(`completed_at`, or `created_at` where the column is absent). Paid, failed, refunded, and in-review
orders are money that did not become stars and stay in the archive's count. The segment filter
`goods` — `{"kind": "stars", "withinDays": 90}` — finds a stars buyer among Omniflow's delivered goods
orders and the carried ones, so "stars buyers without a VPN" is `goods` with `subscription: none`. The
[sales report](/operations/sales-reporting) shows what the old shop delivered in the period apart from
Omniflow's sales and from the previous bot's VPN payments. A carried order is history: no ledger
entry, goods order, or delivery is written for it.

### Documents, tickets, and consents

The privacy policy, the public offer, the service rules, and the FAQ become the pages `privacy`,
`offer`, `terms`, and `faq`, one language each for Russian and English. The FAQ is one page with a
heading per question, in Bedolaga's order; several active rules sections become headed sections of
one page. The text is converted to the [page syntax](/features/support): https links stay links,
other markup is dropped, and a short numbered line standing alone becomes a heading. A document
Bedolaga had switched off is carried unpublished, so its text is not lost. A page that already has
the language in Omniflow — written in the panel or carried before — is never replaced.

Every ticket moves with every message, its status (`answered` becomes `pending`, Omniflow's
**Answered**), its priority, and its dates. The messages are marked delivered and read, so the bot
pushes nothing to the customer, and the operator notices the insert would queue are removed in the
same transaction. A file attached in Bedolaga is carried as a line such as `📎 фото: caption`: the
file itself stays in the previous bot's chat. Accepted documents become consent records with the
policy version `bedolaga`, so a terms gate that asks for a newer version still asks.

### Loyalty and the history archive

Promo groups become a loyalty programme, made only when Omniflow has none: the metric is spend over
ten years (Bedolaga counted total spend, and the spend includes the carried payments), a tier per
group with its discounts and its auto-assign threshold, the default group as the bottom tier at
zero, and a group without a threshold as a tier only an operator grants. It is published and every
customer's standing is evaluated. Every member of a group is also kept in its tier as a membership
noted `Bedolaga`, so nobody's discount lapses while the first evaluation runs. Per-period discounts
are not carried (warning `period_discounts_dropped`). A programme an operator built is never laid
over (`loyalty_program_exists`).

Every other row of every other table moves into `legacy_records`, as it was: wallet transactions,
referral earnings, subscription events, promo codes and their uses, coupons, offers, notifications
sent, wheel spins, payments by provider, button presses, operator actions, errors. Columns that held
secrets — passwords, tokens, hashes, VPN credentials, subscription links, IP addresses — are dropped
before a row is read, and `system_settings` (the bot's keys) and the token tables are never read. A
row of a user who is not carried is left behind. The customer card shows a customer's rows under
**Activity → From the previous bot**; a merge moves them and anonymising erases them. Nothing in
Omniflow acts on them.

## What does not move

| Stays in Bedolaga | Why, and what to do |
| --- | --- |
| Telegram Stars shop orders that were not delivered | Paid, failed, refunded, or in-review orders are not stars anybody received. The plan counts them by status and sum; they stay in the archive. Delivered ones are carried as [history](#stars-shop-orders) |
| Files attached to support messages | The message says a file was attached; the file stays in the previous bot's chat |
| Promo codes as codes customers can still enter | All of the previous bot's codes are in the archive; recreate one you still want in the panel |
| Pending partner withdrawal requests | They are in the archive as history; settle pending ones in Bedolaga first |
| Saved payment methods and auto-payment agreements | Provider tokens belong to Bedolaga's merchant setup; customers turn auto-renewal on again in Omniflow |
| Cabinet passwords | Omniflow has no customer passwords. Customers sign in with Telegram, an e-mailed link (`APP_RESEND_API_KEY`), or a provider. Google, Yandex, Discord, and VK ID links **are** carried as identities bound to the preset issuers, so enable those providers under the preset slugs `google`, `yandex`, `discord`, `vk`. A customer with neither a Telegram ID nor a verified e-mail is imported with the warning `no_sign_in_identity` |
| Deleted users | Skipped with `deleted_in_source` |
| Grace-period overlays | The entitlement ends at the paid `end_date`, not at a grace overlay's date |

## Before you start

- **Bedolaga v5** with numeric Remnawave IDs (`users.remnawave_id`, `subscriptions.remnawave_id`).
  The reader checks the columns it needs and stops with the missing one named.
- **Omniflow deployed**, migrations applied, the API answering on `APP_PUBLIC_URL`, payment providers
  configured, and a plan version for every tariff with active subscriptions. A trial plan (kind
  `trial`) if anybody ever subscribed in Bedolaga: carried trial claims name it.
- **The importer built**, from the same commit as your Omniflow deployment:

  ```bash
  go build -o migrate-bedolaga ./cmd/migrate-bedolaga
  # or as an image
  docker build -f build/go.Dockerfile --build-arg TARGET=migrate-bedolaga -t omniflow-migrate-bedolaga .
  ```

- **A read-only role** on the Bedolaga database for the final import. The reader is read-only by
  itself; a role that can only `SELECT` makes that true twice:

  ```sql
  CREATE ROLE omniflow_reader LOGIN PASSWORD '<choose one>';
  GRANT CONNECT ON DATABASE remnawave_bot TO omniflow_reader;
  GRANT USAGE ON SCHEMA public TO omniflow_reader;
  GRANT SELECT ON ALL TABLES IN SCHEMA public TO omniflow_reader;
  ```

- **An environment file** outside the repository, from `deploy/migration/migration.env.example`,
  `chmod 600`, loaded with `set -a; . /path/to/file; set +a`. The scripts check variables and never
  print them.

### What the importer reads

| Variable | What it is |
| --- | --- |
| `APP_DATABASE_URL` | The Omniflow database it writes |
| `APP_DATA_ENCRYPTION_KEY` | The key the API seals contacts with; verified e-mails are sealed with it |
| `APP_REMNAWAVE_URL`, `APP_REMNAWAVE_TOKEN` | The panel; only `GET /api/users/` is called |
| `APP_BEDOLAGA_DATABASE_URL` | The Bedolaga database; only read |

### The mapping file

Your decisions, in YAML or JSON (`deploy/migration/mapping.example.yaml`). Unknown keys are refused,
so a typo cannot silently leave a tariff unmapped.

```yaml
currency: RUB
blockedUsers: bot_blocked      # or: suspend, active. Required when Bedolaga has blocked users
walletReason: "Balance carried over from the previous bot"
plans:
  - tariffId: 1
    planVersionId: 0b7c…       # the monthly default for tariff 1
  - tariffId: 1
    periodDays: 360
    planVersionId: 5d1e…       # yearly subscriptions of tariff 1
  - trial: true
    planVersionId: 9a40…       # every trial
  - noTariff: true
    planVersionId: 77f2…       # subscriptions sold without a tariff
excludedPaymentMethods: []    # the default; purchases by listed methods are not payment history
referralSettings:              # the REFERRAL_* lines of Bedolaga's .env, if any
  REFERRAL_COMMISSION_PERCENT: "15"
```

More specific rules win: a tariff with `periodDays` over the tariff alone, a tariff rule over a
tariff-less trial rule. `periodDays` matches a subscription whose start-to-end length rounds to that
many days. `plan` lists every Omniflow plan version you can name and every tariff still unmapped.

`excludedPaymentMethods` lists the Bedolaga payment methods whose purchases are not carried as VPN
spend. Left out, nothing is excluded: a purchase from the `balance` is VPN spend like one through a
provider, and a purchase with no method on record is always carried. Methods are matched without
regard to case.

`blockedUsers` has no default on purpose. Bedolaga writes `blocked` both when an operator bans
somebody and when a broadcast finds that the customer blocked the bot; the data cannot tell the two
apart, so until you choose, every blocked user is the conflict `blocked_policy_missing`. The three
policies:

| Policy | The customer arrives | Use it when |
| --- | --- | --- |
| `bot_blocked` | Active, with `bot_delivery_state` set to `blocked` (`imported_from_bedolaga`) | Most blocked users are customers who blocked the bot. Every delivery pass skips them, so the first broadcast does not go into closed chats and its blocked share is not inflated; the bot clears the state the moment they write to it again. A user without a Telegram ID is just active |
| `suspend` | Suspended, with a lifecycle event | Most blocked users were banned by an operator |
| `active` | Active, as if never blocked | You will re-check them yourself |

`bot_blocked` does not switch anyone's subscription off. That happens only if you also turn on
**Settings → Marketing → disable subscriptions of customers who blocked the bot**, which is off by
default.

## Environment variables, Bedolaga → Omniflow

`deploy/migration/00-convert-env.sh` does the conversion below for you: it reads Bedolaga's `.env`,
writes the core settings and the variables of every payment provider whose `<PROVIDER>_ENABLED` is

## Rehearsal

Run it on the server Bedolaga runs on, or anywhere that can reach the bot database container.

<Steps>
  <Step title="Snapshot">
    ```bash
    sh deploy/migration/01-snapshot-bedolaga.sh
    ```
    `pg_dump` runs inside `BEDOLAGA_DB_CONTAINER` (default `remnawave_bot_db`) and writes
    `bedolaga-<time>.dump` with a `.sha256` beside it into `MIGRATION_DIR`. Files are never overwritten.
  </Step>
  <Step title="Restore into a scratch database">
    ```bash
    sh deploy/migration/02-restore-staging.sh "$MIGRATION_DIR"/bedolaga-<time>.dump
    set -a; . "$MIGRATION_DIR/staging.env"; set +a
    ```
    Checks the checksum, starts a PostgreSQL container on `127.0.0.1:${STAGING_PORT:-55432}`, restores,
    and writes `APP_BEDOLAGA_DATABASE_URL` to `staging.env` with a password generated for this copy.
    Point `APP_DATABASE_URL` at a scratch Omniflow database with the migrations applied and your
    catalogue created.
  </Step>
  <Step title="Plan">
    ```bash
    sh deploy/migration/03-plan.sh
    ```
    Writes nothing. Read the counts, the conflicts, the unmapped tariffs, the warnings, and what stays
    in the archive. Fix the mapping and repeat.
  </Step>
  <Step title="Apply, twice">
    ```bash
    sh deploy/migration/04-apply.sh     # asks you to type: apply
    sh deploy/migration/04-apply.sh     # the second run must write nothing
    ```
    `APPLY_LIMIT=100` makes a staged first pass that stops after a hundred writes.
  </Step>
  <Step title="Verify">
    ```bash
    sh deploy/migration/05-verify.sh
    ```
    Then sign in to the scratch Omniflow panel and look at a few customers you know.
  </Step>
</Steps>

<Warning>
  During a rehearsal, run **no Omniflow worker against the production panel**. The worker reconciles
  every active entitlement with Remnawave every fifteen minutes; pointed at production, a rehearsal
  database would start writing to real users. The importer itself only reads the panel, so plan,
  apply, and verify are safe against production Remnawave.
</Warning>

### Conflicts and warnings

A conflict is not imported and is re-evaluated on the next run, so fixing the data and running
`apply` again is the whole procedure. The JSON reports name records by their Bedolaga row ID only.

| Code | Meaning |
| --- | --- |
| `duplicate_telegram_id` | Two Bedolaga users share a Telegram ID; neither is imported |
| `invalid_telegram_id` | A zero or negative Telegram ID |
| `telegram_already_linked` | An Omniflow customer already holds that Telegram ID — somebody used the new bot early. Merge the accounts in the panel afterwards if needed |
| `blocked_policy_missing` | A blocked user and no `blockedUsers` in the mapping |
| `negative_balance` | The customer imports; the balance does not |
| `subscription_without_remnawave_user` | An active subscription with no panel user ID |
| `remnawave_user_not_found` | The panel has no user with that ID |
| `duplicate_remnawave_user` | Two Bedolaga subscriptions point at one panel user |
| `remnawave_user_already_linked` | An Omniflow customer already owns that panel user |
| `unmapped_tariff`, `unknown_plan_version` | Fix the mapping file |
| `user_not_imported`, `referrer_not_imported`, `referee_not_imported` | Follows from a conflict on the user |
| `entitlement_owned_by_omniflow` | A refresh refused because Omniflow already acted on that entitlement |
| `duplicate_campaign_code` | Two Bedolaga campaigns whose codes differ only in case; neither is carried |

Warnings never block: `expiry_differs_from_panel`, `telegram_differs_from_panel`,
`panel_status_differs`, `plan_kind_mismatch`, `plan_version_retired`, `language_defaulted`,
`no_sign_in_identity`, `several_subscriptions` (enable `APP_MULTI_SUBSCRIPTION_ENABLED` and set
`APP_MAX_SUBSCRIPTIONS_PER_CUSTOMER` if customers hold several), `balance_decreased`,
`changed_since_apply`, `tariff_bonus_as_days`, and `campaign_bonus_dropped`. Skips that need no
action: `invalid_campaign_code`, `campaign_not_carried`, `earlier_campaign_registration`, and
`already_in_campaign`.

## How long the cutover takes

Customers notice the window between stopping Bedolaga and the Omniflow bot answering. Inside it:
a `pg_dump` of the bot database, one `apply`, one `verify`, and the manual steps. Each record is its
own short transaction and the panel's user list is read in pages of 500, so `apply` usually takes
seconds to a few minutes; measure it on your own data during the rehearsal — every run's start and
finish are in `bedolaga_import_runs`, and `migrate-bedolaga runs` lists them. The provider dashboards
and the smoke test take longer than the import; thirty minutes is a comfortable window for an
installation that rehearsed.

## Cutover

```bash
sh deploy/migration/06-cutover.sh
```

The script walks the list below, running what it can and stopping for what a person must do. Every
step that changes something prints the command and waits for a typed phrase.

1. **Preconditions.** Rehearsal passed with this mapping, Omniflow deployed, Omniflow's bot and
   worker not running, customers told.
2. **Maintenance.** `docker stop` on Bedolaga's bot (and `BEDOLAGA_EXTRA_CONTAINERS`, such as the
   cabinet). Its database keeps running. The time is written to `MIGRATION_DIR/cutover-at`.
3. **Final snapshot** with `01-snapshot-bedolaga.sh` — the archive of everything that does not move.
4. **Final import.** `04-apply.sh` against production with `APP_BEDOLAGA_DATABASE_URL` on the
   production bot database, then `05-verify.sh`. A mismatch stops the cutover.
5. **Telegram.** Shows the current webhook; in polling mode deletes it; starts Omniflow's bot with
   the same token, which registers its own webhook; shows the registration again. Send `/start` from
   an account that was in Bedolaga.
6. **Payment providers.** Prints `https://<APP_PUBLIC_URL>/v1/payments/webhooks/<slug>` for every
   slug in `PAYMENT_PROVIDERS` to set in that provider's dashboard. Telegram Stars needs no URL.
7. **Subscription links.** Nothing to change: Remnawave owns them. With `SAMPLE_SUBSCRIPTION_URL`
   set the script checks one before and after.
8. **Worker.** Starts Omniflow's worker last; from now on Omniflow reconciles imported entitlements.
   After fifteen minutes, **/admin → System → Drift** should show nothing unexpected.

### Before the first broadcast

Bedolaga marks a user `blocked` only when one of its own broadcasts found the chat closed, and
many installations never ran one, so `blockedUsers: bot_blocked` usually carries few closed chats.
Run **Moderation → Scan now** once the final import is applied and let it finish: it asks Telegram
about every customer and marks the chats that are closed, which the campaign estimate and the
delivery passes then skip. Until a scan has completed after the last import, Omniflow refuses to
start or schedule a Telegram campaign (`blocker_scan_required`), so the first broadcast's blocked
share measures the message rather than the migration.

### Old buttons and old cabinet addresses

Customers' chats keep the previous bot's messages with their inline buttons. A tap on one sends
callback data Omniflow does not speak, such as `menu_buy`: the bot answers it, removes the dead
keyboard, and sends its main menu as a new message — the old message may be a photo, which cannot
be edited into a text screen. It is logged at `Info`, not as an error. An action button from an
older Omniflow release is answered the same way.

If the web panel takes over the previous cabinet's host, its addresses keep working: `/login` goes
to sign-in, `/subscription` to subscriptions, `/referral` to referrals, `/balance` to the wallet,
`/support` to support, `/buy/gift/<code>` to the wallet with the code filled in, and `/?ref=<code>`
to sign-in with the invite code held. Set `LEGACY_PATH_FALLBACK=/account` on the web service and
any other path the panel does not serve goes to `/account` rather than to a 404 (off by default).
`LEGACY_PATH_REDIRECTS` adds or changes entries; see [Configuration](/getting-started/configuration).

### Payments in flight at the cutover

A customer who opened a payment in Bedolaga a minute before step 2 and pays a minute after sends
the provider's notification to Omniflow, which never opened that payment. For YooKassa — the
previous bot's revenue — Omniflow does not refuse it. When the notification's metadata has
Bedolaga's shape (a `user_id`, or a guest `purchase_token`) and the last successful import run
finished less than 30 days ago, Omniflow fetches the payment through YooKassa's authenticated API and
acts on that answer, never on the notification:

- **A customer the import carried over** — the metadata's `user_id` is a Bedolaga user (or, in older
  payments, a Telegram ID), the `user_telegram_id` matches, and the account is open — is credited the
  amount to their wallet, the way Bedolaga would have topped up the balance. The wallet entry is an
  audited credit referenced `bedolaga-yookassa:<payment ID>` and is made once however often the
  notification arrives.
- **Anything else** — a landing or gift purchase, a user the import did not carry, a Telegram ID
  that does not match, a closed account — is queued, not dropped.

Either way the operator group's top-up topic gets a notice with the YooKassa payment ID, and the
payment appears in **/admin → Finance → Previous bot**. A queued payment stays there until an operator
deals with it — credits the right customer from their card, or refunds it in the YooKassa dashboard —
and resolves it with a note (`finance.write`). A payment that is not paid yet is ignored until its
`succeeded` notification arrives. Other providers' late payments are still refused; check their
dashboards for payments made in the first hours after the cutover.

A renewal made in Bedolaga between an earlier run and the final one is picked up by the final run:
an imported entitlement that Omniflow has not acted on yet moves to the new end date, and a balance
that changed gets its correction.

## Verification

`05-verify.sh` reconciles the source against Omniflow's own tables, not against the importer's
bookkeeping:

| Check | Passes when |
| --- | --- |
| nothing left to apply | A fresh plan has no write left |
| users | Every importable Bedolaga user has a customer holding their Telegram ID |
| balance sum | The carried-over movements of every customer sum to their Bedolaga balance |
| active subscriptions | Every active subscription has an entitlement on the same panel user ending at Bedolaga's end date |
| referral pairs | Every importable pair points at the right referrer |

Exit status `4` is a mismatch; the report names the first Bedolaga IDs that failed.

## Rollback

```bash
sh deploy/migration/07-rollback.sh
```

Because the importer never wrote to Bedolaga, Bedolaga's database is exactly as it was when it was
stopped. Rolling back stops Omniflow's worker and bot, counts what happened in Omniflow since
`cutover-at` (paid orders, new customers, wallet movements — set `OMNIFLOW_DB_CONTAINER`, or the
script prints the query), starts Bedolaga again (it registers its own webhook), and asks you to point
the payment providers back. Payments customers made in Omniflow after the cutover do not flow back:
credit them in Bedolaga by hand from that list.

Omniflow's imported data stays. Running `04-apply.sh` again later updates what changed rather than
importing twice.

## Running the importer by hand

```text
migrate-bedolaga plan   -mapping FILE [-json FILE]
migrate-bedolaga apply  -mapping FILE -confirm [-json FILE] [-limit N] [-actor NAME]
migrate-bedolaga verify -mapping FILE [-json FILE]
migrate-bedolaga runs
```

Exit status: `0` done, `1` error, `2` usage, `3` apply left failures or stopped at `-limit`, `4`
verify found a mismatch. `apply` refuses to run without `-confirm`. `-actor` is recorded on every
wallet adjustment's audit event and on the run.
