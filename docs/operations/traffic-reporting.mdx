`/admin/traffic` answers two questions that the anomaly signals cannot. Anomaly
detection answers "who should somebody look at". This answers **which node is
filling up** and **who consumed the most**, and it exports both.

## What is stored and what is not

Remnawave is authoritative for traffic, nodes, and connections. There is no
column anywhere for a byte a customer used — the reconciler records status,
expiry, traffic *limit*, and device limit, and deliberately not consumption.

So the live halves of this screen are read from the panel on every request, as
the boundary [decision 0004](/architecture/decisions#remnawave-boundary) exists
to hold requires. The one thing kept is an hourly sample of each **node's own**
counters, which Remnawave does not keep over time; it feeds the history card at
the bottom of the screen and nothing else. [Decision 0016](/architecture/decisions#traffic-history-is-an-observation)
records why that does not cross the boundary.

What Omniflow adds is the one thing it can: the join. A Remnawave user
identifier resolved to the customer who holds it, and a link to their profile.

## Nodes

Sorted by pressure — nodes with a limit first, by how close they are to it, then
the unlimited ones by absolute use. The question is "which node is filling up",
and the answer belongs at the top.

A node with **no limit reports no saturation figure** rather than 0%. It cannot
be filling up, and rendering zero would sort it among the empty ones when it
belongs off that list entirely.

<Warning>
  **A panel that does not expose a node listing says so.** `nodesReported` is
  false and the screen renders the reason — the route is unsupported, the panel
  could not be reached, or no Remnawave connection is configured.

  This distinction is the point. An empty node table and "we could not ask" look
  identical and mean opposite things, and a page of zeros for an installation
  whose nodes are fine is worse than an honest absence.

  Only the fields Omniflow renders are decoded, and a panel that omits one
  leaves a zero rather than failing the request. If your panel version shapes
  its node listing differently, this section degrades and the rest of the page
  is unaffected — confirm it against your own panel rather than assuming from
  this page.
</Warning>

## Heaviest users

The fifty largest consumers in the current cycle, with lifetime use beside the
cycle figure. Both, because "this month" and "ever" are different questions and
the second explains the first.

**The ranking says how far it looked.** Finding the heaviest users means
scanning every user, and the panel pages at five hundred; the report stops after
ten pages. When it did not reach the end, the screen says the ranking covers the
users it scanned out of the total the panel reports. A truncated ranking
presented as a complete one is worse than no ranking.

**A user Omniflow did not create reads as "not linked"**, not as an error.
Somebody provisioned it in the panel directly, or an import has not run, and
both are real states.

## The export

`GET /v1/panel/reports/traffic/export` returns one CSV with a `section` column —
`node` and `consumer`.

Byte counts are **unscaled**. A gigabyte is 1000³ to some readers and 1024³ to
others, and choosing one in an export makes the file wrong for the other half.
The screen renders binary units and labels them as such (GiB, not GB), because
the conversion it applies divides by 1024 and calling that a gigabyte would be
seven percent out at that scale — enough to stop an operator's arithmetic
reconciling against their host's invoice.

## Devices and subscription requests

Two more read-only cards sit on the same screen. **Devices** is Remnawave's own census
(`GET /api/hwid/devices/stats`): how many devices report each platform and which client applications
they use. **Subscription requests** takes a panel user ID and lists when, from which address, and by
which application that user's subscription was fetched (`GET /api/users/{id}/subscription-request-history`)
— the way to tell whether a link is being used somewhere it should not be. Both are read on each
request and stored nowhere.

There is no history of node usage over time on this screen, by the same rule: a node's figures are
Remnawave's, and keeping them in Omniflow would be the start of a second traffic ledger.

## Usage monitoring

Two optional worker passes watch what Remnawave already counts and tell operators in the **Usage
monitoring** topic. They change nothing in the panel and keep no traffic ledger: the only thing kept
between passes is the previous counter reading of every user, in Valkey with an expiry. Without
`APP_VALKEY_URL` the traffic passes stay off.

| Variable | Default | Meaning |
| --- | --- | --- |
| `APP_TRAFFIC_MONITOR_FAST_THRESHOLD_GB` / `APP_TRAFFIC_MONITOR_FAST_INTERVAL_MINUTES` | off / `10` | Every interval, report users whose `usedTrafficBytes` grew by at least this many gigabytes since the previous pass |
| `APP_TRAFFIC_MONITOR_DAILY_THRESHOLD_GB` | off | Once a day, the same over 24 hours |
| `APP_TRAFFIC_MONITOR_NODES` / `APP_TRAFFIC_MONITOR_IGNORED_NODES` | none | Node UUIDs: watch only users last connected through these, or leave users of these out (`lastConnectedNodeUuid`) |
| `APP_TRAFFIC_MONITOR_EXCLUDED_USERS` | none | Panel user IDs never reported |
| `APP_TRAFFIC_MONITOR_COOLDOWN_MINUTES` | `60` | How long a reported user is not reported again |
| `APP_DEVICE_OVERFLOW_REPORT` | `false` | Once a day, list users with more devices active in the last 30 days (`GET /api/hwid/devices`) than their `hwidDeviceLimit`; a limit of 0 is unlimited |

Disabled and expired users are skipped, and a counter that went down — a reset — is a new starting
point rather than a negative spike. The first pass of each kind only takes a reading. A notice names
the panel user IDs (at most 20, then a count), the window, and the threshold.

## Traffic history

**Traffic history** shows traffic per day across all nodes and, for each node,
the total over 7, 30, or 90 days, the daily average, the busiest hour's online
count, and its limit. The worker's `node_traffic_sample` pass records each
node's counters once an hour and prunes samples older than 400 days, so the
first day appears a few passes after deployment.

A node's counter accumulates within its cycle and drops back when the cycle
resets. A day's traffic is the sum of the positive steps between samples. A drop
to less than half the previous reading is a reset and counts the new reading as
the traffic since it; a smaller drop is the counter wobbling and counts as
nothing. Hours with no
sample — the worker or the panel was down — are covered by the next step. The
route is `GET /v1/panel/reports/traffic/history`; see
[Subscription and acquisition reporting](/operations/business-analytics#traffic-history).

## Public server status

`APP_SERVER_STATUS_ENABLED=true` publishes `/status` in the web app, backed by `GET /v1/status/servers`
on the API: every node the operator has not disabled in Remnawave, with its name, its country label, and
whether the panel reports it connected. It exists so a customer can tell whether a problem is theirs
before writing to support. It is read from `GET /api/nodes`, cached for a minute so a busy page is not
load on the panel, and stored nowhere. No address, traffic figure, or user count is shown. Off by
default; without it the route answers 404 and the page says the service does not publish status.

## Permissions

Both routes need `customers.read`. The half that matters names customers and
their consumption; the node figures are the less sensitive half and travel with
it.
