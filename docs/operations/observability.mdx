title: Health, metrics, and logs
description: The probes each process exposes, the metrics that are actually written, how logging and redaction work, and the real state of tracing
---

Omniflow's operational surface is deliberately small: three unauthenticated HTTP endpoints, one Prometheus registry per process, and structured JSON logs on stdout. Everything on it is designed for your orchestrator and your monitoring, and none of it belongs on the public API host — both bundled proxy examples return 404 for `/metrics` and `/readyz` on the API domain, because those endpoints answer questions about installation internals to anyone who asks. See [Reverse proxy](/operations/reverse-proxy).

This page describes what exists. Every metric in the registry is written somewhere, and the table below says where, because an alert built on a series that is never emitted is an alert that never fires.

## The three endpoints

| Endpoint | Answers | Use it for |
| --- | --- | --- |
| `/livez` | `200 {"status":"ok","version":"…"}` as soon as the process is serving | Liveness probe and restart policy |
| `/healthz` | The same handler, byte for byte | Compatibility with existing deployments |
| `/readyz` | `200 {"status":"ready",…}` or `503 {"status":"degraded",…}` | Readiness probe and load-balancer membership |

They are separate because they answer different questions. A process that is running but cannot reach PostgreSQL should be taken out of the pool, not killed and restarted — restarting it does not bring the database back, and a restart loop turns one failing dependency into no capacity at all.

<Note>
  `version` comes from the image. The release workflow passes `VERSION` to `build/go.Dockerfile`, which stamps it into `main.version` with a linker flag, so a released image reports its own version on `/livez`, in the diagnostics bundle, in the telemetry heartbeat, as the `version` label of `omniflow_build_info`, and as `service.version` on exported traces. A local `go build`, or a compose build that does not pass `VERSION`, reports `dev`.
</Note>

### Where each process listens

| Process | Variable | Default | Notes |
| --- | --- | --- | --- |
| `api` | `APP_HTTP_ADDR` | `:8080` | Always serves the probes, even with no database configured |
| `worker` | `APP_WORKER_HTTP_ADDR` | `:8081` | An empty value disables the listener entirely |
| `bot` | `APP_BOT_METRICS_ADDR` | *(unset)*; `:8083` in `compose.yaml` and `.env.example` | Unset means the bot serves **no** HTTP at all |

The reference `compose.yaml` and `.env.example` set `APP_BOT_METRICS_ADDR=:8083`, on the internal network and never published, so the bot has probes and metrics out of the box. If you run the bot some other way, set it yourself: with it unset, nothing can alert on the bot being down. It is ignored when it equals `APP_BOT_HTTP_ADDR`, the webhook listener's address: publishing metrics on the host Telegram reaches is refused rather than quietly allowed.

## Readiness

Readiness runs one probe per registered dependency and answers 503 while any of them fails.

| Process | Probes registered |
| --- | --- |
| `api`, with `APP_DATABASE_URL` set | `postgres` (`Ping`), `valkey` (`PING`), `remnawave` (authenticated call) |
| `api`, with no `APP_DATABASE_URL` | none |
| `worker` | `postgres` |
| `bot` | `postgres`, and only when a pool exists |

```json
{
  "status": "degraded",
  "checks": [
    {"name": "postgres", "healthy": true, "checkedAt": "2026-08-11T12:00:00Z", "latencyMs": 2},
    {"name": "valkey", "healthy": true, "checkedAt": "2026-08-11T12:00:00Z", "latencyMs": 1},
    {"name": "remnawave", "healthy": false, "error": "timeout", "checkedAt": "2026-08-11T12:00:00Z", "latencyMs": 3001, "consecutiveFailures": 4}
  ]
}
```

`error` is a stable classification and only ever `timeout` (the probe's context expired) or `unavailable`. The driver's own message is dropped on purpose: a pgx or HTTP error routinely contains a DSN, a host name or a credential, and an orchestrator logs this body verbatim.

`consecutiveFailures` counts unhealthy samples in a row and resets on the first success. It is the same counter automatic [maintenance mode](/operations/maintenance-mode) streaks on, so a readiness body tells you how close a dependency is to pausing purchases.

Results are cached for 2 seconds and each probe is bounded at 3 seconds, both compiled in. The cache exists so a burst of readiness requests cannot become a burst of database round trips.

The Remnawave probe is an **authenticated** call (`ListUsers` for a single record), which means an expired or revoked panel token reports as unavailability rather than passing as a healthy panel. See [Remnawave](/integrations/remnawave).

<Warning>
  An API started with no `APP_DATABASE_URL` registers no probes at all and answers `200 {"status":"ready","checks":[]}`. That is a green light for a process that serves only the four operational endpoints and nothing else. If a deployment mistake blanks the database URL, readiness will not catch it — check that `/v1/catalog` answers as well.
</Warning>

### The same picture in the panel

`GET /v1/panel/overview/health` (permission `system.read`) returns the identical `checks` list, so the panel and the load balancer can never disagree about whether PostgreSQL is up, plus payment-provider and digital-goods-provider status read from the database. The **System → Health** tab renders it and refreshes every 30 seconds. See [Admin panel](/operations/admin-panel).

## Service-level indicators

Every SLI below is built from a metric in the table further down this page.

| Surface | Indicator | Built from |
| --- | --- | --- |
| API | Availability: share of requests not answering `5xx` | `omniflow_http_requests_total{status="5xx"}` against the same series' total |
| API | Latency: request duration distribution | `omniflow_http_request_duration_seconds` |
| Bot | Update success: share of updates whose handler neither failed nor panicked | `omniflow_telegram_updates_total{outcome="handled"}` against the total |
| Bot | Outbound delivery: share of Bot API calls answered `ok` | `omniflow_telegram_sends_total` by `outcome` |
| Jobs (fulfillment) | Success rate | `omniflow_jobs_total{kind="fulfillment",outcome="succeeded"}` against the same series' total |
| Jobs (all kinds) | Success rate and duration per kind | `omniflow_jobs_total` and `omniflow_job_duration_seconds` by `kind` |
| Worker passes | Freshness: seconds since each pass last succeeded | `time() - omniflow_periodic_pass_last_success_timestamp_seconds` |
| Queues | Wait: age of the oldest job waiting to start | `omniflow_queue_oldest_available_seconds` |
| Remnawave | Error rate and latency per operation | `omniflow_remnawave_requests_total`, `omniflow_remnawave_request_duration_seconds` |
| Payments | Settlement health | `omniflow_payments_total` by `classification` — a rising `underpayment` or `wallet_unavailable` share is the signal, not a single threshold |
| Payments | Webhook trust | `omniflow_provider_webhooks_total{outcome="signature_invalid"}` — any non-zero rate is worth looking at |
| Backups | Age of the newest restorable backup | `time() - omniflow_backup_last_success_timestamp_seconds` |
| Fulfillment | Drift | Not a Prometheus series; read from the panel's fulfillment drift view — see [Jobs and queues](/operations/jobs-and-queues#fulfillment-jobs) |

Machine-readable alert rules and a starting Grafana dashboard built on these
same metrics are in [Reliability and operations](/operations/reliability#dashboards-and-alerts).

## Metrics

Each process builds its own isolated Prometheus registry, served at `GET /metrics` in the text exposition format alongside the standard Go and process collectors. Every series carries a constant `service` label of `api`, `bot` or `worker`.

Cardinality is bounded by construction. Routes are recorded as chi route **templates** such as `/v1/admin/orders/{orderID}`, never as concrete paths; HTTP status is bucketed to `2xx`, `4xx`, `5xx` or `unknown`; an unmatched request is recorded as `route="unmatched"`. Remnawave operations are the method and the path with every identifier replaced by `:id` (`POST /api/users/:id/actions/enable`), and a segment after `by-username` or `by-telegram-id` is always replaced, so a username never becomes a label. Bot API calls are labelled by method name only; the token in the request path is never read. No customer, order or payment identifier is ever a label, because a scrape target retains label values indefinitely and a metrics endpoint is rarely as well protected as an API.

### What is written

| Metric | Type | Labels | Written by |
| --- | --- | --- | --- |
| `omniflow_build_info` | gauge | `version` | Every process at start-up; always 1 |
| `omniflow_http_requests_total` | counter | `route`, `method`, `status` | Every HTTP request on any process that has metrics |
| `omniflow_http_request_duration_seconds` | histogram | `route`, `method` | The same middleware |
| `omniflow_telegram_updates_total` | counter | `kind`, `outcome` | The bot, once per update. `outcome` is `handled`, `failed` (the handler logged an error), or `panicked` (the bot recovered from a panic and kept serving) |
| `omniflow_telegram_sends_total` | counter | `method`, `outcome` | The bot's HTTP transport, once per Bot API call except the long poll. `outcome` is `ok`, `blocked` (403), `rate_limited` (429), `rejected` (400), `not_found`, `telegram_error`, or `unavailable` (no response) |
| `omniflow_jobs_total` | counter | `kind`, `outcome` | Every River job kind on the worker except the periodic kind: `fulfillment`, `goods_delivery`, and the rest. `outcome` is `succeeded`, `failed`, `cancelled`, `snoozed`, or `timeout`; the bot adds `kind="telegram.update"` |
| `omniflow_job_duration_seconds` | histogram | `kind` | The same jobs, and `kind="telegram.update"` from the bot |
| `omniflow_periodic_pass_runs_total` | counter | `pass`, `outcome` | Every periodic worker pass (`renewal`, `backup`, `payment_reconcile`, …), with `outcome` `succeeded`, `failed`, or `timeout` |
| `omniflow_periodic_pass_duration_seconds` | histogram | `pass` | The same passes |
| `omniflow_periodic_pass_last_success_timestamp_seconds` | gauge | `pass` | Set when a pass finishes without an error. Only the worker that ran the pass has the series, so take the `max` across replicas |
| `omniflow_queue_jobs` | gauge | `queue`, `state` | Every worker replica, every 15 seconds: River jobs per queue in `available`, `running`, `retryable`, `scheduled`, and `discarded` |
| `omniflow_queue_oldest_available_seconds` | gauge | `queue` | The same sample: how long the oldest job waiting to start has waited |
| `omniflow_outbox_pending_events` | gauge | — | The same sample: outbox events not yet dispatched |
| `omniflow_backup_last_success_timestamp_seconds` | gauge | — | The same sample: when the newest backup still on disk completed; 0 when there is none |
| `omniflow_remnawave_requests_total` | counter | `operation`, `outcome` | Every Remnawave call from the api, bot, and worker. `outcome` is `succeeded`, `not_found` (an ordinary lookup miss), or `failed` |
| `omniflow_remnawave_request_duration_seconds` | histogram | `operation` | The same calls |
| `omniflow_remnawave_errors_total` | counter | `code` | Failed Remnawave calls: `remnawave_http_<status>`, `timeout`, or `remnawave_unavailable` |
| `omniflow_provider_webhooks_total` | counter | `provider`, `outcome` | Payment webhook intake. `outcome` is `signature_invalid` for a rejected callback, otherwise the settlement classification below |
| `omniflow_payments_total` | counter | `provider`, `operation`, `classification` | Payment settlement. `classification` is one of `paid`, `late`, `underpayment`, `overpayment`, `currency_mismatch`, `wallet_unavailable`, `duplicate` |
| `omniflow_maintenance_mode` | gauge | — | The API's maintenance controller, on every sample |
| `omniflow_dependency_up` | gauge | `dependency` | Every `/readyz` call, and every maintenance sample on the API |

`omniflow_jobs_total` uses the job **kind**, so the fulfillment series is `kind="fulfillment"`. `fulfillment.operation` is the span name, not a label value, and querying for it matches nothing. Periodic passes are reported by pass name in their own series, not as `kind="periodic_task"`.

A pass that has not succeeded since the worker started has no last-success series. The bundled `OmniflowPeriodicPassFailing` rule covers that case from the run counter.

### Protecting `/metrics` on the API

The API serves `/metrics` on the same listener as the public API. Set
`APP_METRICS_TOKEN` and the route answers only to
`Authorization: Bearer <token>` — configure it as the scrape job's
`authorization` credential in Prometheus. Without a token the route stays open,
as in earlier releases, and the API logs a warning at startup; block the path at
the reverse proxy, as both bundled proxy examples do. The probes `/livez`,
`/readyz`, and `/healthz` are never gated. The worker and the bot serve metrics
on their own listeners, which are not meant to be published, and ignore the
token.

### Turning metrics off

`APP_METRICS_ENABLED` defaults to `true` and is read by the **api** and the **worker**: setting it to `false` leaves the metrics object unbuilt, which removes the `/metrics` route, the HTTP instrumentation middleware, the job and pass observers, and the queue sampler, while the probes keep working. The bot ignores it — it constructs metrics unconditionally and serves `/metrics` whenever `APP_BOT_METRICS_ADDR` is set to something other than the webhook address.

The metrics object is nil-safe throughout: every recording helper returns early on a nil receiver, so disabling metrics removes instrumentation rather than introducing a crash path.

### Alerts worth having

`deploy/observability/prometheus-alerts.yml` carries these as ready rules:

- **Processes:** `omniflow_build_info` absent for one of `api`, `worker`, `bot` for five minutes.
- **Dependencies:** `omniflow_dependency_up == 0` for longer than `APP_MAINTENANCE_FAILURE_STREAK × APP_MAINTENANCE_PROBE_SECONDS`, and maintenance mode open longer than a planned window.
- **Money passes:** `renewal`, `daily_billing`, `payment_reconcile`, or `commerce_maintenance` last succeeded more than fifteen minutes ago — customers are not being charged, or paid orders are not being picked up. Any pass whose every run in thirty minutes failed.
- **Backups:** the newest restorable backup is older than two days, or there has never been one.
- **Queues:** a job on the `critical` queue (fulfillment, digital goods) has waited five minutes to start; jobs were discarded in the last hour; more than 500 outbox events have waited fifteen minutes.
- **Jobs:** fulfillment or digital-goods delivery failing.
- **Remnawave:** more than 10% of calls failing, or p95 latency above three seconds.
- **Telegram:** the bot rate-limited for ten minutes, more than 20% of Bot API calls failing at the transport, any handler panic, or more than 10% of updates ending in an error.
- **Payments:** `underpayment` or `wallet_unavailable` settlements, and any `signature_invalid` webhook.
- **API:** sustained `5xx`.

## Structured logging

All three processes log JSON through `log/slog` with no handler options set, which means the default Info level: the API and bot write to **stdout**, the worker to **stderr**. There is no log-level, log-format or log-destination environment variable anywhere in the repository, so debug logging requires a code change. Collect the streams with your container runtime.

### Redaction

Anything that can reach a log line, an operator notification or a diagnostics bundle passes through a shared redactor first. It removes:

- Telegram bot tokens, and bearer, basic, token, API-key, secret, password and authorization values
- 13-to-19-digit runs, which is card-shaped
- `hwid`, `device_id`, `charge_id` and `invoice_payload` pairs
- **Any** URL in the `http`, `https`, `vless`, `vmess`, `trojan` or `ss` schemes, replaced entirely — even the host identifies the installation a customer connects to

Structured payloads are additionally redacted by key name, matching `token`, `secret`, `password`, `authorization`, `signature`, `api_key`, `hwid`, `subscription_url`, `checkout_url`, `raw_body`, `payload`, `card`, `pan`, `cvv`, `iban`, `email` and `phone`. It is applied to operator notification payloads before the row is written and to the last error on a job before it leaves the process.

The redactor is deliberately aggressive: an over-redacted log line is a minor inconvenience, while a leaked subscription link or bot token is a security incident.

### Classifications instead of messages

Most operational paths log a stable code rather than an error string, which is what makes them safe to log and searchable at the same time:

| Area | Codes |
| --- | --- |
| Health probes | `timeout`, `unavailable` |
| Remnawave | `remote_user_not_found`, `remnawave_http_<status>`, `remnawave_unavailable` |
| Backups | `command_exit_N`, `verification_failed`, `file_missing`, `cancelled`, `backup_failed` |
| Operator topics | `missing_manage_topics_permission`, `chat_not_found`, `forum_topics_disabled`, `bot_not_in_group`, `telegram_error` |

<Note>
  `/readyz` logs `readiness probe failed` with the number of checks and never which one failed. Read the response body, or scrape `omniflow_dependency_up`, to find out.
</Note>

### Correlation

`X-Request-ID` is generated by the first middleware in the chain and echoed on every response. Panel mutations store it on the audit event they write, so a support conversation about "what did this operator change" resolves to one request. The bot logs a `correlation_id` on payment paths, and fulfillment operations and their attempt history carry the same identifier, so one customer tap can be followed to the Remnawave call it caused.

## Tracing

Omniflow's code is instrumented with OpenTelemetry at these hops:

| Hop | Span | Attributes |
| --- | --- | --- |
| Inbound HTTP | `http.server` | `otelhttp` defaults |
| Telegram update | `telegram.update` | `messaging.system=telegram`, update kind, update ID; status `Error` when the handler failed or panicked |
| Fulfillment job | `fulfillment.operation` | `messaging.system=river`, job kind, attempt |
| Any other River job, including each periodic pass | `river.job` | `messaging.system=river`, job kind, attempt; status `Error` unless it succeeded or snoozed |
| PostgreSQL | one span per query | Statement text, trimmed into the span name |
| Outbound HTTP | `http.client` | Method and host only |

Span attributes follow the same rule as metric labels, enforced at a single entry point so no caller has to decide what is safe to record. A Telegram span carries the update ID, which correlates with the logs, but never the Telegram account. Query spans carry statement text and never argument values.

### Exporting traces

Tracing is off until you point it at a collector. Set the standard OpenTelemetry variable on each process you want traced:

```bash
OTEL_EXPORTER_OTLP_ENDPOINT=http://otel-collector:4318
```

With `OTEL_EXPORTER_OTLP_ENDPOINT` or `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` set, the process installs an OTLP/HTTP exporter at start-up and logs `trace export enabled`. The exporter reads the rest of the standard `OTEL_EXPORTER_OTLP_*` variables itself — headers for an authenticated collector, timeout, compression. Each process reports as `omniflow-api`, `omniflow-bot`, or `omniflow-worker` with `service.version` set to the build version.

By default one root trace in ten is sampled, and a child follows its parent's decision, because every query is a span and tracing all traffic would cost more than it tells. Choose another sampler with `OTEL_TRACES_SAMPLER` and `OTEL_TRACES_SAMPLER_ARG`, for example `parentbased_traceidratio` and `1.0` while chasing a problem. W3C trace context is propagated on outbound calls.

Without either endpoint variable the global provider stays a no-op and every span is discarded at no cost, as before.
