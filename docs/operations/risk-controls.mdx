title: Risk controls
description: External blocklists, anomaly detection, and accounts sharing a device — evidence for an operator, never an automatic sanction.
---

Omniflow can subscribe to external blocklists and can watch a handful of metrics
for values that look wrong. Both surfaces produce rows an operator reads.

One rule governs the whole area and is enforced in the schema, the service
layer, and the panel copy: **nothing here punishes a customer**. A match and a
signal are evidence. The adverse action, when there is one, is an ordinary
customer or finance mutation on the customer's own page, with its own
permission, its own mandatory reason, and its own audit event.

That is what makes automated detection safe to run at all: the worst a false
positive can do is cost an operator the time it takes to dismiss it.

## Blocklists

An operator configures a source: a display name, what its entries identify
(`telegram_id`, `email`, or `username`), an HTTPS URL, an optional authorization
header, and a refresh interval.

### What is stored

Only a digest. Each entry is kept as the SHA-256 of its normalised value, salted
by the kind it identifies. Three things follow.

Omniflow holds no readable copy of a third party's list, so it cannot leak or
republish one. A fingerprint from one installation means nothing in another. And
a lookup is still an exact index probe, which is the only kind of lookup a
blocklist needs.

Normalisation happens before hashing and is per kind. Telegram identifiers are
reduced to their canonical decimal form, usernames are lowercased with a leading
`@` or a `t.me/` prefix stripped, and an address is lowercased in the domain
only — lowercasing the local part or stripping dots is a provider-specific
convention that would make two genuinely different addresses collide.

### Refresh

A refresh replaces a source's entries wholesale inside one transaction, so an
entry the publisher removed stops matching in the same instant the new set
starts, and a refresh that fails part way leaves the previous list intact rather
than an arbitrary prefix of the new one.

Both a JSON array and a plain-text file of one value per line are accepted, and
the shape is decided from the first non-space byte rather than from a declared
content type — a list served with a careless `text/plain` still imports. A line
that does not normalise is skipped and counted rather than failing the refresh:
one malformed row in a third-party list must not leave an operator with a stale
blocklist and no explanation.

In a plain-text file, a line starting with `#` is a comment. Whatever follows the
value after a space, a tab, a comma, or a semicolon is the publisher's reason,
so `6923193113 #network scanning` and `6923193113,network scanning` both list
`6923193113`. The reason is kept, cut to 64 characters.

Saving a source in the panel fetches it at the next `lifecycle_sweep`, within
five minutes, instead of waiting out its interval.

A source publishing more than 500,000 entries is refused. A list that suddenly
grows that large is far more likely to be misconfigured or redirected than
genuinely that big, and importing it would replace a working list with garbage.

### Deciding a match

A match records the customer, the source, and the kind of identifier that hit.
An operator decides `allowed` or `blocked` with a mandatory reason, and their
identity is recorded, so an adverse decision can never be anonymous.

Re-detecting a match that has already been decided does not reopen it. The
allowlist goes further: an allowlisted customer is skipped entirely by the
check, which is what makes an operator's "this one is fine" survive the next
refresh of the source.

A blocked match can be appealed, which returns it to the review queue.

### Screening, and "check now"

Customers are screened by their active Telegram identifiers — the only
identifier Omniflow holds in a form a list can be matched against. After each
`lifecycle_sweep` that refreshed at least one source, the worker screens every
active or suspended customer against all enabled sources, a thousand
identifiers per lookup, so an identifier a publisher just added reaches the
review queue with the refresh that brought it.

Under **Risk → Blocklist matches**, an operator with `risk.write` can also run the screen
on demand: **Check this customer** for one customer ID, or **Check all
customers**. The panel reports how many identifiers were checked, how many new
matches were recorded, and how many operator accounts were skipped. The route
is `POST /v1/panel/risk/check` (an optional `customerId` in the body), and each
run writes the audit event `panel.blocklist.screened` with its counts.

### Operators are never flagged

A customer signed in with a Telegram account listed in
`APP_OPERATOR_TELEGRAM_IDS` is never screened: the scheduled screen, "check
now", and a direct check all skip it, and the anomaly rules skip it as a
customer subject too, so an operator testing purchases and refunds does not
raise a signal. The api and the worker read the same variable as the bot for
this. Operator panel accounts carry no Telegram link of their own, so an
operator whose customer account uses a different Telegram ID is exempted by
adding that ID to the variable, or by allowlisting the customer.

## Anomaly detection

Four metrics can be watched, each with its own rule:

| Metric | Measures |
| --- | --- |
| `purchase` | Paid order value per customer in the window |
| `refund` | Refunded value per customer in the window |
| `referral` | Qualified referrals per inviter in the window |
| `traffic` | Observed traffic on a subscription |

A rule carries a window, a warning threshold, an alert threshold, and a minimum
sample. Thresholds are in the metric's own unit — bytes for traffic, minor units
for purchase and refund, a plain count for referral — because converting them
would mean showing an operator a number they did not type.

`minimum_sample` is what stops a brand-new installation raising an alert on its
first three orders. A window with fewer observations than that raises nothing.

<Note>
  The traffic rule is a **level** check, not a rate. Remnawave owns traffic and
  Omniflow holds only the counter it last observed, so the rule flags a
  subscription whose observed usage has passed a threshold, not one whose usage
  grew quickly. The rule's window controls how often such a subscription is
  re-raised, not what is measured.
</Note>

### Deduplication

A condition that persists across several evaluation runs is one signal, not one
per run. The dedupe key is the metric, the subject, and the window bucket the
observation falls in, so a customer who stays above a threshold for six hours
produces one alert per window rather than one per sweep. A signal an operator
has already reviewed stays reviewed when the same condition is observed again.

### Evidence

Each signal carries the numbers that produced it — counts, sums, the currency,
the window — and never a message body, a link, a token, an address, or any other
customer content. An operator reviewing a signal needs to see why it fired,
which is arithmetic, not correspondence.

### Notifications

A raised signal is queued to the `anomaly` operator topic in the same
transaction that persists it, so an alert cannot be announced for a signal that
was rolled back. The notice names the metric, the severity, and the numbers. It
does not name the customer: an operator group is a chat, and the panel is where
somebody with the permission looks the subject up.

## Shared devices

A second account on the same phone is how a trial is taken twice and how a
customer invites themselves for the referral reward. Remnawave already records
which devices (HWIDs) connected through each subscription; Omniflow reads that
list and puts every device seen on two or more customers in front of an
operator under **Risk → Shared devices**.

### What is stored

Only the device's handle: a digest of the HWID, the same one a customer's own
device list uses. The hardware ID itself never leaves the Remnawave adapter.
Omniflow keeps one sighting per device and customer — the platform the client
reported and when the device was first and last seen — and forgets a sighting
when the device has not connected for 180 days. Anonymising a customer deletes
their sightings at once.

A device the client never reports a HWID for is not seen at all, so the check
covers only clients that send one, and only while Remnawave's HWID device
limit is enabled. A HWID can be spoofed: the absence of a match proves nothing.

### The scan

The worker's `shared_device_scan` pass pages through `GET /api/hwid/devices`,
maps each panel user to its customer through the subscription (or the imported
`remnawave_users` link), and folds several subscriptions of one customer on one
phone into a single sighting — two subscriptions of the same person are not two
accounts. Deleted and merged customers are left out, and so are customers
signed in with a Telegram account listed in `APP_OPERATOR_TELEGRAM_IDS`.

A device seen on two or more customers becomes a row in the queue with the
number of accounts, how many of them took a trial, and how many invited
another account on the same device. When a scan adds devices to the queue, the
**monitoring** operator topic gets one notice with how many: never which
customers, because the chat is not where a customer is looked up.

### What it changes on its own

Two things, both reversible by an operator and both shown to whoever they
affect:

- **Trials.** A customer whose device already carried another customer's trial
  is refused one with the reason `device_already_trialled`, shown in their
  language with a pointer to support. The check runs when the trial is claimed,
  so it catches the next account on a device that has already been seen; the
  first connection of a brand-new account is only seen by the next scan.
- **Referrals.** An invited customer on the inviter's device gets the referral
  signal `shared_device`, which moves the pair from `clear` to `held` for review
  and counts toward the withdrawal risk score. Nothing is rejected and no reward
  is taken back automatically; see
  [Referral review](/commerce/referrals-loyalty#signals-ask-for-a-person-they-never-punish).

### Deciding a device

A family on one tablet looks exactly like a second account, so the verdict is a
person's. The queue filters by status and by size — **More than 2 accounts**
shows only the devices with three or more. With `risk.write`, an operator
decides an open device in one of two ways.

**Legitimate** — a family or a shared phone. No reason is needed, because
lifting a hold is not an adverse decision. The device stops refusing trials
and stops holding referrals.

**Ban** (with `customers.write` too) opens a dialog:

- **Accounts** — which customers on the device to ban. Every one except the
  first seen on the device is ticked to begin with, since the first is usually
  the original.
- **Reason** — one of the ban templates: *Several accounts on one device*,
  *Account sharing*, *Payment fraud*, or *Breaking the rules*. It is recorded on
  each customer as `shared_device:<reason>`.
- **Ban length** — 1, 7, 30 or 90 days, or no end. A timed ban is lifted by
  the worker's `lifecycle_sweep` once it runs out, with the lifecycle event
  `restored` (reason `ban_expired`) and the audit event `customer.ban_expired`.
  Restoring the customer by hand ends it at once.
- **Send the customer the reason** — the reason's template goes to the customer
  as a message.
- **Annul subscriptions** (needs `subscriptions.write`) — every running
  subscription of each banned customer gets a `disable` through the
  fulfillment pipeline, the same change as disabling it on the customer page.
  They stay disabled after the ban ends.

Each banned customer goes through the same suspension as the customer page —
lifecycle event, audit event `panel.customer.suspended` — and the device is
recorded as banned, with `panel.shared_device.banned` in the audit log.

Either verdict covers the customers on the device at the time. Another customer
joining the device reopens it, and the earlier verdict stays on the row so the
operator sees what was decided for fewer accounts.

The routes are `GET /v1/panel/risk/shared-devices` (`status`, `minAccounts`,
`customerId`, cursor) with `risk.read`,
`POST /v1/panel/risk/shared-devices/{handle}/review` with `risk.write`, and
`POST /v1/panel/risk/shared-devices/{handle}/ban` with `risk.write` and
`customers.write`. Open devices count toward the number beside **Risk** in the
panel menu.

## When any of this runs

Both surfaces are driven by `internal/sweeper` in the worker process, not by a
request. Its passes run as River periodic jobs — `lifecycle_sweep` and
`anomaly_evaluation` — so each runs once per interval however many worker
replicas are up, and each is idempotent, so a pass that runs twice reaches the
same state as one that ran once. See
[Jobs and queues](/operations/jobs-and-queues#periodic-passes-and-in-process-loops).

| Pass | Cadence |
| --- | --- |
| Gift and personal-offer expiry, and lifting timed bans | Every `lifecycle_sweep`, five minutes |
| Blocklist refresh | Every `lifecycle_sweep`, but only for sources whose own interval has elapsed |
| Blocklist screen of all customers | After a `lifecycle_sweep` that refreshed a source, and on demand |
| Anomaly evaluation | Its own `anomaly_evaluation` pass, fifteen minutes |
| Shared-device scan | Its own `shared_device_scan` pass, every three hours, run by the worker's Remnawave monitoring |

Anomaly evaluation runs on its own cadence because it aggregates over the orders
table, and a persisting signal is deduplicated by window — running it more often
produces no extra alerts, only extra work.

A failing pass never stops the others. A publisher being unreachable must not
prevent gifts expiring, and a rule that cannot be evaluated must not stop a list
refreshing. Each blocklist source is independent for the same reason: one being
down leaves the others refreshed and leaves the failing source's previous
entries intact, rather than emptying a list nobody could replace.

## Editing thresholds and sources

Both are edited in the panel under **Risk**, with `risk.write`.

The threshold form applies the same coherence rule the evaluator does — an alert
threshold at least the warning threshold, and a window of at least five minutes
— so a rule that would be silently skipped at evaluation time is refused at save
time instead. Each field states the unit it is in.

The source form is HTTPS-only, and an empty authorization header means "keep
what is stored", so re-saving a source never echoes its credential back into the
browser. That holds only while the URL is unchanged: saving a new URL without
re-entering the header is refused with `422 secret_required`, because a header
entered for one publisher must never be sent to another.

The worker downloads a source only from a **public** address. Loopback, private,
link-local (which includes cloud metadata), and the other non-public ranges are
refused at connect time, after the hostname has been resolved, and again for
every redirect — which must also stay on HTTPS. A source refused this way is
marked failing with the error code `destination_refused`, distinct from
`unreachable`, so the panel shows that the address itself is the problem.

## Permissions

`risk.read` reads sources, matches, rules, and signals. `risk.write` decides a
match, appeals one, manages sources and rules, and edits the allowlist.

Every role that holds `risk.write` also holds `customers.read`, which is
asserted by a unit test: a role that could decide a match without being able to
read the customer would be deciding blind.
