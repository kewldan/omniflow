description: Plan-scoped squad sets, add-on versions, mid-period capacity, and the proration rules behind each price

Two things let a customer shape a subscription beyond picking a plan: choosing which squads it uses, and buying extra capacity part-way through a period.

Both are authored on the plan version, both are validated on the server rather than in the interface, and both end up folded into a single entitlement so that Remnawave receives one desired state rather than a plan followed by a correction.

## Plan-scoped squad sets

A plan version carries two squad collections:

- `remnawave_squad_ids` — always assigned to every subscription on that plan;
- `plan_version_squads` — the selectable set, each row carrying a Russian and an English label and a sort order.

`squad_selection` decides what the customer may do:

| Value | Behaviour |
| --- | --- |
| `automatic` | Squads are assigned from the plan. A submitted selection is refused. |
| `optional` | The customer may add squads from the offered set, within `max_selectable_squads`. |
| `required` | The customer must pick at least `min_selectable_squads`, and at least one. |

An empty value behaves as `automatic`, and any value outside the three is refused outright rather than guessed at.

The final squad set for the entitlement is the included squads plus the accepted selection, deduplicated and sorted. Sorting matters: two customers who pick the same squads in a different order must produce byte-identical entitlement state, otherwise drift detection would report a mismatch that is not real.

A selection is validated against the plan on the server. Callback data naming a squad the plan does not offer is refused with `squad_not_offered`, so a crafted callback cannot attach a squad the customer never paid for.

The configurator only appears when a plan actually offers a choice. A plan with `automatic` selection goes straight from the plan screen to payment, exactly as before.

### The refusals in full

| Reason | Raised when |
| --- | --- |
| `squad_selection_not_allowed` | The plan assigns squads automatically, or the stored selection mode is unrecognised |
| `squad_selection_required` | The plan requires a choice and nothing was chosen |
| `squad_not_offered` | A submitted squad is not in the version's offered set |
| `squad_selection_too_few` | Fewer than `min_selectable_squads` were chosen |
| `squad_selection_too_many` | More than `max_selectable_squads` were chosen |

All five wrap one domain error and surface as HTTP 422 with the reason as the RFC 9457 `type`, which both customer surfaces translate into their own copy.

One more check runs before anything is charged: every squad the order would grant — the plan's own, the chosen ones, and a squad add-on's — must still exist in the Remnawave panel. The api and the bot read the panel's internal squads (`GET /api/internal-squads`, cached for a minute) and refuse a squad it no longer has with HTTP 422 `squad_unavailable` and a matching bot message. A panel that does not answer does not block the sale: the check is there to catch a squad an operator deleted, and an outage is what fulfillment retries are for. An automatic renewal is never refused this way.

The database backs the bounds up: `min_selectable_squads` at least 0, `max_selectable_squads` above 0 when set, a named cross-column check requiring the maximum to be at least the minimum, and labels of 1–80 characters in each language.

### The server catalogue

**Servers** on the catalogue page is how Omniflow labels and limits the sale of each Remnawave internal squad, as Bedolaga's server list does — without managing the squad or its nodes, which Remnawave keeps ([decision 0004](/architecture/decision-0004-remnawave-boundary)). It lists the panel's internal squads with their member count, read live and never stored, beside each one's catalogue entry (`GET /v1/panel/catalog/servers`, `catalog.read`). An entry (`PUT`/`DELETE /v1/panel/catalog/servers/{squadID}`, `catalog.write`, audit `panel.server.saved` and `panel.server.deleted`) holds:

| Field | What it does |
| --- | --- |
| Name in each language | The catalogue's own name for the squad |
| Country | Two letters shown as a flag in front of the squad's label wherever a customer chooses squads, in the bot and on the web |
| Customer limit (`maxUsers`) | The most customers a sale may put on the squad, counted as customers with a live entitlement on it. At checkout a full squad is refused with `squad_full` to a customer not already on it; a renewal, and a customer already on it, are never refused |
| Price for choosing it (`prices`) | What choosing the squad in the configurator adds to the plan's price, per currency, for the version's own duration and scaled to the period bought. A squad the version includes for everyone is never charged. Loyalty and promo discounts do not apply to it |
| Trials may use it | A trial order keeps only the squads open to trials; one left with none is refused with `squad_unavailable` |

The screen also shows Omniflow's count of live customers on each squad against its limit, and flags a catalogued squad the panel no longer has. A squad without an entry is sold exactly as before. An automatic renewal keeps the squads the customer chose last time that the version still offers, and prices them the same way, so a chosen server costs the same on every renewal.

### Choosing squads at checkout

*Web.* On `/account/checkout`, a **Servers** fieldset appears only when the plan reports the selection as configurable. Each checkbox sends `PATCH /v1/account/checkout` with the whole `squadIds` array, and the server re-prices and returns the entire checkout. The bounds the page shows are guidance only: the real check runs at order creation, because a second implementation of the same counting rule in React is exactly what would eventually let through a set the order then refuses.

*Telegram.* Choosing a payment method opens the squad configurator first when the plan is configurable, and each `squad:` callback toggles one squad.

`GET /v1/account/plans/{planVersionID}` returns the whole picture as `squads` with `selection`, `minimum`, `maximum`, `configurable`, and the offered list. The confirmed set is stored on the order in `selected_squad_ids`; if it is empty, settlement falls back to the plan version's own set.

A choosable squad set is authored in the plan version editor at `/admin/catalog`: set **Squad selection** to `optional` or `required`, add a row per squad under **Squads the customer chooses from**, and give each a Russian and an English label. The squads are picked by name from the live Remnawave list. [Catalog and promotions](/commerce/catalog-promotions) has the full version editor reference and what publishing refuses.

## Add-ons

An add-on adds capacity to a subscription. It can be bought two ways:

- **With the plan**, at checkout or in a saved cart. It is charged on the same order, so one confirmation is one payment, and it covers the whole first period at the catalog price.
- **Mid-period**, against a live entitlement. It is charged on its own order, with `operation = 'addon'`, and priced with its version's proration rule against the time the period has left.

Three kinds exist:

| Kind | Adds |
| --- | --- |
| `traffic` | Bytes on top of the entitlement's allowance |
| `devices` | Device slots on top of the entitlement's limit |
| `squads` | Additional Remnawave squads |

An add-on is offered only for plan versions that list it in `plan_version_addons`. Buying one against a plan that does not offer it is refused with `addon_unavailable`. That join is not only curation: the add-on identifier arrives in customer-controlled callback data or a URL path, so the join is the check that stops a customer attaching an add-on to a plan it was never priced for. An identifier that is not even a UUID is treated the same way rather than as a parse error.

### Versioned pricing

Add-ons are versioned exactly like plans. The add-on row carries presentation and is mutable; the version carries what the customer gets and what it costs, and is not. `addon_versions` is immutable once an order references it, and `order_addon_lines` stores a snapshot of the version's capacity, price, and proration rule at purchase time. Changing an add-on's price creates a new version; it never rewrites a historical order.

### Authoring an add-on

<Steps>
  <Step title="Open the catalogue">
    Go to `/admin/catalog` and switch to the **Add-ons** tab. The list shows the
    code, a kind badge, the current version as `v{n}`, and a Visible or Hidden
    badge. It is read-only — there is no edit or retire control on a row.
  </Step>
  <Step title="Describe it">
    Press **New add-on**. Fill Code, Kind, Name (EN), Name (RU), and the
    kind-dependent payload: Traffic in GB, Device slots, or a comma-separated list
    of squad IDs. Traffic is converted to bytes in the browser before it is sent.
  </Step>
  <Step title="Price it and bound it">
    Set Maximum quantity, the mid-period pricing rule, and Prices in the same
    `RUB=19900, USD=299` form the plan editor uses. Flip **Visible** and type a
    reason.
  </Step>
  <Step title="Save">
    Submitting calls `PUT /v1/panel/catalog/addons` (`catalog.write`) and returns
    the add-on ID. Audit `panel.addon.saved`.
  </Step>
</Steps>

Saving an existing code upserts the add-on row — visibility and sort order only — and **publishes a new version every time**. There is no in-place edit, for the same reason plans have none: a historical order must keep costing what it cost.

What the save refuses, all with 422:

- A missing code, or a code that does not match `^[a-z][a-z0-9_-]{1,63}$`;
- A proration rule outside the three known ones;
- A maximum quantity below 1;
- No prices at all;
- A `traffic` add-on with no traffic, a `devices` add-on with no slots, a `squads` add-on with no squads, or any other kind;
- A name missing in either language. A missing translation is refused rather than stored blank, because an add-on with no name in one language is an empty row on the customer's screen.

Retiring a version is `POST /v1/panel/catalog/addon-versions/{addonVersionID}/retire` (`catalog.write`, audit `panel.addon_version.retired`). Retiring one that is already retired matches no row and answers 404. There is no retire control in the panel either.

<Note>
  The add-on offer set on a plan version is written from the `addonIds` array
  on `POST /v1/panel/catalog/plans/{planID}/versions`, and publishing
  **replaces** that set rather than merging it. The version editor at
  `/admin/catalog` lists the add-ons as checkboxes and starts from the previous
  version's set, so a new price keeps the add-ons the plan already offered.
</Note>

The offer check matches by add-on rather than by add-on version, so any live version of an offered add-on qualifies once the add-on is listed.

### Buying add-ons with the plan

*Web.* `/account/checkout` renders an **Add-ons** section when the plan version offers any. Each entry is a toggle button; tapping it calls `POST /v1/account/checkout/addons/{addonVersionID}`, which toggles the line at quantity one and returns the whole re-priced checkout. The quote breakdown then reports `addonMinor` separately from `subtotalMinor` and `discountMinor`, because a customer told only what they owe cannot tell a promotion from an add-on, and the two have very different consequences if either is wrong.

*Telegram.* The checkout screen grows an add-ons button when the plan offers any; the list toggles one entry per tap.

Toggling an add-on the plan does not offer answers 404 `plan_unavailable` on the web and "that add-on is no longer available" in the bot. An archived add-on, a retired version, or one with no price in the order currency is refused with `addon_unavailable`.

<Note>
  A promo code discounts the **plan price only**. The subtotal is the plan price
  plus the add-on total, but the discount is computed against the plan price
  alone, so a percentage off never eats into add-on capacity.
</Note>

### Buying add-ons mid-period

*Telegram.* Subscriptions → pick one → **Add-ons** → tap an add-on. The purchase becomes its own order at quantity one; the wallet settles it when the balance covers it, and otherwise the ordinary payment screen appears.

*Web.* `/account/subscriptions/{id}` lists the add-ons the subscription's plan offers under **Add to this subscription**, each with what it costs now under its proration rule — `GET /v1/account/subscriptions/{subscriptionID}/addons`. **Add** calls `POST` on the same route with `addonVersionId`, `quantity`, and an `Idempotency-Key` header, which opens the same order the bot does. The wallet settles it when it covers the price; otherwise the customer is taken to the order page and pays the rest through a provider. A repeated request with the same key resolves to the same order.

A mid-period purchase refuses with:

| Refusal | Raised when |
| --- | --- |
| `no_active_subscription` | The target subscription has no live entitlement — "add-ons can only be bought for an active subscription" |
| `ErrSubscriptionUnknown` | The subscription is not this customer's |
| `ErrAddonQuantity` | Quantity is zero or below, or above the version's `max_quantity` |
| `ErrUnsupportedProration` | The stored proration rule is not one this build knows |
| `addon_unavailable` | Archived, retired, unpriced in the order currency, or not offered for that plan |
| `addon_not_applicable` | It would grant nothing: traffic on unlimited traffic, or slots on unlimited devices |

Maintenance blocks the purchase entirely, like any other order. Reusing an idempotency key with different add-on parameters is refused rather than silently resolved to the earlier order. The same add-on twice in one order is refused outright.

#### Buying after a top-up

An add-on the wallet cannot cover can be saved instead of paid through a provider, as Bedolaga's add-on cart does, and is then bought by itself once a top-up covers it. In the bot the confirmation screen shows **🛍 Buy after a top-up** whenever the wallet falls short; on the web the add-on list shows **Buy after a top-up** beside **Add**, which calls `PUT /v1/account/subscriptions/{subscriptionID}/addons/cart` and takes the customer to the wallet. The saved add-on is the customer's one open cart — it replaces a saved plan or shop item — with kind `addon`, the subscription it attaches to, and the price the customer was shown. The add-on list then carries it as `cart`, with what it costs now and what the wallet still lacks, and **Discard** (`DELETE` on the same route) drops it; in the bot it is the ordinary saved-cart screen.

Settling a top-up, and the periodic cart sweep, open the add-on's order under the cart's own idempotency key only when the wallet covers all of it, so a short wallet opens nothing and a duplicated top-up or a sweep racing the settlement buys it once. The order is never more than the saved price: a mid-period price only falls as the period runs on, and a rise — the operator changed the catalog — is refused with `cart_price_changed` and switches the cart's automatic purchase off, as is an add-on or subscription that can no longer take it (`cart_plan_unavailable`). [Saved carts](/commerce/wallet-topup-cart#saved-carts) covers the rest of the cart's lifecycle.

### Paid traffic reset

A plan version may sell a reset of the traffic counter before the period ends, as Bedolaga's paid traffic reset does. **Paid traffic reset (% of the price)** in the version editor (`trafficResetPriceBps`, basis points of the version's own price in the order currency, rounded up) turns it on; empty sells none. A subscription on such a version with limited traffic shows **Reset traffic** on its page — `GET /v1/account/subscriptions/{subscriptionID}/traffic-reset` prices it and `POST` on the same route, with an `Idempotency-Key`, opens an order with operation `traffic_reset`. The wallet settles it when it covers the price; otherwise the order page takes the rest. Settlement queues one `reset_traffic` operation keyed `order:<id>:reset`, so a replayed settlement resets once. In the bot the same subscription shows **🔄 Reset traffic · price** on its screen; the button opens a confirmation with the price and whether the wallet covers it, and confirming opens the same order (keyed `bot-reset:` plus the tap) and, when the wallet falls short, the payment-method choice. The period's end does not move. A version that sells no resets, unlimited traffic, and a paused or lapsed subscription answer `traffic_reset_unavailable` or `no_active_subscription` before any money moves.

### Changing the traffic package

A subscription with limited traffic may switch its traffic package to a bigger or a smaller one part-way through the period, as Bedolaga's package change does. A *package* is a `traffic` add-on the plan version offers; the subscription's current package is every traffic pack still counting on its live entitlement.

*Web.* `/account/subscriptions/{id}` shows **Traffic package** when there is something to switch to: what the current packages add, and each package the plan offers with **Increase** or **Decrease**, plus **No package** when one is attached. Choosing one shows the preview in place — the new package's price for the time left, the unused part of what it replaces, what the wallet covers, what is left to pay, and what goes back to the wallet — and **Confirm** commits it. `GET /v1/account/subscriptions/{subscriptionID}/traffic-package` returns the options, each with a quote; `POST` on the same route with `{"addonVersionId": …}` (omitted for none) and an `Idempotency-Key` opens the order.

*Telegram.* The subscription screen shows **📶 Traffic package** with the same list; a package opens the same preview, and confirming opens the same order (keyed `bot-traffic:` plus the tap) and, when the wallet falls short, the payment-method choice.

The arithmetic:

```text
charge = the new package's price under its own proration rule, for the time the period has left
credit = Σ over the packages it replaces: what was paid for the pack × time it had left ÷ time it would have counted
```

A pack's *what was paid* is its line's charge, scaled down by whatever share of its order was not paid (a discount, a refund); a pack bought for the customer by somebody else — a gift — is released with nothing handed back. A pack with a lifetime counts until its lifetime ends, or the period's end if that is sooner. The credit is rounded down.

The change is one `traffic_change` order whose subtotal is the charge. Its [credit line](/commerce/orders-payments#credit-lines) records the packs it releases and their remainder, which reaches the wallet when the order settles and is spent by it first: a bigger package costs the charge less the credit, and a smaller one costs less than the credit and leaves the difference in the wallet. Settlement then releases the old packs (`entitlement_addons.released_at`, by this order), takes exactly what they added off the entitlement, applies the new pack, and queues one `set_limits` keyed `order:<id>:change`, in the paying transaction. A released pack no longer counts towards the allowance, towards **Most traffic add-ons may add**, or towards the lifetime sweep. The credit is posted only while every pack it hands back is still counting on the subscription's current entitlement, so two changes racing for the same pack hand it back once.

The period's end does not move, and the traffic counter is not reset: a smaller package can leave a customer who already used more than it allows `LIMITED` until the next period or a reset. Changes are priced at the catalogue's prorated price, without a loyalty discount or a promo code.

| Refusal | Raised when |
| --- | --- |
| `traffic_change_unavailable` | The subscription has unlimited traffic, or nothing to switch to |
| `capacity_change_same` | The new package adds exactly what the current ones do |
| `no_active_subscription` | No live entitlement, a paused one, or one scheduled to start later |
| `addon_unavailable` | The package is not offered, retired, unpriced in the currency, or not a traffic package |
| `addon_limit_reached` | The new package would go past **Most traffic add-ons may add** |

### Proration rules

The proration rule is a property of the add-on version, and it is always explicit. Omniflow never infers a partial price from remaining time unless the add-on says so. It applies only to a mid-period purchase; an add-on bought with the plan covers a full period and is charged at the catalog price whatever its rule says.

| Rule | Charge | Suited to |
| --- | --- | --- |
| `full_price` | The catalog price, whatever remains of the period | Capacity that does not decay, such as device slots |
| `remaining_period` | Catalog price × remaining ÷ total, rounded up to the next minor unit | Traffic, where value scales with time |
| `daily_rate` | Catalog price ÷ whole period days, rounded up, × remaining days, rounded up, capped at the full price | Add-ons an operator prices per day |

Three properties hold for every rule, and each has its own unit test:

1. A prorated charge never exceeds the catalog price.
2. Rounding is always up, so a partial period never rounds to nothing.
3. A purchase made before the period starts, or against a period with no remaining time, falls back to the full price. Charging zero for capacity that will still be delivered would give it away.

The intermediate multiplication is done in 128 bits. A long period and a large price would overflow a 64-bit product and produce a nonsensical charge.

### Applying an add-on

Settlement folds the purchased capacity into the entitlement itself before the desired provisioning state is computed, so Remnawave receives one combined result rather than a plan followed by a correction:

```text
entitlement.traffic_allowance_bytes += Σ traffic × quantity
entitlement.device_limit            += Σ slots × quantity
entitlement.remnawave_squad_ids      = existing ∪ add-on squads
```

An entitlement with an unlimited allowance stays unlimited: the update leaves a null traffic allowance or device limit null, because adding capacity to "no limit" is meaningless. An add-on that would grant nothing is therefore never sold. A traffic add-on on a subscription with unlimited traffic, or a device add-on on one with unlimited devices, is left out of the offer on the web and in the bot, and an order for it — bought with the plan or mid-period — is refused with `addon_not_applicable` before any money moves. An add-on applies when at least one thing it carries lands: traffic on a limited allowance, slots on a limited device count, or any squad. The check reads the plan version for a purchase and the live entitlement for a mid-period add-on.

A version whose [traffic mode](/commerce/catalog-promotions#traffic-modes-and-packages) is `fixed` sells no traffic add-on at all, even one it lists: the offer on the web and in the bot leaves them out, and an order for one — with the plan, mid-period, or from a saved add-on purchase — is refused with `addon_unavailable`.

Squads are a set and are never multiplied by quantity. Buying two of the same squad add-on charges twice and grants the same squads once, which is why `max_quantity` on a squad add-on should be 1.

### Caps and pack lifetime

Three limits bound what add-ons may add, and each is checked at order creation, before any money moves, for add-ons bought with the plan and mid-period alike. A refusal is `addon_limit_reached` on the web and a matching message in the bot.

| Limit | Where it is set | Effect |
| --- | --- | --- |
| Most devices per subscription | Settings → Commerce → Plan changes and resets (`maxDeviceLimit`) | Device add-ons cannot take a subscription's device limit past it. An unlimited device count has nothing to cross |
| Most traffic add-ons may add | The plan version editor (`maxAddonTrafficBytes`) | The traffic of every pack still counting on the entitlement, plus the new one, may not exceed it |
| Pack lasts (days) | The add-on editor, traffic add-ons only (`lifetimeDays`) | The pack stops counting that many days after it is applied |

A pack with a lifetime gets `entitlement_addons.expires_at` when it is applied. The commerce maintenance pass the worker runs takes every pack past it back off its entitlement — the allowance is lowered by exactly what the pack added, never below zero — and queues a `set_limits` operation keyed `addon:<pack id>:expire`. The pack is marked `expired_at` in the same transaction, so a replayed pass subtracts nothing. A paused entitlement keeps the lower allowance in its row and its resume pushes it. A pack without a lifetime lasts as long as the entitlement it was added to, as every pack did before.

Every priced line is snapshotted onto `order_addon_lines` with the code, kind, version, traffic, slots, squads, proration rule, and period end, so an order explains itself years later without reading the catalogue.

### Idempotent fulfillment

`entitlement_addons` is unique on `(order_id, addon_version_id)`. A replayed settlement finds the row already present, skips it, and leaves the entitlement untouched. Only lines that were actually inserted contribute to the totals, so a partial replay cannot double-count.

A mid-period add-on order enqueues its own fulfillment operation keyed `order:<order id>:addon`, carrying the `set_limits` operation for the combined result, and the order moves to `fulfilled`. An add-on bought with the plan needs no separate operation: it is already part of the entitlement the plan's own `create` operation provisions. [Fulfillment](/commerce/fulfillment) covers what happens to that operation next.

### When there is nothing to attach to

If the target subscription has no live entitlement by the time an add-on settles, the money is not lost and nothing is rolled back. The order stays `paid`, an `addon.no_active_entitlement` audit event is written in the `financial` category with a failure outcome, and an operator notification of kind `fulfillment_failure` is queued, deduplicated on the order. Rolling back a recorded payment would be worse than leaving an operator a clear task — nothing here may roll back money that has already been taken.

## API reference for this area

| Route | Auth | Purpose |
| --- | --- | --- |
| `GET /v1/panel/catalog/addons` | `catalog.read` | List add-ons |
| `GET /v1/panel/catalog/addons/{addonID}/versions` | `catalog.read` | Version history for one add-on |
| `PUT /v1/panel/catalog/addons` | `catalog.write` | Create an add-on or publish its next version |
| `POST /v1/panel/catalog/addon-versions/{addonVersionID}/retire` | `catalog.write` | Retire one version |
| `POST /v1/panel/catalog/plans/{planID}/versions` | `catalog.write` | Publish a plan version, including its `addonIds` offer set |
| `GET /v1/account/plans/{planVersionID}` | Customer session | The squad offer and the add-on offer for one version |
| `PATCH /v1/account/checkout` | Customer session | Submit a squad selection |
| `POST /v1/account/checkout/addons/{addonVersionID}` | Customer session | Toggle one add-on on the open checkout |
| `GET /v1/account/subscriptions/{subscriptionID}/addons` | Customer session | The add-ons a live subscription may add, priced for the time left |
| `POST /v1/account/subscriptions/{subscriptionID}/addons` | Customer session, `Idempotency-Key` | Buy one mid-period add-on |
| `GET /v1/account/subscriptions/{subscriptionID}/traffic-package` | Customer session | The traffic packages a live subscription may switch to, each with a preview |
| `POST /v1/account/subscriptions/{subscriptionID}/traffic-package` | Customer session, `Idempotency-Key` | Switch the traffic package |

The add-on save and retire routes are implemented but missing from `api/openapi.yaml`, so they are absent from the generated client and the published API reference. [Integrating with the API](/integrations/api) explains how to call them anyway.
