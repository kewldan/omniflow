---
title: "0014 — Apple in-app purchases ship only with a native app"
description: Why Apple IAP is out of scope for Omniflow's web panel and Telegram bot, and what would have to exist first
---

**Status:** Accepted.

## Context

Bedolaga accepts Apple in-app purchases through its iOS companion app: the app
buys an auto-renewable subscription through StoreKit, and the server verifies
the transaction with App Store Server API and follows App Store Server
Notifications for renewals and refunds.

Omniflow has no native application. Its customer surfaces are a web panel and a
Telegram bot. App Store guidelines allow StoreKit purchases only inside an app
distributed through the App Store; a web page or a bot cannot start one.

## Decision

**Apple IAP is not implemented in Omniflow until a native iOS client exists.**
No StoreKit receipt verification, App Store Server API client, or App Store
Server Notifications endpoint is added: each would be an unreachable payment
path, and AGENTS.md requires every capability to be wired end to end.

When a native app is built, it ships with its own architecture record covering
the App Store Server API credentials, transaction-to-order mapping, refunds and
revocations through notifications, and family sharing.

## Consequences

- Operators migrating from Bedolaga with iOS app subscribers must keep those
  subscribers on the App Store side until a native app exists; the importer
  does not convert App Store subscriptions.
- iOS customers pay through the web panel or the bot with the other providers.

## Revisit when

A native iOS (or macOS) client for Omniflow is accepted onto the roadmap.
