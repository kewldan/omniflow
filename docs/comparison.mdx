Omniflow is not the only open-source way to sell Remnawave subscriptions. This page compares it with the projects operators most often evaluate alongside it, using each project's own public documentation.

<Note>
Bedolaga Bot and RemnaCore were compared on 11 August 2026 against their public `main` branches and have not been re-checked since. The Bedolaga Cabinet rows were re-checked on 14 August 2026 against its published 1.61.0 feature list, which is more detailed than the README the first pass used and is why several rows below are new. Omniflow's own column tracks this repository and was last updated on 14 August 2026. Feature sets move quickly. Verify against the upstream repository before making a decision, and open an issue if anything here is out of date or unfair.
</Note>

## The projects

| Project | What it is | License | Stack |
| --- | --- | --- | --- |
| **Omniflow** | Telegram-first commerce and support platform for Remnawave, with complete operator and customer web panels | Apache-2.0 | Go 1.26, PostgreSQL 18, Valkey 9, River, Next.js 16 / React 19 |
| **[Bedolaga Bot](https://github.com/BEDOLAGA-DEV/remnawave-bedolaga-telegram-bot)** | Mature Telegram sales bot for Remnawave, administered from inside Telegram | MIT | Python 3.13, aiogram 3.x, FastAPI, PostgreSQL + SQLAlchemy, Redis |
| **[Bedolaga Cabinet](https://github.com/BEDOLAGA-DEV/bedolaga-cabinet)** | Customer web cabinet for Bedolaga Bot; requires the bot's Cabinet API | AGPL-3.0 | React, Vite, TypeScript, Tailwind, Nginx |
| **[RemnaCore](https://github.com/BEDOLAGA-DEV/RemnaCore)** | Modular DDD platform wrapping Remnawave, with reseller and plugin support; marked in development | AGPL-3.0 | Go 1.26, PostgreSQL 18, Valkey 9, NATS JetStream, Extism/wazero WASM, React 19 |

License differences are worth reading carefully. Omniflow is Apache-2.0, which permits closed modification and includes an explicit patent grant. Bedolaga Bot is MIT. Bedolaga Cabinet and RemnaCore are AGPL-3.0, which extends copyleft obligations to users served over a network.

## How to read the tables

| Mark | Meaning |
| --- | --- |
| ✅ | Available today |
| 🚧 vX.X | Planned; see the [roadmap](https://github.com/kewldan/omniflow/blob/main/ROADMAP.md) |
| 🔭 | Post-1.0 candidate, not scheduled |
| ❌ | Deliberately not planned |
| — | Not documented in that project's public README |

A dash means the capability is absent from the project's own public documentation. Internal implementation details such as ledger design or idempotency handling may exist in code without appearing in a README, so treat a dash as "unverified", not as a proven gap.

The 🔭 rows that came out of the 14 August 2026 reading of Bedolaga Cabinet 1.61.0 are collected as [Post-1.0 product gaps](https://github.com/kewldan/omniflow/blob/main/ROADMAP.md) in the roadmap. Each one there states what Omniflow has today and what the absence costs, which is the part a one-cell mark cannot carry.

Omniflow's shipped surface today is v0.1–v0.10: the complete backend commerce model, a feature-complete Telegram bot, wallet top-up with deferred carts, add-ons, optional concurrent subscriptions, a production runtime with health probes, metrics, tracing, encrypted backups, and maintenance mode, and a complete operator panel — sign-in with two-factor, optional OIDC, granular RBAC, an append-only audit trail, and the day-to-day screens for customers, finance, catalogue, support, marketing, risk, and every installation setting, and a complete customer web panel — sign-in, subscriptions, checkout, wallet, the digital-goods shop, support, news, referrals, loyalty, and a customer's own data export and deletion request. What remains is v1.0: release engineering rather than product surface.

Provider count is the clearest gap. Bedolaga bundles an order of magnitude more providers, and if a specific Russian acquirer is a hard requirement, that is a decisive advantage today. Omniflow adds providers on demand rather than for parity, so the relevant question is whether the provider you need is present, not how many exist.

Omniflow's counterweight is the financial model. Every order and payment mutation carries an idempotency key, webhook intake is replay-safe with raw-event retention, and balances derive from an append-only double-entry ledger where corrections are compensating entries rather than updates. These invariants are documented and tested — see [Financial invariants](/commerce/financial-invariants).

Omniflow enforces marketing consent, quiet hours, frequency caps, and delivery deduplication, and separates transactional from marketing classification. Those constraints were built before the campaign tooling that now uses them, which is the order that makes them hold: a suppression list added after the first broadcast is a suppression list somebody has already been missed by.

Advertising measurement is the sharpest of the marketing gaps, and it is worth understanding why rather than reading it as a missing checkbox. Payment settles on the backend, sometimes a day after the click that started it, so an advertising platform learns nothing unless a click identifier is carried into the order and uploaded back as an offline conversion. Omniflow does not do this today, which means a paid channel cannot be attributed at all. When it arrives it will be the operator's own analytics, never project telemetry, and it will be per-installation, off by default, and bound by the marketing consent already enforced above — see [Telemetry](/operations/telemetry) for the line that separates the two.

Two of those marks are decisions rather than backlog. Node and squad control is ❌ for the same reason node health and routing are further down: Remnawave owns nodes, hosts, squads, and Xray state, and an operator reaches them in Remnawave's own panel. Account-sharing detection is 🔭 with a condition attached — whether Omniflow may hold per-connection observations at all is a boundary question that has to be settled before it is a feature, not after.

The reporting rows are the substantive gap. Omniflow's dashboard reports a fixed 30-day window on purpose, so that two visits compare, but it is currently the only window: there is no breakdown by plan, period, or day, no trial-to-paid conversion, and no settlement rate per provider. With four bundled providers, an acquirer that quietly starts failing shows up as support tickets and a growing stuck-payment queue rather than as a number that moved.

Omniflow deliberately keeps administration out of Telegram. As of v0.5 Telegram carries operator notifications and backup/restore actions, and nothing else: those two are exempt because an incident is exactly when a browser and a panel may be unavailable. Every other control lives in the web panel, where RBAC, audit, and confirmation dialogs can be enforced consistently.

That is a real trade-off. Bedolaga operators are productive on day one with no reverse proxy, TLS, or browser. Omniflow needs one — but as of v0.8 the browser is enough: plans, providers, limits, the Remnawave connection, the bot, backups, and session policy are all configured from the panel, with no environment file or SQL involved.

Two rows there deserve their reasoning rather than their mark. E-mail and password sign-in is genuinely undecided: Telegram, OIDC, and a magic link are the ways into an Omniflow account, a password is a credential to phish, reset, and breach, and not having one is defensible — but the choice has never been written down, so it currently reads as an oversight. It is on the roadmap as a decision to record, not as a feature to build.

The client application catalogue is a trade-off rather than an omission. Omniflow's connect screen renders a client table compiled into the application, which both the bot and the web panel read, so a customer cannot be told to install one client in the chat and a different one in the browser. Keeping one source is the point; needing a release to add a client is what it costs. See [Connecting a device](/customer/connection).

## Architecture and operations

| Capability | Omniflow | Bedolaga | RemnaCore |
| --- | --- | --- | --- |
| Language | Go | Python | Go |
| Durable job engine | River, transactional | — | NATS JetStream + Watermill |
| Transactional outbox for domain events | ✅ | — | ✅ (45 events) |
| Message broker required | ❌ | ❌ | ✅ |
| Plugin runtime | 🔭 | — | ✅ (WASM) |
| Kubernetes, Helm, Pulumi | 🔭 | — | ✅ |
| Single-server Docker Compose deployment | ✅ | ✅ | ✅ |
| OpenTelemetry traces and Prometheus metrics | ✅ | — | ✅ |
| Anonymous telemetry with complete opt-out | ✅ | — | — |
| Node health, smart routing, speed test | ❌ | — | ✅ |

RemnaCore is the closest architectural relative — the same Go, PostgreSQL 18, Valkey 9, and React 19 foundation. The divergence is what each project treats as mandatory. RemnaCore requires NATS JetStream and ships a WASM plugin runtime with Kubernetes and Pulumi deployment. Omniflow lists a broker, a plugin runtime, and Kubernetes as post-1.0 candidates precisely so that a single-server operator never has to run them.

RemnaCore also reaches into node health monitoring, smart routing, and speed tests. Omniflow does not, and will not: Remnawave is authoritative for nodes, hosts, squads, and Xray state, and Omniflow uses only its supported API. See [Data ownership](/architecture/data-ownership).

## Choosing between them

**Choose Bedolaga Bot** if you need the widest payment-provider coverage today, want to administer everything from Telegram without deploying a web panel, or need growth mechanics such as contests, custom landing pages, and referral payouts that Omniflow has deferred past 1.0. Adding the cabinet also gets you the reporting and presentation layer Omniflow has not built: sales figures over a period you choose, settlement rates per provider, per-node traffic, and information pages you publish from the panel instead of hosting elsewhere. If you sell through paid advertising, note the attribution gap in particular — Bedolaga carries a click identifier into the order and uploads the conversion back, and Omniflow does not.

**Choose RemnaCore** if you need white-label reseller capability with commission tracking, or are already running Kubernetes and want a plugin runtime and event bus as first-class infrastructure. Note its stated development status before committing production traffic.

**Choose Omniflow** if financial correctness is your priority — idempotent orders and webhooks, an append-only double-entry ledger, wallet credit that cannot be applied twice, and fulfillment that never loses a successful payment when Remnawave is unavailable — and if you want administration behind RBAC and an audit trail rather than in a chat window. Omniflow is also the option that treats the Remnawave boundary as inviolable and keeps a single-server install free of a broker, plugin runtime, or orchestrator.

Since v0.5 it is additionally the option that takes production operation seriously on a single server: readiness probes that classify each dependency without leaking it, Prometheus metrics whose labels can never carry a customer identifier, encrypted backups verified by read-back before they are trusted, and a maintenance mode that pauses new purchases without disturbing money already taken.

<Note>
Both panels are complete as of v0.10: the operator panel since v0.8, and the customer panel — sign-in, subscriptions, checkout, wallet, shop, support, referrals, and personal data — since v0.10. Customers can self-serve in a browser or in Telegram, against the same records: a cart started in a chat is the cart the browser shows, and a support reply read on the web stops being unread in Telegram.

The v1.0 gate is release engineering rather than product surface, and one item in it remains: an independent security review of authentication, authorization, payments, and secret handling. That one names an external reviewer engagement rather than a change to this repository. The compatibility matrix, signed artifacts, and the reliability and documentation gates are done.

Complete is not the same as at parity. The 🔭 rows above are capabilities Bedolaga Cabinet has and Omniflow does not — reporting depth, advertising attribution, published information pages — and none of them is scheduled. [Post-1.0 product gaps](https://github.com/kewldan/omniflow/blob/main/ROADMAP.md) records each one with what exists today and what the absence costs.
</Note>
