Omniflow is not the only open-source way to sell Remnawave subscriptions. This page compares it with the projects operators most often evaluate alongside it, using each project's own public documentation.

<Note>
Compared on 11 August 2026 against the public `main` branch of each project. Feature sets move quickly. Verify against the upstream repository before making a decision, and open an issue if anything here is out of date or unfair.
</Note>

## The projects

| Project | What it is | License | Stack |
| --- | --- | --- | --- |
| **Omniflow** | Telegram-first commerce and support platform for Remnawave, with an operator and customer web panel arriving later | Apache-2.0 | Go 1.26, PostgreSQL 18, Valkey 9, River, Next.js 16 / React 19 |
| **[Bedolaga Bot](https://github.com/BEDOLAGA-DEV/remnawave-bedolaga-telegram-bot)** | Mature Telegram sales bot for Remnawave, administered from inside Telegram | MIT | Python 3.13, aiogram 3.x, FastAPI, PostgreSQL + SQLAlchemy, Redis |
| **[Bedolaga Cabinet](https://github.com/BEDOLAGA-DEV/bedolaga-cabinet)** | Customer web cabinet for Bedolaga Bot; requires the bot's Cabinet API | AGPL-3.0 | React, Vite, TypeScript, Tailwind, Nginx |
| **[RemnaCore](https://github.com/BEDOLAGA-DEV/RemnaCore)** | Modular DDD platform wrapping Remnawave, with reseller and plugin support; marked in development | AGPL-3.0 | Go 1.26, PostgreSQL 18, Valkey 9, NATS JetStream, Extism/wazero WASM, React 19 |

License differences are worth reading carefully. Omniflow is Apache-2.0, which permits closed modification and includes an explicit patent grant. Bedolaga Bot is MIT. Bedolaga Cabinet and RemnaCore are AGPL-3.0, which extends copyleft obligations to users served over a network.

## How to read the tables

| Mark | Meaning |
| --- | --- |
| ✅ | Available today |
| 🚧 vX.X | Planned; see the [roadmap](https://github.com/kewldan/omniflow/blob/main/ROADMAP.md) |
| 🔭 | Post-1.0 candidate, not scheduled |
| ❌ | Deliberately not planned |
| — | Not documented in that project's public README |

A dash means the capability is absent from the project's own public documentation. Internal implementation details such as ledger design or idempotency handling may exist in code without appearing in a README, so treat a dash as "unverified", not as a proven gap.

Omniflow's shipped surface today is v0.1–v0.5: the complete backend commerce model, a feature-complete Telegram bot, wallet top-up with deferred carts, add-ons, optional concurrent subscriptions, and a production runtime with health probes, metrics, tracing, encrypted backups, and maintenance mode. There is no web panel yet.

Provider count is the clearest gap. Bedolaga bundles an order of magnitude more providers, and if a specific Russian acquirer is a hard requirement, that is a decisive advantage today. Omniflow adds providers on demand rather than for parity, so the relevant question is whether the provider you need is present, not how many exist.

Omniflow's counterweight is the financial model. Every order and payment mutation carries an idempotency key, webhook intake is replay-safe with raw-event retention, and balances derive from an append-only double-entry ledger where corrections are compensating entries rather than updates. These invariants are documented and tested — see [Financial invariants](/commerce/financial-invariants).

Omniflow deliberately keeps administration out of Telegram. As of v0.5 Telegram carries operator notifications and backup/restore actions, and nothing else: those two are exempt because an incident is exactly when a browser and a panel may be unavailable. Every other control lives in the web panel, where RBAC, audit, and confirmation dialogs can be enforced consistently.

That is a real trade-off. Bedolaga operators are productive on day one with no reverse proxy, TLS, or browser. Omniflow operators today configure plans, providers, and limits through environment files and the operator API, and wait for v0.6 for a panel.

## Architecture and operations

| Capability | Omniflow | Bedolaga | RemnaCore |
| --- | --- | --- | --- |
| Language | Go | Python | Go |
| Durable job engine | River, transactional | — | NATS JetStream + Watermill |
| Transactional outbox for domain events | ✅ | — | ✅ (45 events) |
| Message broker required | ❌ | ❌ | ✅ |
| Plugin runtime | 🔭 | — | ✅ (WASM) |
| Kubernetes, Helm, Pulumi | 🔭 | — | ✅ |
| Single-server Docker Compose deployment | ✅ | ✅ | ✅ |
| OpenTelemetry traces and Prometheus metrics | ✅ | — | ✅ |
| Anonymous telemetry with complete opt-out | ✅ | — | — |
| Node health, smart routing, speed test | ❌ | — | ✅ |

RemnaCore is the closest architectural relative — the same Go, PostgreSQL 18, Valkey 9, and React 19 foundation. The divergence is what each project treats as mandatory. RemnaCore requires NATS JetStream and ships a WASM plugin runtime with Kubernetes and Pulumi deployment. Omniflow lists a broker, a plugin runtime, and Kubernetes as post-1.0 candidates precisely so that a single-server operator never has to run them.

RemnaCore also reaches into node health monitoring, smart routing, and speed tests. Omniflow does not, and will not: Remnawave is authoritative for nodes, hosts, squads, and Xray state, and Omniflow uses only its supported API. See [Data ownership](/architecture/data-ownership).

## Choosing between them

**Choose Bedolaga Bot** if you need the widest payment-provider coverage today, want to administer everything from Telegram without deploying a web panel, or need growth mechanics such as contests, custom landing pages, and referral payouts that Omniflow has deferred past 1.0.

**Choose RemnaCore** if you need white-label reseller capability with commission tracking, or are already running Kubernetes and want a plugin runtime and event bus as first-class infrastructure. Note its stated development status before committing production traffic.

**Choose Omniflow** if financial correctness is your priority — idempotent orders and webhooks, an append-only double-entry ledger, wallet credit that cannot be applied twice, and fulfillment that never loses a successful payment when Remnawave is unavailable — and if you want administration behind RBAC and an audit trail rather than in a chat window. Omniflow is also the option that treats the Remnawave boundary as inviolable and keeps a single-server install free of a broker, plugin runtime, or orchestrator.

Since v0.5 it is additionally the option that takes production operation seriously on a single server: readiness probes that classify each dependency without leaking it, Prometheus metrics whose labels can never carry a customer identifier, encrypted backups verified by read-back before they are trusted, and a maintenance mode that pauses new purchases without disturbing money already taken.

<Warning>
Omniflow has no web panel today. If an operator or customer web interface is a requirement right now, Bedolaga Cabinet or RemnaCore ships one and Omniflow does not until v0.6 and v0.9 respectively.
</Warning>
