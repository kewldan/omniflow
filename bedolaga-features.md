# Bedolaga Cabinet — полный перечень возможностей продукта

> Документ описывает функциональность **веб-кабинета** (`bedolaga-cabinet`, React + Vite + TypeScript)
> — фронтенда к Cabinet API бота [Remnawave Bedolaga Telegram Bot](https://github.com/BEDOLAGA-DEV/remnawave-bedolaga-telegram-bot).
> Версия на момент составления: **1.61.0**.
>
> Кабинет — это «витрина» и «пульт управления» VPN-сервисом: то, что раньше жило только внутри
> Telegram-бота (покупка подписки, баланс, рефералка, поддержка, админка), вынесено в полноценный
> веб-интерфейс, доступный из браузера и как Telegram Mini App.

## 0. Архитектура и модель продукта

### 0.1. Как это устроено

```
Браузер / Telegram Mini App
        │
        ▼
Caddy / Nginx / Traefik  ──►  /api/*  ──►  remnawave_bot:8080   (Cabinet API бота)
                         ──►  /*      ──►  /srv/cabinet          (статика SPA)
                                              │
                                              ▼
                                     Remnawave Panel (XTLS/Xray-ноды)
```

**Как работает.** Кабинет — статический SPA-бандл (HTML/JS/CSS), не имеющий собственного бэкенда.
Вся бизнес-логика живёт в боте; кабинет ходит в него через `/api/*` (обратный прокси срезает префикс).
Авторизация — JWT (access ~15 мин + refresh ~7 дней), CORS-домены задаются на стороне бота
(`CABINET_ALLOWED_ORIGINS`). Бот, в свою очередь, управляет пользователями и подписками в панели
Remnawave, которая уже конфигурирует Xray-ноды.

**Зачем нужно.** Позволяет разворачивать кабинет отдельно от бота (или вообще на CDN), не дублируя
бизнес-логику и не открывая наружу панель Remnawave. Один бэкенд обслуживает и Telegram-бота,
и веб-кабинет — данные всегда консистентны.

### 0.2. Три канала доставки одного и того же продукта

| Канал | Как определяется | Особенности |
|---|---|---|
| Обычный браузер | `WebAdapter` | Полный UI, email-авторизация, OAuth |
| Telegram Mini App | `TelegramAdapter` + `@telegram-apps/sdk-react` | Haptic feedback, fullscreen, нативная кнопка «Назад», оплата Telegram Stars |
| Публичные лендинги | Роуты `/buy/:slug` | Продажа **без регистрации**, доступ по e-mail/Telegram-контакту |

**Как работает.** `PlatformProvider` при старте определяет среду и подставляет соответствующий
адаптер (`src/platform/adapters/`). Компоненты не знают, где они выполняются — они спрашивают у
платформы «умеешь ли ты вибрацию / фуллскрин / Stars-инвойс».

**Зачем нужно.** Один код — три сценария продаж: холодный трафик с лендинга, тёплый из Telegram,
и возвраты через веб. Не нужно поддерживать три отдельных приложения.

## 1. Платформенные возможности

### 1.1. Мультиспособная авторизация

Кабинет поддерживает одновременно несколько способов входа в один и тот же аккаунт:

| Способ | Endpoint | Сценарий |
|---|---|---|
| Telegram Login Widget | `POST /cabinet/auth/telegram/widget` | Классическая кнопка «Login with Telegram» на сайте |
| Telegram Mini App initData | `POST /cabinet/auth/telegram` | Бесшовный вход внутри Telegram |
| Telegram OIDC | `POST /cabinet/auth/telegram/oidc` | OAuth-подобный флоу для доменов без виджета |
| E-mail + пароль | `POST /cabinet/auth/email/login` | Веб-first пользователи без Telegram |
| OAuth-провайдеры | `google`, `yandex`, `discord`, `vk` | Быстрый вход в один клик |
| Deep-link токен | `requestDeepLinkToken` / `pollDeepLinkToken` | Вход из бота: бот выдаёт токен, страница его опрашивает |
| Auto-login | `POST /cabinet/auth/login/auto` | Одноразовые ссылки (например, из письма или рассылки) |

**Как работает.** Все способы приводят к одной паре токенов (`access` + `refresh`), которые
хранятся в `store/auth.ts` и автоматически обновляются интерцептором `api/client.ts` при 401.
`saveReturnUrl()` запоминает страницу, с которой пользователя выкинуло на логин, чтобы вернуть
его туда после входа.

**Зачем нужно.** Аудитория VPN-сервисов разнородная: часть живёт в Telegram, часть приходит с
рекламы в браузере и Telegram не имеет. Требовать Telegram от всех — терять конверсию;
требовать e-mail от телеграмных — тоже.

#### Связывание и слияние аккаунтов

- **`/profile/accounts`** (`ConnectedAccounts.tsx`) — привязка/отвязка Telegram и OAuth-провайдеров
  к уже существующему аккаунту (`linkProviderInit` → редирект → `linkProviderCallback`).
- **`/merge/:mergeToken`** (`MergeAccounts.tsx`) — слияние двух аккаунтов. Сначала показывается
  **preview** (`getMergePreview`): что будет с балансом, подписками, рефералами обеих сторон,
  и только потом выполняется `executeMerge`.
- **Смена e-mail** — двухшаговая: `requestEmailChange` отправляет код на новый адрес,
  `verifyEmailChange` его подтверждает.

**Зачем нужно.** Классическая беда: человек купил подписку в боте, потом зарегистрировался в вебе
по e-mail и получил второй пустой аккаунт. Merge с превью решает это без обращения в поддержку и
без риска потерять оплаченное.

#### Восстановление доступа
`POST /cabinet/auth/password/forgot` → письмо → `/reset-password` → `POST /cabinet/auth/password/reset`.
Верификация e-mail (`/verify-email`) может быть включена или выключена админом
(`branding/email-auth` → `verification_enabled`).

### 1.2. RBAC — роли, права и политики доступа

**Модель.** Право — строка вида `resource:action` (`users:read`, `tariffs:*`, `*:*`).
Сопоставление реализовано в `store/permissions.ts`:

```
'*:*'        → матчит всё
'users:*'    → матчит users:read, users:edit, users:delete…
'users:read' → точное совпадение
```

Дополнительно у роли есть **уровень** (`level`) — админ не может назначить или отредактировать
роль выше собственного уровня (`canManageRole`).

**Что можно настраивать (`/admin/roles`, `/admin/policies`):**

- **Роли** — имя, описание, уровень, набор прав, цвет и иконка (для визуального различения в UI),
  системные роли защищены от удаления (`is_system`).
- **Назначения** — привязка роли к пользователю, опционально **с датой истечения** (`expires_at`).
- **Политики доступа (ABAC-слой)** — правила `resource` + `actions` + `effect: allow | deny` +
  `conditions` + `priority`, опционально привязанные к роли. Позволяют выразить «разрешено всё,
  кроме X» или «разрешено только в таких-то условиях».
- **Журнал аудита** (`/admin/audit-log`) — кто, что и когда сделал, с экспортом.

**Как работает в UI.** Каждый админ-роут обёрнут в `<PermissionRoute permission="...">`.
Если права нет — пункт меню не отображается и прямой переход блокируется. Список прав
подтягивается один раз при входе.

**Зачем нужно.** Реальные сервисы обслуживаются командой: саппорт должен видеть тикеты и
пользователей, но не трогать тарифы и выплаты; маркетолог — кампании и промокоды, но не ноды.
Плюс аудит-лог — обязательное требование, когда к деньгам имеют доступ несколько человек.

Полный список охраняемых разделов: `apps`, `audit_log`, `ban_system`, `broadcasts`, `bulk_actions`,
`campaigns`, `channels`, `coupons`, `email_templates`, `info_pages`, `landings`, `news`, `partners`,
`payment_methods`, `payments`, `pinned_messages`, `promo_groups`, `promo_offers`, `promocodes`,
`remnawave`, `roles`, `sales_stats`, `servers`, `settings`, `stats`, `tariffs`, `tickets`,
`traffic`, `updates`, `users`, `wheel`, `withdrawals`.

### 1.3. Мультиязычность

**Языки:** русский, английский, китайский (`zh`), фарси (`fa`).
Реализация — `i18next` + `i18next-browser-languagedetector`, файлы в `src/locales/*.json`
(объём ru-локали — свыше 320 КБ, то есть переведён буквально весь интерфейс, включая админку).

**Как работает.** Язык определяется в порядке: явный выбор пользователя (хранится на бэке через
`PATCH /cabinet/info/user/language`) → язык Telegram-клиента → язык браузера → дефолт сервиса.
Список доступных языков отдаёт бэкенд (`/cabinet/info/languages`), то есть админ может ограничить
набор. Административный контент (инфостраницы, тарифы в лендингах, e-mail-шаблоны, подписи кнопок
бота) хранится как `Record<lang, string>` — то есть переводится отдельно для каждого языка.

**Зачем нужно.** Bedolaga используется в основном на рынках с обходом блокировок — RU, Иран,
Китай. Локализация на фарси и китайский с RTL/CJK-типографикой — это не «приятное дополнение»,
а условие работы на этих рынках.

### 1.4. Тема оформления и анимированные фоны

**Уровни кастомизации:**

1. **Серверная палитра** (`/cabinet/branding/colors`) — владелец сервиса задаёт акцентный цвет,
   фон/поверхность/текст отдельно для тёмной и светлой тем, а также цвета success/warning/error.
   Из базовых цветов генерируется полная шкала оттенков (50…950, плюс 850 для тёмной темы) —
   `utils/colorConversion.ts`, `hooks/useThemeColors.ts`.
2. **Разрешённые темы** (`/cabinet/branding/themes`) — можно оставить только тёмную или только светлую.
3. **Пользовательские предпочтения** (`useUserThemePreferences`) — режим (`dark`/`light`/`system`),
   пресет скругления (`none`/`small`/`medium`/`large`/`pill`), плотность интерфейса
   (`compact`/`comfortable`/`spacious`).
4. **Анимированный фон** — 21 тип: `aurora`, `sparkles`, `vortex`, `shooting-stars`,
   `background-beams`, `background-beams-collision`, `gradient-animation`, `wavy`,
   `background-lines`, `boxes`, `meteors`, `grid`, `dots`, `spotlight`, `ripple`, `fireflies`,
   `snowfall`, `starfield`, `matrix-rain`, `liquid-gradient`, `constellation`. У каждого —
   собственные настройки, плюс общие: прозрачность, блюр и **`reducedOnMobile`** (упрощение на
   слабых устройствах).

**Как работает.** Цвета применяются как CSS-переменные на `:root`, поэтому смена темы не требует
перезагрузки. Значения цветов проходят через `sanitizeColor()` — разрешены только hex, rgb/rgba,
hsl/hsla и именованные цвета, что закрывает CSS-инъекцию через админские настройки.

**Зачем нужно.** Продукт продаётся как white-label: владельцы разных VPN-сервисов на одном движке
должны выглядеть по-разному. При этом контроль остаётся у владельца — пользователь настраивает
только комфорт (плотность, скругления), но не ломает брендинг.

### 1.5. Экраны блокировки (blocking screens)

`store/blocking.ts` перехватывает специальные ответы API и вместо обычного интерфейса показывает
один из экранов:

| Экран | Когда показывается | Что предлагает |
|---|---|---|
| `MaintenanceScreen` | Режим техобслуживания | Сообщение админа, автоповтор |
| `ChannelSubscriptionScreen` | Не подписан на обязательные каналы | Список каналов + кнопка «Проверить» |
| `BlacklistedScreen` | Аккаунт в чёрном списке | Причина, контакт поддержки |
| `AccountDeletedScreen` | Аккаунт удалён | Информация о восстановлении |
| `ServiceUnavailableScreen` | Бэкенд недоступен | Ретрай |

**Зачем нужно.** Без этого пользователь во время техработ видел бы каскад непонятных ошибок и шёл
бы в поддержку. Экран обязательной подписки на каналы — прямой маркетинговый инструмент
(см. [6.11](#611-обязательные-подписки-на-каналы)).

### 1.6. Прочая платформенная механика

- **Command Palette** (`⌘K` / `Ctrl+K`) — быстрый переход по разделам, особенно ценно в админке
  с её ~80 экранами.
- **WebSocket-уведомления** (`providers/WebSocketProvider`) — живые события: ответ в тикете,
  зачисление платежа, прогресс массовой операции. Без перезагрузки страницы.
- **Устойчивость к деплою** — `lazyWithRetry` в `App.tsx`: если после релиза изменились хэши
  чанков и старая вкладка не может догрузить код, страница один раз сама перезагружается
  (с защитой от цикла — не чаще раза в 30 секунд).
- **Восстановление скролла** (`useScrollRestoration`) — возврат на прежнюю позицию списка после
  перехода в детальную карточку.
- **Санитизация контента** — весь пользовательский и админский HTML (новости, инфостраницы,
  лендинги, e-mail-шаблоны) прогоняется через `DOMPurify`.
- **Безопасные редиректы** (`utils/safeRedirect.ts`, покрыт тестами) — защита от open redirect
  в возвратных URL платёжек и авторизации.
- **Rate limiting на клиенте** (`utils/rateLimit.ts`) — например, кнопка «Обновить трафик» имеет
  серверный кулдаун (`rate_limited` + `retry_after_seconds`), UI его уважает.
- **Мультивалютность** (`api/currency.ts`) — курсы валют кэшируются, суммы хранятся в копейках
  (`*_kopeks`) и форматируются с учётом валюты сервиса.

## 2. Пользовательские фичи

### 2.1. Дашборд (`/`)

Сводный экран: статус подписки и остаток дней, использованный трафик с цветовой зоной
(`useTrafficZone` — зелёная/жёлтая/красная), баланс, активные промо-предложения, последние новости,
быстрые действия (продлить, пополнить, подключиться).

**Зачем нужно.** Ответ на два главных вопроса пользователя — «когда у меня всё кончится» и
«что делать прямо сейчас» — без единого клика.

---

### 2.2. Подписки — мультиподписочная модель

Кабинет поддерживает **несколько одновременных подписок** у одного пользователя
(`/subscriptions`, `/subscriptions/:id`), а не одну, как было исторически. Все операции принимают
опциональный `subscription_id`.

#### Что можно делать с подпиской

| Операция | Endpoint | Описание |
|---|---|---|
| Купить | `POST /cabinet/subscription/purchase` | С предварительным просчётом цены (`purchase-preview`) |
| Купить по тарифу | `POST /cabinet/subscription/purchase-tariff` | Готовый тариф вместо конструктора |
| Продлить | `POST /cabinet/subscription/renew` | Список опций периодов с ценами |
| Сменить тариф | `POST /cabinet/subscription/tariff/switch` | С превью пересчёта (`switch/preview`) |
| Поставить на паузу | `POST /cabinet/subscription/pause` | Заморозка оставшихся дней |
| Отозвать | `POST /cabinet/subscription/revoke` | Досрочное прекращение |
| Удалить | `DELETE /cabinet/subscriptions/:id` | Полное удаление подписки |
| Автоплатёж | `POST /cabinet/subscription/autopay` | Автопродление с баланса |

**Как работает превью.** Перед списанием денег фронт запрашивает `purchase-preview` /
`switch/preview` и показывает итоговую сумму, скидки и что изменится. Только после подтверждения
уходит боевой запрос.

**Зачем нужно.** Смена тарифа с пересчётом остатка — источник конфликтов и возвратов; превью
делает сделку прозрачной. Мультиподписки нужны, когда один аккаунт обслуживает семью или команду
с разными наборами стран.

#### Конструктор подписки

Помимо готовых тарифов, при включённом режиме пользователь собирает подписку сам:

- **Период** — фиксированные периоды или произвольное число дней (`custom_days_enabled`,
  `price_per_day_kopeks`, `min_days`/`max_days`).
- **Трафик** — фиксированный лимит, произвольный объём (`custom_traffic_enabled`,
  `traffic_price_per_gb_kopeks`) или пакеты докупки (`traffic_topup_packages`).
- **Страны/сквады** — выбор доступных локаций (`GET/POST /cabinet/subscription/countries`).
- **Устройства** — докупка (`devices/purchase`), уменьшение лимита (`devices/reduce`),
  предварительный расчёт цены (`devices/price`) с учётом скидок и остатка дней.

**Сохранение корзины** (`save-cart` для трафика и устройств) — если пользователь выбрал опции, но
не оплатил, состояние сохраняется на бэке, и бот может напомнить о брошенной корзине.

**Зачем нужно.** Конструктор поднимает средний чек (человек берёт ровно то, что нужно, и чаще
докупает), а сохранение корзины — прямой инструмент возврата ушедших без оплаты.

#### Управление устройствами (HWID)

`GET /cabinet/subscription/devices` — список подключённых устройств; переименование
(локальный алиас до 64 символов), удаление конкретного устройства или сброс всех.

**Зачем нужно.** Лимит устройств — основа тарифной сетки. Без самостоятельного сброса каждый
переустановленный телефон превращался бы в тикет в поддержку.

#### Трафик

`POST /cabinet/subscription/refresh-traffic` — принудительное обновление счётчика из панели, с
защитой от спама (кэш + `rate_limited`). Отдаёт использовано/лимит в байтах и ГБ, процент,
признак безлимита и **lifetime-потребление**. Режим сброса трафика задаётся тарифом:
`DAY`, `WEEK`, `MONTH`, `MONTH_ROLLING`, `NO_RESET`.

### 2.3. Подключение (`/connection`, `/connection/qr`)

**Что даёт.** Ссылка на подписку, QR-код для сканирования телефоном
(`qrcode.react`), и **инструкции по подключению для конкретной платформы** с кнопками
«Открыть в приложении» (deep-link по схеме приложения), «Скопировать ссылку», «Скачать».

**Как работает.** Конфигурация приложений (`GET /cabinet/subscription/app-config`) приходит с
бэкенда в формате, совместимом с Remnawave app-config: платформы → приложения → блоки → кнопки.
Каждое приложение может быть помечено `featured`. Кнопки бывают трёх типов: `external` (внешняя
ссылка), `subscriptionLink` (подставляется персональная ссылка), `copyButton`. Тексты
локализованы (`LocalizedText`). Блоки рендерятся четырьмя визуальными стилями на выбор:
`AccordionBlock`, `CardsBlock`, `MinimalBlock`, `TimelineBlock`.

Отдельно — **Happ downloads** (`/cabinet/subscription/happ-downloads`): прямые ссылки на сборки
клиента Happ.

В Telegram Mini App deep-link открывается через нативный API, в браузере — через
`utils/openAppScheme.ts` с фолбэком на страницу магазина приложений.

**Зачем нужно.** «Как это подключить» — топ-1 причина обращений в поддержку у любого VPN.
Пошаговая инструкция под конкретную ОС с кнопкой в один клик снимает основную массу тикетов, а
редактируемость конфига (`/admin/apps`) позволяет добавить новый клиент без релиза кабинета.

### 2.4. Баланс и платежи (`/balance`)

#### Пополнение

Флоу: `/balance/top-up` (выбор метода) → `/balance/top-up/:methodId` (сумма и подопции) →
редирект на платёжку → `/balance/top-up/result` (результат).

**Поддерживаемые провайдеры** (набор включается админом в `/admin/payment-methods`):
Telegram Stars, Tribute, CryptoBot, Heleket, YooKassa, MulenPay, PayPalych (Pal24), Platega, WATA,
Freekassa (в т.ч. отдельно СБП и Карта), CloudPayments, Kassa AI, RioPay, SeverPay, PayPear,
RollyPay, AuraPay, OverPay, Etoplatezhi, Antilopay, Jupiter, Donut, Lava, Apple In-App Purchase,
а также ручное пополнение админом.

**Как работает.** `POST /cabinet/balance/topup` создаёт платёж и возвращает `payment_url` +
`expires_at`. В Telegram Mini App для Stars вместо URL создаётся нативный инвойс
(`POST /cabinet/balance/stars-invoice`). Незавершённые платежи попадают в
`pending-payments`, и пользователь может **вручную инициировать проверку статуса**
(`.../check`) — на случай, если вебхук от провайдера не дошёл. Метод и id платежа дублируются в
`sessionStorage` (`utils/topUpStorage.ts`), а если он потерян — есть фолбэк
`pending-payments/:method/latest`.

**Зачем нужно.** Множество провайдеров — не прихоть: у VPN-сервисов регулярно отваливаются
эквайринги, и возможность за минуту переключить трафик на другой шлюз через админку — вопрос
выживания бизнеса. Ручная проверка статуса — против «деньги списались, баланс не пополнился».

#### Сохранённые карты и рекуррентные платежи

`/balance/saved-cards` — список привязанных карт с возможностью отвязки. Страница
`/recurrent-payments` — юридический документ об условиях автосписаний.

#### История транзакций

`GET /cabinet/balance/transactions` с пагинацией и фильтром по типу.

`GET /cabinet/subscription/trial` — доступность триала и его условия, `POST` — активация.

**Зачем нужно.** Основной канал конверсии. Гранулярность (какие серверы доступны в триале) не даёт
раздавать премиум-локации бесплатно.

Плюс **тестовое уведомление** (проверить, что канал доставки работает) и **история уведомлений**.

**Зачем нужно.** Уведомления об истечении — главный драйвер продлений; но неотключаемый спам ведёт
к блокировке бота пользователем, что убивает канал навсегда. Тонкая настройка сохраняет и
конверсию, и канал.

## 3. Монетизация и маркетинг

### 3.1. Тарифы

Тариф (`/admin/tariffs`) — центральная сущность продукта:

- Название, описание, активность, порядок отображения, **уровень тарифа** (`tier_level`).
- Лимиты: трафик (ГБ), устройства, максимум устройств, цена доп. устройства.
- **Периоды и цены** (`period_prices`) — произвольный набор «N дней → цена».
- **Ежедневная тарификация** (`is_daily` + `daily_price_kopeks`) — списание по дням вместо периода.
- **Разрешённые сквады** + индивидуальные лимиты трафика по серверам (`server_traffic_limits`).
- **Привязка к промо-группам** — тариф может быть доступен только определённым сегментам.
- Конструктор: произвольные дни, произвольный трафик, пакеты докупки трафика.
- `is_trial_available` — участвует ли в триале, `show_in_gift` — можно ли дарить.
- `external_squad_uuid` — привязка к внешнему скводу Remnawave.
- Режим сброса трафика (`traffic_reset_mode`), переопределяющий глобальную настройку.
- Статистика по тарифу (`/admin/tariffs/:id/stats`).

**Зачем нужно.** Вся ценовая политика, сегментация и апсейл-лестница (`tier_level`) описываются
данными, без правок кода.

---

### 3.2. Промокоды (`/admin/promocodes`)

**Типы:** бонус на баланс, дни подписки, выдача тарифа, скидка.

**Параметры:** код, максимум использований, окно валидности (`valid_from`/`valid_until`),
**только для первой покупки** (`first_purchase_only`), привязка к промо-группе, привязка к тарифу.

**Статистика** (`/admin/promocodes/:id/stats`): всего активаций, активаций сегодня, лента последних
использований с указанием пользователей.

Активация — `POST /cabinet/promocode/activate`. Если промокод применим к нескольким подпискам,
API возвращает `eligible_subscriptions`, и UI просит выбрать конкретную.

---

### 3.3. Промо-группы и программа лояльности

**Промо-группа** — сегмент пользователей с собственными скидками:

- Скидка на серверы (`server_discount_percent`)
- Скидка на трафик (`traffic_discount_percent`)
- Скидка на устройства (`device_discount_percent`)
- **Скидки по периодам** (`period_discounts`: чем длиннее период, тем больше скидка)
- `apply_discounts_to_addons` — распространять ли скидки на допуслуги
- `auto_assign_total_spent_kopeks` — **автоматическое назначение при достижении суммы трат**

Последний параметр превращает промо-группы в **программу лояльности**: `/cabinet/promo/loyalty-tiers`
отдаёт пользователю лестницу уровней с текущей потраченной суммой, текущим и следующим уровнем и
прогрессом в процентах.

**Зачем нужно.** Автоматическое повышение уровня — сильный механизм удержания: пользователь видит
«до следующего уровня осталось N ₽» и это стимулирует продлеваться заранее и брать длинные периоды.

---

### 3.4. Промо-предложения (`/admin/promo-offers`)

**Что это.** Персональные ограниченные по времени офферы, привязанные к событию
(`notification_type`): «подписка заканчивается», «триал закончился», «давно не заходил» и т. д.

**Как работает.**
- **Шаблоны** (`promo-offers/templates`) — текст сообщения, текст кнопки, срок жизни оффера
  (`valid_hours`), процент скидки, бонус на баланс, длительность действия активированной скидки
  (`active_discount_hours`), а для тест-доступа — `test_duration_hours` и `test_squad_uuids`.
- **Рассылка** (`promo-offers/broadcast`) — создать офферы для сегмента или конкретного
  пользователя, опционально с push-уведомлением; отчёт: сколько создано, сколько уведомлений ушло
  и сколько провалилось.
- На стороне пользователя: `/cabinet/promo/offers` → `claim` активирует скидку, которая становится
  «активной скидкой» (`/cabinet/promo/active-discount`) и автоматически применяется при покупке.
  Пользователь может её и **сбросить** — если хочет приберечь для другой покупки.
- **Логи** (`promo-offers/logs`) — что кому отправлено и что активировано.

**Зачем нужно.** Триггерные офферы с дедлайном — самый эффективный инструмент возврата
отваливающихся пользователей, и здесь он полностью настраиваемый, без участия разработчика.

---

### 3.5. Лендинги (`/admin/landings`, публичный `/buy/:slug`)

**Конструктор посадочных страниц прямо в админке.** Каждый лендинг:

- `slug`, заголовок, подзаголовок, блок преимуществ (иконка + заголовок + описание), футер.
- Набор тарифов с периодами и **отображением зачёркнутой старой цены** (`original_price_kopeks`,
  `discount_percent`).
- Набор платёжных методов, отдельно настраиваемых для этого лендинга (включая `return_url`
  и подопции метода).
- **Акция с обратным отсчётом** (`LandingDiscountInfo`: процент, `ends_at`, текст бейджа).
- `custom_css`, SEO-мета (`meta_title`, `meta_description`), собственный анимированный фон.
- `sticky_pay_button` — залипающая кнопка оплаты на мобильных.
- **Интеграция аналитики**: отдельные цели для просмотра (`analytics_view_goal`) и клика
  (`analytics_click_goal`) с независимыми переключателями.
- Возможность включить на лендинге покупку в подарок (`gift_enabled`).

**Ключевая механика — покупка без регистрации.** `POST /cabinet/landing/:slug/purchase` принимает
только `contact_type` (`email` | `telegram`) и `contact_value`. После оплаты пользователь получает
токен активации (`/buy/success/:token` → `POST /cabinet/landing/activate/:token`), а аккаунт
создаётся автоматически.

**Аналитика лендинга** (`/admin/landings/:id/stats`) — просмотры, конверсии, список покупок.

**Зачем нужно.** Классическая воронка «реклама → лендинг → оплата» без промежуточного шага
регистрации даёт кратно более высокую конверсию, чем «зайдите в бота и разберитесь». А то, что
лендинг собирается в админке, позволяет маркетологу тестировать десяток посадочных в неделю без
разработчика.

---

### 3.6. Рекламные кампании (`/admin/campaigns`)

**Что это.** Отслеживаемые каналы привлечения с бонусом за регистрацию.

**Параметры кампании:**
- `start_parameter` — метка, которая приходит в deep-link бота (`?start=...`) и в web-ссылке.
- **Тип бонуса**: `balance` (деньги на счёт), `subscription` (готовая подписка с заданными
  днями/трафиком/устройствами/сквадами), `tariff` (конкретный тариф на N дней), `none`.
- Привязка к **партнёру** (`partner_user_id`) — регистрации по кампании засчитываются партнёру.
- Готовые ссылки: `deep_link` (Telegram) и `web_link` (кабинет).

**Статистика** (`/admin/campaigns/:id/stats`): регистрации, выданные бонусы в деньгах,
**конверсия**, выручка, графики по дням, поимённый список зарегистрировавшихся.
Плюс сводка по всем кампаниям (`campaigns/overview`) и топ кампаний на дашборде.

**Зачем нужно.** Позволяет посчитать реальный ROI каждого рекламного размещения: сколько людей
пришло, сколько заплатило, сколько денег принесло — против того, сколько было выдано бонусов.

---

### 3.7. Купоны — оптовая продажа доступа (`/admin/coupons`)

**Что это.** Генерация **партии** одноразовых кодов доступа: «500 купонов на тариф X на 30 дней
по оптовой цене Y».

**Как работает.** Создаётся батч (`name`, `tariff_id`, `period_days`, `coupons_count`,
`wholesale_price_kopeks`, `valid_days`), API возвращает готовые **ссылки** и **токены**.
По ссылке `/coupon/:token` открывается публичная страница (без авторизации), показывающая тариф,
период, срок действия и ссылку на бота. Погашение — `POST /cabinet/coupon/redeem`. Если у
пользователя уже есть подписка на этот тариф, купон её **продлевает** (`renewed: true`).
Всю партию можно **отозвать** одной кнопкой (`revoke`), при этом уже погашенные не затрагиваются.

Учёт по батчу: `active_count` / `redeemed_count` / `revoked_count`.

**Зачем нужно.** Модель B2B/реселлинга: продать блок доступов дистрибьютору или разыграть коды в
партнёрском канале, не заводя реселлеров в систему как пользователей. Возможность отозвать всю
партию — страховка на случай утечки кодов.

---

### 3.8. Подарочные подписки (`/gift`)

**Как работает.** Пользователь выбирает тариф и период (`GET /cabinet/gift/config` отдаёт тарифы
с `show_in_gift`, доступные способы оплаты, текущий баланс и активную скидку), указывает
**получателя** (e-mail или Telegram) и **сопроводительное сообщение**. Оплата — с баланса
(`payment_mode: 'balance'`) или через платёжный шлюз.

Дополнительно поддерживается режим **code-only** (`is_code_only`) — подарок без указания
получателя, в виде кода, который можно передать как угодно.

Разделы: `pending` (подарки, ожидающие получателя), `sent` (отправленные — со статусом и тем, кто
активировал), `received` (полученные). Активация — по коду (`POST /cabinet/gift/activate`) или по
ссылке `/buy/gift/:token`.

Админ видит подарки конкретного пользователя (`/admin/users/:id` → `getUserGifts`).

**Зачем нужно.** Сезонный драйвер продаж и виральный канал: получатель подарка — это новый
пользователь, приведённый бесплатно.

---

### 3.9. Колесо фортуны (`/wheel`)

**Пользовательская часть.** Анимированное колесо с призами (эмодзи + цвет + название).
Оплата спина — **Telegram Stars** или **днями подписки** (каждый канал включается независимо).
Ограничение — дневной лимит спинов; для оплаты днями есть минимум оставшихся дней подписки.
API возвращает `rotation_degrees` — то есть итог определяет **сервер**, а фронт лишь проигрывает
анимацию до нужного угла. История спинов — с пагинацией.

**Админская часть** (`/admin/wheel`):
- **RTP** (`rtp_percent`) — целевой процент возврата, вокруг которого балансируются вероятности;
  плюс возможность задать **ручную вероятность** конкретному призу (`manual_probability`).
- Призы: тип, значение, «денежная стоимость» приза (`prize_value_kopeks` — для расчёта RTP),
  бонус на баланс, дни подписки, ГБ трафика; порядок призов drag-and-drop (`reorder`).
- Настройки промокода-приза: префикс (`promo_prefix`) и срок жизни (`promo_validity_days`).
- **Статистика**: всего спинов, выручка, выплаты, **фактический RTP против настроенного**,
  разбивка по типам оплаты, распределение призов, топ выигрышей, лента всех спинов.

**Зачем нужно.** Геймификация ежедневного возврата в приложение плюс дополнительная монетизация
через Stars. Контроль RTP — принципиален: без него механика легко становится убыточной, а с
фактическим RTP в отчёте владелец видит реальную экономику развлечения.

---

### 3.10. Конкурсы и опросы

- **Конкурсы** (`/contests`) — мини-игры (`game_type` + `game_data` + инструкция) с призом в днях
  подписки. Один раунд — одна попытка (`already_played`).
- **Опросы** (`/polls`) — многошаговые анкеты (вопрос → варианты → следующий вопрос) с
  **вознаграждением за прохождение** (`reward_granted`). Прогресс сохраняется, можно вернуться и
  продолжить.

**Зачем нужно.** Конкурсы — вовлечение и повод для рассылки; опросы — сбор продуктовой обратной
связи, за который пользователю платят, что радикально поднимает долю ответивших.

## 4. Партнёрская программа

### 4.1. Реферальная система (`/referral`)

**Для пользователя:** персональная ссылка, список приглашённых (с отметками «оформил подписку» /
«оплатил»), лента начислений с указанием причины и кампании, суммарный заработок, условия
программы (`/cabinet/referral/terms`).

**Зачем нужно.** Самый дешёвый канал привлечения в VPN-нише; прозрачная статистика по каждому
рефералу — то, ради чего люди реально начинают приводить друзей.

### 4.2. Выплаты (`/referral/withdrawal/request`)

**Как работает.** `WithdrawalBalanceResponse` раскладывает баланс на составляющие:
всего заработано, потрачено внутри сервиса, уже выведено, в обработке, **доступно к выводу**.
Есть режим `only_referral_mode` (выводить можно только реферальные, но не пополненные средства),
минимальная сумма, глобальный флаг включения выплат и человекочитаемая причина отказа
(`cannot_request_reason`). Реквизиты вводятся текстом по заданному шаблону (`requisites_text`).

**Админская обработка** (`/admin/withdrawals`): очередь заявок с суммой ожидающих выплат,
**скоринг риска** каждой заявки (`risk_score`, `risk_level`, развёрнутый `risk_analysis`),
контекст по пользователю (баланс, число рефералов, суммарный заработок), и действия
approve / reject (с комментарием) / complete.

**Зачем нужно.** Реферальные программы — магнит для фрода (самореферальство, накрутка,
мультиаккаунты). Автоматический скоринг + двухфазное подтверждение (approve → complete)
позволяют платить быстро, но не вслепую.

### 4.3. Партнёрская программа (`/referral/partner/apply`, `/admin/partners`)

Уровень выше обычной рефералки — для арбитражников и владельцев каналов.

**Заявка партнёра:** компания, сайт, Telegram-канал, описание, ожидаемое количество рефералов в
месяц, **желаемый процент комиссии**. Админ рассматривает (`/admin/partners/applications/:id/review`),
одобряет с назначением фактического процента или отклоняет с комментарием.

**Управление партнёром:** индивидуальная комиссия (`/admin/partners/:userId/commission`),
привязка рекламных кампаний (`/admin/partners/:userId/campaigns/assign`), отзыв статуса
(`/admin/partners/:userId/revoke`), глобальные настройки программы (`/admin/partners/settings`).

**Статистика партнёра:** регистрации, рефералы, заработок, конверсия, заработок за сегодня/неделю/
месяц, график по дням, **сравнение периодов** (текущий против предыдущего с трендом up/down/stable),
топ рефералов.

### 4.4. Граф реферальной сети (`/admin/referral-network`)

**Что это.** Интерактивная визуализация реферальных связей на `sigma.js` + `graphology` с
force-directed раскладкой (ForceAtlas2).

**Возможности:** выбор области (`scoped` — по кампании, партнёру, пользователю), детализация по
узлу (пользователь или кампания), поиск по сети.

**Зачем нужно.** Фрод-схемы в рефералке визуально распознаются мгновенно — «звезда» из десятков
пустых аккаунтов вокруг одного узла видна на графе, но незаметна в табличном отчёте.

## 5. Поддержка и коммуникации

### 5.1. Тикет-система (`/support`, `/admin/tickets`)

**Пользователь:** создаёт тикет с темой и текстом, прикрепляет **медиа** (фото/видео/документы,
в том числе несколько файлов — `media_items`), ведёт переписку.

**Админ:** очередь тикетов с фильтрами и статистикой (всего / открытые / ожидающие / отвеченные /
закрытые), ответ, смена **статуса** и **приоритета**, возможность **заблокировать ответы**
в тикете (`is_reply_blocked`).

**Настройки** (`/admin/tickets/settings`):
- **SLA** — включение, целевое время ответа в минутах, интервал проверки, кулдаун напоминаний.
  Просроченные тикеты подсвечиваются и по ним уходят напоминания.
- **Режим системы поддержки** (`support_system_mode`): `tickets` (только тикеты),
  `contact` (только прямой контакт — ссылка на оператора), `both`.
- Раздельные переключатели уведомлений для пользователей и для админов.

**Уведомления о тикетах** — отдельный канал со счётчиком непрочитанных
(`/cabinet/tickets/notifications/unread-count`), отметкой прочтения по одному, по тикету и всех
сразу — и для пользовательской, и для админской стороны.

**Зачем нужно.** SLA-контроль превращает поддержку из «когда-нибудь ответим» в измеримый процесс.
Режим `contact` нужен маленьким сервисам, где тикеты избыточны и всё решается в личке.

### 5.2. Рассылки (`/admin/broadcasts`)

**Каналы:** Telegram, e-mail или **оба сразу** (`channel: 'telegram' | 'email' | 'both'`).

**Таргетинг.** Бэкенд отдаёт готовые сегменты (`BroadcastFilter`) **с количеством получателей в
каждом** — сгруппированные, плюс фильтры по тарифам (`TariffFilter` с числом активных
пользователей) и кастомные фильтры.

**Содержимое:**
- Текст сообщения + **медиа** (фото/видео/документ, загрузка через `/cabinet/media/upload`).
- **Кнопки**: набор преднастроенных (`BroadcastButton` с дефолтами) и произвольные
  (`CustomBroadcastButton`: label + `callback`/`url` + кастомный emoji-иконка).
- Для e-mail — тема и HTML-содержимое, редактируемое **визуальным редактором** (TipTap).
- **Категория** (`system` / `news` / `promo`) — соотносится с пользовательскими настройками
  уведомлений, то есть отключивший промо не получит промо-рассылку.

**Управление:** история рассылок, детальная карточка с прогрессом и **остановка на лету**
(`POST /admin/broadcasts/:id/stop`).

**Зачем нужно.** Счётчики аудитории до отправки не дают выстрелить в 20 000 человек по ошибке;
кнопка стоп — страховка, если ошибка всё же произошла. Учёт категорий — защита от блокировок бота
пользователями и от попадания писем в спам.

### 5.3. Новости (`/news/:slug`, `/admin/news`)

Полноценный блог: статьи с WYSIWYG-редактором (TipTap: форматирование, цвет, выделение,
подчёркивание, выравнивание, ссылки, изображения), **категории** и **теги** с цветами,
загрузка медиа, черновик/публикация (`togglePublish`), **закрепление** важной статьи
(`toggleFeatured`).

**Зачем нужно.** Канал донесения информации о новых локациях, работах и акциях внутри самого
продукта — без зависимости от того, читает ли пользователь Telegram-канал.

### 5.4. Инфостраницы (`/admin/info-pages`, `/info/:slug`)

Произвольные страницы или FAQ-блоки с:
- **мультиязычным** заголовком и содержимым (`Record<lang, string>`),
- иконкой и порядком сортировки (drag-and-drop reorder),
- **режимом отображения** `bot` / `web` / `both` — страница может показываться только в боте,
  только в кабинете или везде,
- **подменой встроенных вкладок** (`replaces_tab`: `faq`, `rules`, `privacy`, `offer`).

**Зачем нужно.** Позволяет владельцу сервиса заменить дефолтные тексты своими юридическими
документами и добавить собственные разделы, не трогая код.

### 5.5. Юридические страницы (`/admin/legal-pages`)

Отдельный редактор правил сервиса и FAQ с версионированием по дате обновления (`updated_at`),
плюс публичные роуты `/privacy` и `/offer`, доступные без авторизации.

### 5.6. Шаблоны e-mail (`/admin/email-templates`)

Для каждого типа системного письма (верификация, сброс пароля, истечение подписки и т. д.) и
**для каждого языка** можно переопределить тему и HTML-тело. Интерфейс показывает список
доступных **переменных контекста** (`context_vars` + общие `common_context_vars`), даёт
**предпросмотр** с подстановкой и **отправку тестового письма** на указанный адрес. Кастомный
шаблон удаляется одной кнопкой — возвращается дефолтный.

**Зачем нужно.** Транзакционные письма — лицо сервиса и главный фактор доставляемости.
Предпросмотр и тестовая отправка избавляют от классического «разослали 5000 писем со сломанной
вёрсткой».

### 5.7. Закреплённые сообщения (`/admin/pinned-messages`)

Сообщение (текст + фото/видео), которое бот показывает пользователям: **перед меню**
(`send_before_menu`) и/или **при каждом `/start`** (`send_on_every_start`). Можно разово
разослать (`broadcast` с отчётом sent/failed), деактивировать или **открепить у всех**
(`unpin` с отчётом).

**Зачем нужно.** Способ донести критичную информацию (миграция домена, авария, смена реквизитов)
до 100% активной аудитории, а не только до тех, кто читает канал.

## 6. Административная панель

### 6.1. Дашборд (`/admin/dashboard`)

Сводка в реальном времени:

- **Ноды**: всего / онлайн / офлайн / отключено, суммарно пользователей онлайн, по каждой ноде —
  адрес, соединение, `users_online`, трафик, uptime Xray, версии Xray и ноды, страна, системная
  информация. Действия прямо с дашборда: **перезапуск** и **включение/выключение** ноды.
- **Подписки**: всего / активных / триальных / платных / истёкших, куплено за сегодня/неделю/месяц,
  **конверсия триал→платная**.
- **Финансы**: доход за сегодня / за месяц / за всё время, отдельно доход с подписок.
- **График выручки** по дням.
- Статистика по тарифам, топ реферреров, топ кампаний, последние платежи, системная информация.

### 6.2. Аналитика продаж (`/admin/sales-stats`)

Отдельный раздел с разрезами за произвольный период:

| Отчёт | Содержание |
|---|---|
| Summary | Общая выручка, ручные пополнения, активные подписки и триалы, новые триалы, новые платные, истёкшие, конверсия триал→платная, продления, выручка с допуслуг |
| Trials | Триалы и регистрации по дням, конверсия, средняя длительность триала, разбивка по провайдерам авторизации |
| Subscriptions | Продажи по тарифам, по периодам, по дням, по дням в разрезе тарифов, средний чек, топ-тариф |
| Renewals | Продления по периодам |
| Addons | Выручка с допуслуг (трафик, устройства) |
| Deposits | Пополнения балансов |
| **Payment health** | Состояние платёжных методов — доля успешных платежей по провайдерам |

**Зачем нужно.** «Payment health» отвечает на вопрос, который иначе всплывает только через жалобы:
какой эквайринг начал отваливаться. Разбивка триалов по провайдерам авторизации показывает,
из какого канала приходят конвертирующиеся пользователи.

### 6.3. Управление пользователями (`/admin/users`, `/admin/users/:id`)

Поиск по списку и по Telegram ID, общая статистика. В карточке пользователя доступно:

**Баланс и подписки:** ручное изменение баланса с описанием операции, изменение подписки,
выдача подписки, сброс подписки, сброс триала.

**Статус и ограничения:** блокировка с причиной / разблокировка, отключение,
**точечные ограничения** (`restriction_subscription` — запретить покупку подписки,
`restriction_topup` — запретить пополнение, с указанием причины), удаление (мягкое и полное).

**Сегментация:** назначение промо-группы, индивидуальный процент реферальной комиссии.

**Рефералы:** список приглашённых, **назначение реферрера вручную**, удаление реферрера,
удаление конкретного реферала.

**Синхронизация с панелью:** статус синхронизации, `sync/from-panel` и `sync/to-panel` — то есть
разрешение расхождений между базой бота и Remnawave в обе стороны.

**Диагностика:** информация из панели (`panel-info`), потребление по нодам (`node-usage`),
журнал активности, история запросов подписки, транзакции, подарки.

**Устройства:** список HWID пользователя, переименование, удаление конкретного, сброс всех.

**Зачем нужно.** Это рабочее место саппорта: почти любой инцидент («не работает», «списали дважды»,
«не вижу подписку») закрывается с одной страницы, без доступа к БД и панели Remnawave.

### 6.4. Массовые операции (`/admin/bulk-actions`)

**Доступные действия:** продлить подписку, добавить дни, отменить подписку, активировать подписку,
сменить тариф, добавить трафик, начислить баланс, назначить промо-группу, выдать подписку,
установить лимит устройств, удалить подписку, удалить пользователя.

**Две страховки:**
1. **`dry_run`** — прогон без изменений: сколько записей будет затронуто, сколько пропущено,
   какие будут ошибки.
2. **SSE-стрим прогресса** (`executeWithStream`) — операция выполняется с живой отдачей событий
   `progress` (текущий/всего, конкретный пользователь, успех/ошибка) и финальным `complete`
   со сводкой.

Опасные операции требуют явных флагов: `delete_from_panel`, `force_delete_active_paid`.

**Зачем нужно.** Компенсация всей базе за аварию, миграция тарифа, зачистка мёртвых аккаунтов —
задачи на тысячи записей. Dry-run превращает необратимую операцию в проверяемую, а стрим прогресса
показывает, что процесс не завис.

### 6.5. Управление Remnawave (`/admin/remnawave`)

Полноценный пульт панели прямо из кабинета:

**Ноды:** список, детальная карточка, статистика по ноде, обзор (`nodes/overview`),
**реалтайм-метрики** (`nodes/realtime`), действия над нодой (`nodes/:uuid/action`),
**перезапуск всех нод**.

**Сквады:** список, детальная карточка (`/admin/remnawave/squads/:uuid`), создание, изменение,
удаление, действия над сквадом, **миграция пользователей между сквадами** (`squads/migrate`).

**Синхронизация:**
- `sync/from-panel` / `sync/to-panel` — массовая синхронизация в обе стороны,
- `sync/servers` — синхронизация списка серверов,
- `sync/subscriptions/statuses` — сверка статусов подписок,
- `sync/subscriptions/validate` — валидация,
- `sync/subscriptions/cleanup` — очистка «сирот»,
- **автосинхронизация** с переключателем, статусом и ручным запуском (`sync/auto/*`),
- **рекомендации** (`sync/recommendations`) — что система советует синхронизировать.

**Мониторинг:** статус подключения к панели, здоровье (`health`), системная информация,
inbounds, статистика по устройствам, **топ потребителей трафика** (`top-consumers`),
история запросов подписки, сводка (`recap`).

**Зачем нужно.** Без этого администратор вынужден держать открытыми две панели и вручную сводить
данные. Рассинхрон между базой бота и Remnawave — самая частая причина «оплатил, но не работает»;
здесь есть и диагностика, и кнопки лечения.

### 6.6. Серверы (`/admin/servers`)

Управление серверами (сквадами) как товарными позициями: отображаемое имя, описание, код страны,
доступность, цена, **лимит пользователей** (`max_users`) с признаком заполненности (`is_full`) и
статусом доступности, порядок сортировки, **право участия в триале**, привязка к промо-группам.
Плюс статистика по серверу и синхронизация списка из панели.

**Зачем нужно.** Лимит пользователей на сервер позволяет не перегружать ноды и создаёт
дефицитность премиум-локаций; привязка к промо-группам делает локации инструментом апсейла.

### 6.7. Мониторинг трафика (`/admin/traffic-usage`)

Таблица потребления по пользователям **в разрезе нод** (`node_traffic: Record<node, bytes>`)
с фильтрами по периоду, тарифу, статусу подписки, набору нод, произвольному диапазону дат,
поиском и сортировкой. **Обогащение данных** (`traffic/enrichment`) добавляет число подключённых
устройств, суммарные траты, даты подписки и последнюю ноду. Есть **экспорт в CSV**.

**Зачем нужно.** Поиск абузеров и понимание, какие ноды нужно масштабировать. Обогащение позволяет
отличить «дорогого, но платящего» пользователя от «дорогого и бесплатного».

### 6.8. Система банов (`/admin/ban-system`)

Отдельная подсистема защиты от шеринга аккаунтов, работающая через агентов на нодах.

**Мониторинг:** статус и здоровье системы (в т.ч. детальное), список агентов и их сводка,
список нод, общая статистика (пользователи, активные, превысившие лимит, всего запросов,
наказаний, активных наказаний, агенты и ноды онлайн, uptime).

**Анализ пользователя:** число **уникальных IP**, всего запросов, лимит, признак превышения,
число блокировок, детальный список IP (с временем первого/последнего появления, нодой, числом
запросов и **геолокацией** — страна, город), лента последних запросов (время, источник, назначение,
порт, протокол, действие, нода) и **определённый тип сети** (`network_type`).

**Действия:** бан пользователя на N минут с причиной, разбан, список наказаний с историей
(кто, когда, за что, когда автоматически разблокируется).

**Настройки:** параметры системы с переключателями и **белым списком** (добавление/удаление).

Отдельно: отчёты, топ по трафику, список нарушений, пользователи сверх лимита.

**Зачем нужно.** Шеринг одного аккаунта на десятки людей — главная утечка выручки в VPN.
Автоматическое обнаружение по числу уникальных IP с учётом типа сети (мобильный оператор
естественным образом даёт много IP) и временный бан вместо перманентного — баланс между защитой
выручки и ложными срабатываниями на честных пользователях.

### 6.9. Платежи (`/admin/payments`, `/admin/payment-methods`)

- **Журнал платежей** с поиском и статистикой (общей и по результатам поиска).
- **Настройка методов оплаты**: включение/выключение, редактирование параметров каждого
  провайдера, **порядок отображения** (drag-and-drop), настройка подопций (например, СБП vs карта
  у Freekassa), лимиты сумм, иконки, `return_url`.
- **Сертификат OverPay** — загрузка PKCS-сертификата с парольной фразой, отображение субъекта,
  срока действия и наличия цепочки, признак блокировки пути/пароля переменными окружения.

**Зачем нужно.** Смена платёжного шлюза при отвале эквайринга — операция на минуты, а не на релиз.

### 6.10. Настройки (`/admin/settings`)

**Редактор конфигурации бота из веб-интерфейса.** Настройки сгруппированы по категориям; каждая
имеет: тип, текущее и оригинальное значение, признак переопределения (`has_override`), список
допустимых значений (`choices`), подсказку с описанием / форматом / примером / предупреждением.

Ключевые защиты:
- `env_locked` — значение задано через переменную окружения и **не редактируется** из UI;
- `read_only` — только чтение;
- `is_secret` — значение маскируется;
- сброс к дефолту (`DELETE /admin/settings/:key`).

**Зачем нужно.** Позволяет менять поведение бота без SSH и рестарта контейнера, но при этом
критичные секреты остаются в `.env` и защищены от изменения через веб.

### 6.11. Обязательные подписки на каналы

`/admin/channel-subscriptions` — список каналов, на которые пользователь обязан быть подписан.
Для каждого: ID канала, ссылка, заголовок, активность, порядок и два важных флага —
**`disable_trial_on_leave`** и **`disable_paid_on_leave`**: отключать ли триальную и/или платную
подписку при отписке от канала.

**Зачем нужно.** Конвертация пользователей сервиса в аудиторию канала. Раздельные флаги позволяют
требовать подписку только от «халявщиков» на триале, не наказывая платящих клиентов.

### 6.12. Прочие админ-разделы

- **`/admin/apps`** — редактор конфигурации клиентских приложений в формате Remnawave app-config:
  платформы, приложения (с признаком `featured`), блоки с заголовком/описанием и кнопками трёх
  типов, локализованные тексты (en/ru/zh/fa/fr), а также привязка к готовому конфигу панели
  по UUID. Это управляет содержимым страницы «Подключение».
- **`/admin/updates`** — проверка обновлений: текущая версия бота и кабинета, наличие новых
  релизов, changelog из GitHub-релизов, ссылки на репозитории.
- **Меню бота** (`/cabinet/admin/menu-layout`) — визуальный конструктор клавиатуры бота:
  строки, кнопки в строке, тип (встроенная/кастомная), стиль (`primary`/`success`/`danger`/
  `default`), кастомный emoji-иконка, локализованные подписи, URL и способ открытия
  (`external` / `webapp`), плюс сброс к дефолту.
- **Стили кнопок** (`/cabinet/admin/button-styles`) — оформление и подписи семи основных разделов
  бота (`home`, `subscription`, `balance`, `referral`, `support`, `info`, `admin`).

## 7. Кастомизация и брендирование

### 7.1. Брендинг

| Что | Endpoint | Описание |
|---|---|---|
| Название сервиса | `PUT /cabinet/branding/name` | Заголовок, вкладка браузера |
| Логотип | `POST/DELETE /cabinet/branding/logo` | Загрузка файла или буквенный фолбэк |
| Палитра | `PATCH /cabinet/branding/colors` | Полная цветовая схема |
| Разрешённые темы | `PATCH /cabinet/branding/themes` | Только тёмная / только светлая / обе |
| Анимация фона | `PATCH /cabinet/branding/animation`, `/animation-config` | Вкл/выкл + тип и параметры |
| Fullscreen | `PATCH /cabinet/branding/fullscreen` | Полноэкранный режим Mini App |
| Футер | `getFooterEnabled` / `updateFooterEnabled` | Показывать ли футер |
| E-mail-авторизация | `PATCH /cabinet/branding/email-auth` | Вкл/выкл + требовать ли верификацию |
| Подарки | `PATCH /cabinet/branding/gift-enabled` | Вкл/выкл раздел подарков |

Build-time переменные (`VITE_APP_NAME`, `VITE_APP_LOGO`, `VITE_TELEGRAM_BOT_USERNAME`,
`VITE_API_URL`) задают дефолты; runtime-брендинг из API их переопределяет.

**Зачем нужно.** Позволяет продавать один и тот же движок разным операторам под их брендом,
причём смена бренда — это настройка в админке, а не пересборка образа.

### 7.2. Аналитика

- **Яндекс.Метрика** (`yandex_metrika_id`) и **Google Ads** (`google_ads_id` + `google_ads_label`)
  — счётчики подключаются настройкой, без правки кода (`hooks/useAnalyticsCounters.ts`).
- **Офлайн-конверсии** (`offline_conv_*`): включение, ID счётчика, measurement secret (хранится
  маскированным), список целей (`name` + `event_id` + правило дедупликации).
- **ClientID Яндекса** (`utils/yandexCid.ts`) — CID пробрасывается в **каждую покупку**:
  продление, покупка трафика, покупка устройств, покупка тарифа передают `yandex_cid` на бэкенд.

**Зачем нужно.** Это то, что превращает рекламу из «слива бюджета» в управляемый канал: платёж
происходит на бэкенде (иногда через сутки после клика), и без офлайн-конверсий с CID рекламные
системы никогда не узнают, какой клик принёс деньги.

### 7.3. Верификация сайта

`GET /cabinet/public/site-verification` (`hooks/useSiteVerification.ts`) — выдача мета-тегов
верификации для поисковых систем и вебмастер-панелей без пересборки фронтенда.

## 8. Матрица feature-флагов

Часть разделов появляется в навигации только при определённых условиях
(`hooks/useFeatureFlags.ts`):

| Раздел | Условие показа | Источник |
|---|---|---|
| Рефералы | `referral_terms.is_enabled` | `/cabinet/referral/terms` |
| Колесо фортуны | `wheel_config.is_enabled` | `/cabinet/wheel/config` |
| Конкурсы | `count > 0` | `/cabinet/contests/count` |
| Опросы | `count > 0` | `/cabinet/polls/count` |
| Подарки | `gift.enabled` | `/cabinet/branding/gift-enabled` |
| Вкладки инфо | `visibility.{faq,rules,privacy,offer,recurrent}` | `/cabinet/info/visibility` |
| Разделы админки | наличие права `<resource>:read` | RBAC |

**Отдельная деталь реализации.** Значения флагов кэшируются в `localStorage`
(ключ `cabinet-feature-flags`): пока запросы в полёте, флаги были бы `undefined`, вкладки
«Рефералы»/«Колесо» появлялись бы с задержкой и нижняя навигация «прыгала» при каждом холодном
старте. Кэш убирает layout shift, а при изменении флага на бэкенде UI догоняет после ответа.

**Зачем нужно.** Один бинарник обслуживает сервисы с очень разной конфигурацией: кому-то не нужны
рефералы, кто-то не хочет геймификации. Пункт меню, ведущий на выключенную функцию, — худший
вариант; feature-флаги убирают его полностью.

## Сводка: что это даёт бизнесу

| Блок | Ключевая ценность |
|---|---|
| Мультиавторизация + merge | Не терять пользователей на границе «бот ↔ веб» |
| Конструктор подписок + превью | Выше средний чек, меньше споров и возвратов |
| ~25 платёжных провайдеров | Устойчивость к отвалу эквайринга |
| Лендинги + кампании | Измеримый ROI рекламы, покупка без регистрации |
| Промо-группы + лояльность | Автоматическое удержание и апсейл |
| Промо-офферы | Возврат отваливающихся по триггеру |
| Купоны | B2B/реселлинг-канал |
| Рефералка + партнёрка + граф | Дешёвое привлечение с контролем фрода |
| Ban-system | Защита выручки от шеринга аккаунтов |
| Remnawave-пульт + синхронизация | Быстрое разрешение «оплатил, но не работает» |
| RBAC + аудит | Безопасное масштабирование команды |
| Брендинг + i18n | White-label и выход на RU/IR/CN рынки |
